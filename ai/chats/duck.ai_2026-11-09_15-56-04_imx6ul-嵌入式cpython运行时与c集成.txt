这是为 60 MB 空闲 Flash 设定的项目预算；如果 `ssl`、`sqlite3` 等还没有包含在原系统里，依赖库也会计入增量，最终要以目标镜像测量为准。Buildroot 支持用 `make graph-size` 查看包和文件对目标文件系统大小的贡献；其文档说明，体积统计应在完整干净构建后评估。[3]

构建后至少检查：

```bash
make clean
make
make graph-size
```

如果完整 `make clean` 对你的迭代成本太高，可以在试验阶段先做普通比较；但正式记录体积数据时，按 Buildroot 文档建议做干净构建，避免把增量构建结果误当成完整统计。最后还要测设备实际启动后的 RSS/峰值内存，因为 Flash 上的安装体积不等于进程运行内存。

## 5. 面向微电网策略的边界

这套裁剪方案能让 CPython 运行时更小，也能避免运行期间反复解析源码；**它不会赋予 Python 硬实时保证**。建议把高频采样、快速闭环、保护判断和执行输出留在 C/C++ 或独立控制器中，让 Python 提供较慢时标的策略计算和设定值更新。上线前应在设备负载下测控制调用的 P99.9 和最坏响应时间，并由原生层对 Python 输出做范围、超时和故障检查。

可以把 CPython **嵌入现有 C 程序**，由 C 程序控制解释器生命周期、加载策略模块和调用策略函数；再把一小组经过审核的 C 接口注册为 Python 内置模块，供策略调用。推荐结构是：**单个长驻 CPython 解释器 + 独立策略线程 + C 函数提供受控网关 API**。

先特别注意：导入 `.py` 时，CPython 会在缓存有效时加载对应 `.pyc`；但 `.pyc` 仍是 CPython 字节码，不是原生机器码。若采用无源码部署，普通 `__pycache__/模块名.cpython-版本.pyc` 在源码缺失时不会被标准导入器加载；要么部署源码和缓存，要么使用源码缺失时可导入的传统位置 `模块名.pyc`。[1]

## 1. 运行时与文件布局

先固定一个 CPython 次版本，例如设备固件所选的 `3.x`，C 程序、CPython 库、C 接口模块和策略字节码都按这个版本构建。`.pyc` 文件包含字节码格式版本标记，不能指望升级 CPython 后继续兼容。[2]

一个可维护的设备布局示例：

```text
/usr/lib/libpython3.x.so
/usr/lib/python3.x/                 # CPython 标准库
/usr/lib/python3.x/lib-dynload/     # 标准库中的本地扩展模块，需要时保留
/opt/gateway/strategy/current/      # 当前策略包
/opt/gateway/strategy/staged/       # 新策略暂存区
```

`python3.x` 及标准库路径请以设备上的实际安装位置为准。策略配置文件与 Python 程序分开保存：**普通参数变化只重新加载配置，不要因此重新解析脚本。**

策略部署有两种方式：

- **保留 `.py` 和预编译缓存：** 使用包内 `__pycache__` 目录；发布时验证源码和缓存匹配，设备文件系统设为只读，关闭运行时写缓存。
- **只部署 `.pyc`：** 构建时用 `compileall -b` 生成传统位置的 `.pyc`，例如 `strategy.pyc`，再在目标设备上验证导入。不要只留下 `__pycache__` 里的缓存文件。[1]

若源码与字节码一起部署，可用 checked-hash 缓存验证二者匹配；如果改用 unchecked-hash 以跳过导入时的校验，就必须由固件或策略安装流程校验包的签名/哈希，避免加载过期或不匹配的字节码。[2]

## 2. 将 C 功能注册为内置 Python 模块

对于与 C 主程序紧密耦合的接口，推荐做成**内置模块**，例如 Python 中的 `import gw`。它比让脚本直接访问设备节点或调用任意 C 符号更易限制权限，也不需要再部署一个单独的扩展 `.so`。

下面是一个简化示例。假设主程序提供读取测量快照和提交设定值的接口：

```c
#define PY_SSIZE_T_CLEAN
#include <Python.h>
#include <math.h>

struct grid_snapshot {
    double active_power_kw;
    double frequency_hz;
};

/* 由现有 C 程序提供：
   读取一份一致的快照；提交设定值到安全队列。 */
extern int grid_snapshot_read(struct grid_snapshot *out);
extern int grid_enqueue_power_setpoint(double kw);

#define POWER_MIN_KW (-500.0)
#define POWER_MAX_KW ( 500.0)

static PyObject *
gw_get_measurements(PyObject *self, PyObject *args)
{
    struct grid_snapshot s;

    if (!grid_snapshot_read(&s)) {
        PyErr_SetString(PyExc_RuntimeError, "measurement snapshot unavailable");
        return NULL;
    }

    return Py_BuildValue(
        "{s:d,s:d}",
        "active_power_kw", s.active_power_kw,
        "frequency_hz", s.frequency_hz
    );
}

static PyObject *
gw_request_power(PyObject *self, PyObject *args)
{
    double kw;

    if (!PyArg_ParseTuple(args, "d:request_power", &kw))
        return NULL;

    if (!isfinite(kw) || kw < POWER_MIN_KW || kw > POWER_MAX_KW) {
        PyErr_SetString(PyExc_ValueError, "power setpoint out of range");
        return NULL;
    }

    /* 建议只入队；由原生控制任务校验并执行，不在此处直接操作硬件。 */
    if (!grid_enqueue_power_setpoint(kw)) {
        PyErr_SetString(PyExc_RuntimeError, "setpoint queue unavailable");
        return NULL;
    }

    Py_RETURN_NONE;
}

static PyMethodDef gw_methods[] = {
    {"get_measurements", gw_get_measurements, METH_NOARGS,
     "Return a measurement snapshot."},
    {"request_power", gw_request_power, METH_VARARGS,
     "Submit a checked power setpoint."},
    {NULL, NULL, 0, NULL}
};

static struct PyModuleDef gw_module = {
    PyModuleDef_HEAD_INIT,
    "gw",
    "Gateway APIs exposed to strategy scripts.",
    -1,                 /* 单解释器示例；有模块可变状态时应设计模块状态 */
    gw_methods
};

PyMODINIT_FUNC
PyInit_gw(void)
{
    return PyModule_Create(&gw_module);
}
```

`PyMethodDef` 方法表是把 C 函数暴露为 Python 模块函数的常规方式。[3] 主程序应将真正敏感的操作封装在 `grid_enqueue_power_setpoint()` 这类 C 接口中；由原生代码再次做范围、状态和安全联锁检查，不能把保护责任交给 Python 脚本。

策略中的调用可以类似这样：

```python
import gw

def step():
    m = gw.get_measurements()
    # 做策略计算
    target_kw = calculate_target(m)
    gw.request_power(target_kw)
```

实际策略函数最好一次获取一份一致的测量快照、完成一批计算，再提交结果；避免每个测量字段都跨一次 Python/C 边界。

## 3. 在 C 程序中初始化解释器

内置模块必须在初始化解释器**之前**注册。推荐用 `PyConfig_InitIsolatedConfig()` 和 `Py_InitializeFromConfig()` 管理路径和环境，而不是只调用无配置的 `Py_Initialize()`。文档将 isolated configuration 定位为把 Python 嵌入应用、隔离环境配置的用法。[4]

结构示意如下；路径要替换成目标固件真实路径：

```c
#include <Python.h>
#include <stdio.h>

static int
append_python_path(PyConfig *config, const wchar_t *path)
{
    PyStatus status = PyWideStringList_Append(
        &config->module_search_paths, path
    );
    return PyStatus_Exception(status) ? -1 : 0;
}

static int
init_embedded_python(void)
{
    PyConfig config;
    PyStatus status;

    if (PyImport_AppendInittab("gw", PyInit_gw) == -1) {
        fprintf(stderr, "cannot register built-in module gw\n");
        return -1;
    }

    PyConfig_InitIsolatedConfig(&config);
    config.use_environment = 0;
    config.site_import = 0;
    config.install_signal_handlers = 0;
    config.write_bytecode = 0;

    /*
     * 显式指定模块搜索路径，避免依赖启动目录、PYTHONPATH 或用户环境。
     * 路径随 CPython 版本、Buildroot 配置和目标镜像调整。
     */
    config.module_search_paths_set = 1;

    if (append_python_path(&config, L"/usr/lib/python3.x") < 0 ||
        append_python_path(&config, L"/usr/lib/python3.x/lib-dynload") < 0 ||
        append_python_path(&config, L"/opt/gateway/strategy/current") < 0) {
        PyConfig_Clear(&config);
        fprintf(stderr, "cannot set Python module search paths\n");
        return -1;
    }

    status = Py_InitializeFromConfig(&config);
    if (PyStatus_Exception(status)) {
        fprintf(stderr, "Python initialization failed: %s\n",
                status.err_msg ? status.err_msg : "unknown error");
        PyConfig_Clear(&config);
        return -1;
    }

    PyConfig_Clear(&config);
    return 0;
}
```

这段示例的 `python3.x` 是占位符，必须替换为实际目录。因为显式设置了 `module_search_paths_set`，必须把策略目录以及运行所需的标准库和扩展模块目录都列全；如果用了 `ssl`、`math` 等本地扩展模块，通常要保证对应的 `lib-dynload` 模块和依赖库也安装在目标系统中。

初始化失败时，建议让主程序**禁用策略功能或按产品设计进入安全降级状态**，不要带着未初始化或初始化不完整的解释器继续运行。

## 4. 从 C 加载策略模块并调用函数

模块导入后会执行一次模块顶层代码；之后 C 程序应保存函数对象并重复调用它，而不是每个控制周期重新导入或启动 Python。

```c
static PyObject *strategy_step = NULL;

static int
load_strategy(void)
{
    PyObject *module = PyImport_ImportModule("strategy");
    if (module == NULL) {
        PyErr_Print();
        return -1;
    }

    PyObject *func = PyObject_GetAttrString(module, "step");
    Py_DECREF(module);

    if (func == NULL || !PyCallable_Check(func)) {
        Py_XDECREF(func);
        PyErr_Print();
        return -1;
    }

    Py_XDECREF(strategy_step);
    strategy_step = func;  /* 保存新引用 */
    return 0;
}

static int
call_strategy(double active_power_kw, double frequency_hz, double *target_kw)
{
    PyObject *result = PyObject_CallFunction(
        strategy_step, "dd", active_power_kw, frequency_hz
    );

    if (result == NULL) {
        PyErr_Print();
        return -1;
    }

    double value = PyFloat_AsDouble(result);
    Py_DECREF(result);

    if (PyErr_Occurred()) {
        PyErr_Print();
        return -1;
    }

    *target_kw = value;
    return 0;
}
```

对应的策略脚本例如：

```python
def step(active_power_kw, frequency_hz):
    # 在这里实现策略算法
    return desired_power_kw
```

这是简化调用示例。产品代码还应对返回值做有限值、范围、执行时限和策略状态检查。Python 异常不应被忽略；要记录异常并采取明确的降级策略。

## 5. 线程和微电网控制周期

建议把 Python 调用放在一个**专用策略线程**中：该线程负责初始化解释器、加载策略并调用 Python；C 主线程和采集线程通过原生快照、消息队列等方式与它交换数据。这样可以避免多线程同时操作 Python 对象，也避免 Python 调用阻塞关键控制任务。

默认 CPython 构建中，调用 Python C API 的线程需要持有相应的线程状态/GIL；由 C 主程序创建的其他线程不能不加管理地直接调用 Python API。若确实要从其他 C 线程调用，必须按 CPython 版本的线程状态接口正确获取和释放状态。对你这个场景，单一策略线程通常更简单稳妥。[5]

此外，Python 接口应尽量**读快照、投递命令，不等待硬件动作完成**。高频保护、快速闭环和硬实时动作仍留在原生控制任务中；Python 负责较慢时标的策略计算。把解释器集成到 C 进程并不会让 Python 字节码拥有硬实时保证。

## 6. 交叉编译与链接

应用程序必须针对设备的 ARM ABI 和同一目标 sysroot 编译，并链接目标侧的 CPython 头文件和库：

- 头文件使用 Buildroot staging/sysroot 中的 `Python.h`，不能误用开发机头文件。
- 链接目标侧的 `libpython3.x`；使用动态库时，要确保相应 `.so` 随 rootfs 安装。
- 不要直接复制开发机 `python3-config` 输出的路径或链接参数；它们可能指向宿主机 Python。
- 将 `gw` 模块的 `PyInit_gw()` 编进主程序，并确认它在 Python 初始化前注册。
- 确认所需本地标准库模块及其共享库依赖已经进入目标文件系统。

Buildroot 的目标包和应用包要使用同一套构建配置与 sysroot；交叉构建能否成功，不只取决于 `-lpython3.x`，还取决于目标 Python 的构建选项和依赖。

## 7. 策略更新与测试

首版建议在网关启动时加载一次策略；更新时把新版本写入 `staged` 目录，先校验包签名/哈希，再在设备上做导入和策略自检，通过后切换到新版本。若要求**不停机热更新**，不要简单假定重新 `import` 就会替换所有旧函数和状态；应设计版本化模块加载和函数指针切换，或让策略解释器运行在可重启的独立进程中。

测试至少覆盖：

- `.py` 源码加载、有效 `.pyc` 加载、无源码 `.pyc` 加载三种情况。
- 缓存版本不匹配、缓存损坏、文件缺失和导入异常。
- C 接口的参数边界、无效值、队列满和设备故障。
- 策略异常或超时后的降级行为。
- 设备真实负载下的控制调用 P99.9 和最大响应时间。

**推荐实施顺序：**先只在 C 程序启动时加载一个 `strategy` 模块，稳定实现 `gw.get_measurements()` 和 `gw.request_power()` 两个接口；接着用有效缓存确认可正常导入；最后再加策略版本切换和更复杂的 C API。
