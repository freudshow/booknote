先把概念拆开：**UTC、local time（本地时间）和 `CLOCK_MONOTONIC` 不是同一类东西。** `clock_gettime()` 里的时钟 ID 选择“用哪种规则取时间”；UTC/本地时间则是把日历时间解释或显示成什么样。Linux 的 `struct timespec` 只是秒和纳秒，不自带时区标签。

### Linux 常见时钟

| 时钟 | 表示什么 | 会不会跳变或受校时影响 | 挂起（suspend）期间 | 适合用途 |
|---|---|---|---|---|
| `CLOCK_REALTIME` | 系统墙上时间，通常理解为自 Unix Epoch 起的秒数 | 管理员改时间可能使它跳变；NTP 也会校正它 | 挂起后反映现实时间 | 日期时间戳、显示时间、与外部系统对时 |
| `CLOCK_MONOTONIC` | 系统启动后的单调时间，起点没有日历意义 | 不会因手动改墙上时间而跳变；频率可能被 NTP 渐进调整 | Linux 通常不计入挂起时间 | 测量程序耗时、超时、间隔 |
| `CLOCK_MONOTONIC_RAW` | 未经内核时间校正的底层单调时钟 | 不受 NTP 的频率校正影响；速率可能随硬件时钟漂移 | 不计入挂起时间 | 观察硬件时钟漂移、特定校时场景 |
| `CLOCK_BOOTTIME` | 类似 `CLOCK_MONOTONIC`，但把挂起时间也算进去 | 不因墙上时间被手动调整而跳变 | **计入**挂起时间 | 希望“现实经过多久”包含睡眠/挂起的超时 |
| `CLOCK_TAI` | TAI 时间尺度的系统时钟 | 与墙上时间相关，但不按 UTC 闰秒方式跳变；正确性依赖系统配置 | 通常随系统时间推进 | 需要避免 UTC 闰秒影响的时间计算 |
| `CLOCK_REALTIME_COARSE`、`CLOCK_MONOTONIC_COARSE` | 对应时钟的低精度、较快读取版本 | 基本语义分别跟随对应的 `REALTIME` / `MONOTONIC` | 跟随对应时钟 | 大量读取时可接受较低分辨率的场景 |
| `CLOCK_PROCESS_CPUTIME_ID` | 当前进程实际消耗的 CPU 时间 | 不表示墙上经过时间 | 进程没运行时不增长 | 测量进程 CPU 用量 |
| `CLOCK_THREAD_CPUTIME_ID` | 当前线程实际消耗的 CPU 时间 | 不表示墙上经过时间 | 线程没运行时不增长 | 测量某个线程的 CPU 用量 |

这些时钟的定义和 Linux 提供的变体可参见 `clock_gettime()` 文档；`COARSE` 版本以读取更快为取舍，精度较低。[1,2]

### UTC 和 local time 怎么对应？

- `CLOCK_REALTIME` 的数值是自 Epoch 起的时间值，**不是“本地时区时间”**。程序要显示 UTC，通常用 `gmtime()`；要按当前时区显示本地时间，用 `localtime()`。
- 本地时间是根据时区规则（如 `TZ` 环境变量或系统时区设置）转换出来的；更改时区通常改变显示结果，不是把系统时钟往前或往后拨。
- UTC 与本地时间的差别通常是时区偏移和夏令时规则。涉及闰秒时，还要注意 POSIX 时间及系统实现对闰秒的处理方式；不要把 `CLOCK_REALTIME` 当成能精确表达所有 UTC 闰秒细节的通用时间尺度。

### 容易混淆的另外两种“时钟”

**硬件 RTC** 是主板上的实时时钟，断电后通常靠电池继续计时；它和 `clock_gettime()` 暴露给程序的时钟 ID 不是一回事。系统启动时可从 RTC 初始化系统时间，之后程序通常读取的是内核维护的系统时钟。RTC 里存 UTC 还是本地时间，取决于系统配置。

**闹钟时钟** `CLOCK_REALTIME_ALARM` 和 `CLOCK_BOOTTIME_ALARM` 则是给定时器使用的时钟类型，可用于在系统挂起时唤醒系统；它们不是另一套普通时间表示。Linux 还支持一些设备时钟，例如通过动态时钟 ID 读取特定 PTP 设备。[1]

### 实际怎么选

- **测耗时、实现超时：**通常用 `CLOCK_MONOTONIC`。
- **超时要把系统挂起时间也算上：**用 `CLOCK_BOOTTIME`。
- **写日志或显示日期时间：**用 `CLOCK_REALTIME`，再按 UTC 或本地时区格式化。
- **测 CPU 消耗：**用进程或线程 CPU 时钟。
- **不要直接相减 `CLOCK_REALTIME` 的两次读数来测耗时**：系统时间可能被校正或跳变；应改用单调时钟。[1,2]

最适合这种需求的通常是 **`tmpfs`**：它挂载后就是一个正常的目录树，可以用 `mkdirat()`、`openat()`、`unlinkat()`、`renameat()` 等普通文件 API 管理目录和文件。创建挂载需要 `CAP_SYS_ADMIN`；仅仅 `geteuid()==0` 不一定够，比如容器、用户命名空间或受限的服务进程可能没有该能力。[1]

下面的例子创建 `/run/myapp-tmpfs`，挂载一个最多 64 MiB、最多 4096 个 inode 的 `tmpfs`，再创建子目录和文件：

```c
#define _GNU_SOURCE

#include <sys/mount.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <unistd.h>
#include <errno.h>
#include <stdio.h>
#include <string.h>

static int write_all(int fd, const char *buf, size_t len)
{
    while (len > 0) {
        ssize_t n = write(fd, buf, len);
        if (n < 0) {
            if (errno == EINTR)
                continue;
            return -1;
        }
        buf += n;
        len -= (size_t)n;
    }
    return 0;
}

int main(void)
{
    const char *mnt = "/run/myapp-tmpfs";

    /* 创建挂载点；如果已存在，后面的 mount 仍可能因已挂载而失败。 */
    if (mkdir(mnt, 0700) == -1 && errno != EEXIST) {
        perror("mkdir mountpoint");
        return 1;
    }

    /*
     * size 是上限，不是启动时一次性预留的 RAM。
     * mode=0700 限制挂载根目录权限。
     * nosuid,nodev,noexec 是适合一般临时数据目录的安全选项。
     */
    if (mount("tmpfs", mnt, "tmpfs",
              MS_NOSUID | MS_NODEV | MS_NOEXEC,
              "size=64m,nr_inodes=4096,mode=0700") == -1) {
        perror("mount tmpfs");
        return 1;
    }

    int rootfd = open(mnt, O_RDONLY | O_DIRECTORY | O_CLOEXEC);
    if (rootfd == -1) {
        perror("open mountpoint");
        return 1;
    }

    if (mkdirat(rootfd, "data", 0700) == -1 && errno != EEXIST) {
        perror("mkdirat data");
        close(rootfd);
        return 1;
    }

    int dirfd = openat(rootfd, "data",
                       O_RDONLY | O_DIRECTORY | O_CLOEXEC | O_NOFOLLOW);
    if (dirfd == -1) {
        perror("openat data");
        close(rootfd);
        return 1;
    }

    int fd = openat(dirfd, "hello.txt",
                    O_WRONLY | O_CREAT | O_TRUNC |
                    O_CLOEXEC | O_NOFOLLOW,
                    0600);
    if (fd == -1) {
        perror("openat hello.txt");
        close(dirfd);
        close(rootfd);
        return 1;
    }

    const char msg[] = "temporary data in tmpfs\n";
    if (write_all(fd, msg, sizeof(msg) - 1) == -1) {
        perror("write");
        close(fd);
        close(dirfd);
        close(rootfd);
        return 1;
    }

    close(fd);
    close(dirfd);
    close(rootfd);

    puts("tmpfs mounted; wrote /run/myapp-tmpfs/data/hello.txt");
    return 0;
}
```

例如保存为 `tmpfs_demo.c`，可用 `gcc -Wall -Wextra -O2 tmpfs_demo.c -o tmpfs_demo` 编译。挂载选项通过 `mount()` 的最后一个参数传入；`size=` 和 `nr_inodes=` 分别限制文件系统可用空间和 inode 数量。[1,2]

挂载成功后，就像管理普通目录一样管理它：

- 创建目录：`mkdirat(dirfd, "subdir", 0700)`
- 打开或创建文件：`openat(dirfd, "file", O_CREAT | O_WRONLY, 0600)`
- 删除文件：`unlinkat(dirfd, "file", 0)`
- 删除空目录：`unlinkat(dirfd, "subdir", AT_REMOVEDIR)`
- 重命名：`renameat(old_dirfd, "old", new_dirfd, "new")`

使用目录文件描述符配合 `*at()` 系列函数，通常比不断拼接绝对路径更容易控制文件操作范围。`O_NOFOLLOW` 可避免最后一个路径分量是符号链接时跟随它。

**生命周期和资源注意事项：**`tmpfs` 内容在卸载后会丢失；它按实际使用量消耗内存，但在系统配置允许时也可能使用 swap，所以它不等于“绝不使用 swap 的 RAM 磁盘”。嵌入式设备上建议设置明确的 `size=` 和 `nr_inodes=` 上限，避免数据或小文件数量失控。[2]

程序不退出就不会自动卸载。确定不再使用时，可调用：

```c
if (umount2("/run/myapp-tmpfs", 0) == -1)
    perror("umount2");
```

如果目录或文件仍被打开、某进程的当前目录位于该挂载内，卸载可能失败。另一个要点是：挂载会改变**当前挂载命名空间**中的目录视图；如果不希望影响同一命名空间内的其他进程，应考虑在独立挂载命名空间中操作。

**`tmpfs` 是 Linux 的一种临时文件系统**：挂载后，它像普通文件系统一样提供目录、文件、权限和读写操作，但内容由内核放在虚拟内存中管理，而不是写入普通磁盘文件系统。它不需要块设备或 `mkfs`；卸载该挂载点后，里面的内容就丢失。[1,2]

### 它占用的是 RAM 吗？

通常会占用 RAM，但不能简单理解成“所有内容永远锁在物理内存里”。tmpfs 按使用量动态增长和缩小；如果系统启用了 swap，tmpfs 中不常用的页面也可能被换出到 swap。`size=` 设定的是该挂载的**容量上限**，不是挂载时预留这么多 RAM，也不保证系统一定有足够资源让它用满。[1,2]

例如：

```sh
mkdir -p /mnt/ramdisk
mount -t tmpfs -o size=64m,nr_inodes=4096,mode=0700 tmpfs /mnt/ramdisk

mkdir -p /mnt/ramdisk/data
echo "临时内容" > /mnt/ramdisk/data/test.txt

df -h /mnt/ramdisk
df -i /mnt/ramdisk
```

这里 `size=64m` 限制该挂载最多使用约 64 MiB，`nr_inodes=4096` 限制文件和目录数量，`mode=0700` 设置挂载根目录权限。文件太多可能先耗尽 inode；空间或 inode 不足时，新建文件或写入可能失败。`df -h` 看空间，`df -i` 看 inode 使用情况。

### 它和 ramfs、RAM disk 有何不同？

- **tmpfs**：动态使用内存，有容量和 inode 限制，可使用 swap。
- **ramfs**：也是内存中的文件系统，但没有可配置的容量上限，也不能使用 swap；写得过多可能耗尽系统内存。
- **RAM disk**（如 `/dev/ram0`）：模拟固定大小的块设备，通常还要在上面创建 ext4 等文件系统；它和 tmpfs 的实现方式不同。[1]

因此，通常需要临时目录时会选 **tmpfs**，而不是不设上限的 ramfs。

### 常见用途

- `/run`：常用于保存本次启动期间的运行状态，例如 PID 文件、socket 和服务状态。
- `/dev/shm`：常用于进程间共享内存。
- `/tmp`：有些系统会把临时文件目录放在 tmpfs 上。
- 应用自己的临时数据：例如缓存、解压中间文件、短期日志。

`/run`、`/tmp` 是目录名或用途约定；**它们是否挂载为 tmpfs，要看系统配置**。[1]

### 嵌入式设备上要留意什么？

1. **别存需要保留的数据。** 卸载或重启后内容会消失，突然断电也不会保留。
2. **设好资源上限。** 除 `size=` 外，如果应用可能创建大量小文件，也要考虑 `nr_inodes=`。上限设得过大并不代表设备有足够内存。
3. **它会和应用竞争内存。** 大量写入 tmpfs 可能让其他进程可用内存减少；如果设备没有 swap，压力会直接落在 RAM 上。
4. **速度不等于必然更快。** tmpfs 避免了普通磁盘写入，但仍受内存带宽、内存压力、文件大小和访问模式影响。
5. **确认内核支持。** 若挂载时报“不支持的文件系统类型”等错误，检查内核是否启用了 tmpfs 支持；某些嵌入式系统还需要确认 `mount` 工具是否支持相应选项。

总的来说，tmpfs 适合**可丢弃、短期、需要像文件一样访问的数据**；不适合唯一副本、重要日志或需要断电保存的数据。
