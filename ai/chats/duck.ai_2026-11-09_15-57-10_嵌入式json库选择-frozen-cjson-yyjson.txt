对于 **STM32F103ZET6 这类资源受限、通常没有 RTOS 或不希望依赖堆的嵌入式场景**，我首推：

## 推荐：Frozen

**Frozen** 同时提供 JSON 解析和生成能力，采用类似 `json_scanf()` / `json_printf()` 的接口，目标就是嵌入式系统；它还提供基于回调的低层解析接口，可以避免构造完整的 JSON 树。[1]

它比较适合你的原因是：

- 支持**反序列化**：JSON → C 变量或结构体字段；
- 支持**序列化**：C 变量 → JSON 字符串；
- 可以使用调用者提供的固定缓冲区；
- 不需要像 cJSON 那样默认构造一棵完整的动态 JSON 树；
- 支持低层回调解析，适合串口、TCP、HTTP 分包接收；
- 代码量和 API 相对可控，适合裸机或简单 RTOS 环境。

典型用法类似：

```c
#include "frozen.h"

typedef struct
{
    int id;
    int temperature;
    int enabled;
} device_config_t;

device_config_t cfg;
char tx_buf[128];

const char *json =
    "{\"id\":123,\"temperature\":25,\"enabled\":true}";

/* 反序列化 */
json_scanf(json,
           strlen(json),
           "{id:%d, temperature:%d, enabled:%B}",
           &cfg.id,
           &cfg.temperature,
           &cfg.enabled);

/* 序列化 */
int len = json_printf(tx_buf,
                      sizeof(tx_buf),
                      "{id:%d, temperature:%d, enabled:%B}",
                      cfg.id,
                      cfg.temperature,
                      cfg.enabled);
```

不过，使用 Frozen 时应避免依赖会动态分配内存的格式选项，例如字符串复制相关的用法。字符串字段最好使用固定数组、长度检查和显式拷贝，并对 `json_printf()` 的返回值进行边界判断。

## 几个常见库的选择

| 库 | 序列化 | 反序列化 | 动态内存风险 | 适合 STM32F103 | 评价 |
|---|---:|---:|---:|---:|---|
| **Frozen** | 支持 | 支持 | 较低，可控制 | **很适合** | 首选，适合固定结构和通信协议 |
| **cJSON** | 支持 | 支持 | 较高 | 一般 | API 最容易上手，但默认使用 `malloc/free` 并构造树 |
| **tiny-json + json-maker** | 需配合 json-maker | 支持 | 很低 | 适合 | 适合静态内存，但需要两个库 |
| **jsmn** | 不支持 | 仅分词 | 无动态内存 | 很适合解析 | 极简，但需要自己写字段提取和 JSON 生成 |
| **Parson** | 支持 | 支持 | 较高 | 不太推荐 | 易用，但更偏桌面/通用应用 |

### cJSON

cJSON 的优点是成熟、资料多、API 直观。但解析时会为每个 JSON 节点建立 `cJSON` 结构，默认使用 `malloc/free`；输出 JSON 时也可能进行动态扩容。虽然可以通过 `cJSON_InitHooks()` 替换内存分配器，也可以用 `cJSON_PrintPreallocated()` 避免输出缓冲区动态分配，但解析树本身仍然有额外内存开销。[2]

因此，在 STM32F103 上：

- JSON 很小；
- 业务代码已经大量使用 cJSON；
- 有可靠的内存池；
- 可以接受固定的最大节点数；

那么 cJSON 也可以使用。但不建议直接使用系统堆作为长期运行设备的唯一方案，因为堆碎片和异常路径上的释放问题会降低可预测性。实际嵌入式项目中，cJSON 依赖大量 `malloc/free` 可能造成内存不足或碎片问题。[3]

### jsmn

jsmn 非常小，约两百行代码、无依赖、无动态内存、支持增量解析，并且只保存 token 的位置和长度。[4]

它适合：

```text
串口接收 JSON
        ↓
jsmn 分词
        ↓
自己查找 key
        ↓
strtoul / atoi / 自定义转换
```

但是 jsmn **不是完整的序列化/反序列化库**：

- 没有 JSON 生成器；
- 不会自动把 JSON 映射到 C 结构体；
- 需要自己处理字符串转义、数值范围、字段类型和数组遍历。

如果你的协议字段非常少，jsmn 加一个自定义 JSON 输出函数反而可能是最省资源的方案；如果希望直接获得可维护的双向序列化 API，则不如 Frozen。

### tiny-json

tiny-json 的设计很适合嵌入式：不使用动态内存，可以由用户静态预留 `json_t` 节点数组；字符串通常直接引用原始 JSON 缓冲区，不复制内容。[5]

但它主要解决的是**解析**，项目说明也建议使用另一个 `json-maker` 来创建 JSON。因此它适合：

- 反序列化要求高；
- 序列化格式比较固定；
- 愿意搭配一个轻量生成器；
- 希望完全静态内存。

## 我的具体建议

### 情况一：普通设备配置、命令、状态上报

选择：

> **Frozen + 静态收发缓冲区**

例如：

```c
#define JSON_RX_SIZE  256
#define JSON_TX_SIZE  256

static char json_rx[JSON_RX_SIZE];
static char json_tx[JSON_TX_SIZE];
```

同时限制：

- 最大 JSON 长度；
- 最大嵌套深度；
- 最大字符串长度；
- 数组最大元素数量；
- 整数取值范围；
- 不使用浮点数，优先使用整数或定点数。

### 情况二：极端节省 Flash/RAM，字段非常少

选择：

> **jsmn + 自定义序列化函数**

例如发送数据时直接使用：

```c
int json_make_status(char *buf, size_t size,
                     uint32_t id, int temperature)
{
    int n = snprintf(buf, size,
                     "{\"id\":%lu,\"temperature\":%d}",
                     (unsigned long)id,
                     temperature);

    if (n < 0 || (size_t)n >= size) {
        return -1;
    }

    return n;
}
```

接收数据时用 jsmn 查找字段。固定格式的 JSON，直接 `snprintf()` 生成通常比引入完整 JSON 生成器更简单；嵌入式开发讨论中也常建议对固定 JSON 使用 `snprintf()`。[6]

### 情况三：已有大量 cJSON 代码，兼容性优先

可以使用：

> **cJSON + 自定义静态内存池**

不要直接依赖默认的 `malloc/free`。通过 `cJSON_InitHooks()` 将内存操作重定向到固定内存池，并使用 `cJSON_PrintPreallocated()` 输出到预分配缓冲区。[2]

## 最终结论

如果要求是“一个 C 库同时完成序列化和反序列化”，我的排序是：

1. **Frozen：最推荐**
2. **cJSON：最成熟、最容易上手，但内存开销和堆风险较大**
3. **tiny-json + json-maker：静态内存优先时很合适**
4. **jsmn + 自定义生成器：资源最省，但开发工作最多**

对于 STM32F103ZET6，我会采用：

> **固定协议：Frozen；极简协议：jsmn + `snprintf()`；已有 cJSON 生态：cJSON + 内存池。**

如果 JSON 数据量较大、传输频繁或对实时性要求较高，建议直接采用二进制协议；JSON 更适合配置、调试、设备管理和低频通信，而不是高吞吐实时数据。

在 **i.MX6UL + Linux** 平台上，我建议优先选择：

> **cJSON**

相比 STM32 裸机环境，i.MX6UL 运行 Linux 后通常有更多 RAM、完整 libc、进程隔离和成熟的内存管理，因此 cJSON 的动态内存开销通常是可以接受的。cJSON 是 ANSI C 编写的轻量级 JSON 库，支持解析、构造、序列化，并且集成方式简单，通常只需要加入 `cJSON.c` 和 `cJSON.h`。[1]

## 推荐顺序

| 库 | 推荐场景 | 优点 | 主要缺点 |
|---|---|---|---|
| **cJSON** | 一般设备应用、协议、配置文件 | 简单、资料多、集成方便 | 使用动态内存，解析会构造 JSON 树 |
| **yyjson** | 高频通信、大 JSON、性能敏感 | 解析和生成性能较好，功能完整 | API 比 cJSON 复杂一些 |
| **Jansson** | 配置系统、复杂 JSON、稳定性优先 | API 完整、文档好、Unicode 支持较完整 | 体积和内存开销通常比 cJSON 大 |
| **jsmn** | 只做轻量解析 | 极小、无动态内存、支持增量解析 | 只分词，不负责完整对象管理和序列化 |

## 为什么首选 cJSON

cJSON 的使用模型很直接：

```c
cJSON *root = cJSON_Parse(json_text);

if (root == NULL) {
    return -1;
}

cJSON *id = cJSON_GetObjectItemCaseSensitive(root, "id");
if (cJSON_IsNumber(id)) {
    printf("id = %d\n", id->valueint);
}

cJSON_Delete(root);
```

构造和序列化：

```c
cJSON *root = cJSON_CreateObject();

cJSON_AddNumberToObject(root, "id", 123);
cJSON_AddStringToObject(root, "name", "imx6ul");
cJSON_AddBoolToObject(root, "enabled", 1);

char *text = cJSON_PrintUnformatted(root);
if (text != NULL) {
    printf("%s\n", text);
    free(text);
}

cJSON_Delete(root);
```

cJSON 解析时会分配并构造一棵 `cJSON` 节点树，默认使用 `malloc/free`；解析完成后需要通过 `cJSON_Delete()` 释放整个树。[1]

在 Linux 用户态程序中，这种方式通常足够实用，特别适合：

- 设备配置文件；
- MQTT、HTTP、WebSocket 消息；
- 设备状态上报；
- 与云端或上位机通信；
- JSON 数据量在几 KB 到几十 KB；
- 不要求极限吞吐量。

## 什么时候选择 yyjson

如果你的应用有以下特点，可以优先考虑 **yyjson**：

- JSON 解析频率很高；
- 单条消息较大；
- CPU 占用比较敏感；
- 需要批量处理 JSON；
- 需要比 cJSON 更好的解析和序列化性能。

例如网关、协议转换、日志处理、视频或工业数据采集程序，yyjson 通常比 cJSON 更合适。它的代价是 API 和内存模型相对复杂，项目人员需要理解读模式、写模式以及内存池等概念。

可以简单理解为：

> **cJSON 偏向“易用和快速开发”，yyjson 偏向“性能和吞吐量”。**

## 什么时候选择 Jansson

如果主要用途是 Linux 配置系统、复杂配置文件或对 JSON 规范支持要求较高，可以考虑 **Jansson**。它专门提供 JSON 编码、解码和数据操作功能，API 稳定，文档和测试较完整，并且不依赖其他第三方库。[2]

但在 i.MX6UL 这种嵌入式 Linux 设备上，Jansson 通常不是首选，除非：

- 项目已经使用 Jansson；
- 需要它的错误处理或数据操作 API；
- JSON 层次较复杂；
- 更重视完整性而不是库体积。

## 不建议继续使用 Frozen

前一个 STM32 场景中推荐 Frozen，是因为它更适合资源受限、避免构造完整 JSON 树的情况。

但在 i.MX6UL Linux 上，通常没有必要为了节省几 KB 内存而牺牲 cJSON 的易用性和资料数量。除非你明确要求：

- 无堆内存；
- 固定缓冲区；
- 高度可预测的内存使用；
- 裸机式通信处理；

否则 cJSON 或 yyjson 更合适。

## 我的最终建议

如果没有特殊性能要求：

> **选择 cJSON。**

如果性能要求较高：

> **选择 yyjson。**

如果只需要极简解析，并且序列化格式固定：

> **选择 jsmn + 自己的序列化函数。**

推荐的工程选择可以是：

```text
普通应用、配置、MQTT、HTTP：cJSON
高频解析、大数据量、网关：yyjson
复杂配置和完整 JSON 操作：Jansson
串口协议、小数据、固定字段：jsmn
```

对于大多数 i.MX6UL Linux 项目，我会采用：

> **cJSON + 统一封装层 + 输入长度限制 + 严格类型检查**

不要让业务代码到处直接调用 `cJSON_GetObjectItem()`，可以封装成：

```c
int json_get_int(const cJSON *root,
                 const char *key,
                 int *value);

int json_get_string(const cJSON *root,
                    const char *key,
                    char *buf,
                    size_t buf_size);
```

这样以后即使从 cJSON 更换到 yyjson，也只需要修改 JSON 适配层。

针对 **i.MX6UL + Linux，每秒处理 500～1000 条 JSON 报文**，我建议把首选改为：

> **yyjson**

尤其是报文需要同时进行解析和生成时，yyjson 比 cJSON 更适合作为高频数据通道的 JSON 库。yyjson 的设计目标就是高性能 JSON 解析和生成，同时提供只读解析、可修改文档、写出 JSON、自定义内存分配器等能力。其项目定位为高性能 C JSON 库。[1]

## 为什么不再优先推荐 cJSON

500～1000 条/秒本身不一定很高，但要看每条报文大小和字段数量：

- 500 条/秒、每条 200 字节：压力通常不大；
- 1000 条/秒、每条 5～10 KB：压力会明显增加；
- 如果每条报文都要解析、修改、重新序列化，内存分配和 JSON 树构建会成为重要开销；
- 如果同时还有网络、数据库、日志、业务计算，JSON 处理的峰值延迟也需要关注。

cJSON 的 API 简单，但解析时会构造完整的动态 JSON 树，并大量使用节点分配；使用完后还需要递归释放整棵树。[1] 对低频配置和普通协议非常方便，但在高频数据通道中容易产生：

- `malloc/free` 调用较多；
- 堆碎片；
- 临时内存峰值较高；
- p99 延迟波动；
- JSON 树节点带来的额外内存占用。

因此，cJSON 不是不能达到 1000 条/秒，而是它通常不是这个场景下的最佳默认选择。

## 推荐方案

### 方案一：普通高频报文

使用：

```text
yyjson
    ↓
预分配接收缓冲区
    ↓
解析为只读文档
    ↓
提取业务字段
    ↓
业务处理
    ↓
yyjson 写入预分配输出缓冲区
```

如果只是读取字段，不修改 JSON，优先使用只读解析模式。不要为了读取几个字段而频繁创建和修改完整 JSON 对象。

伪代码结构如下：

```c
yyjson_read_err err;
yyjson_doc *doc = yyjson_read_opts(
    rx_buf,
    rx_len,
    0,
    NULL,
    NULL,
    &err
);

if (doc == NULL) {
    /* 处理格式错误 */
    return -1;
}

yyjson_val *root = yyjson_doc_get_root(doc);
yyjson_val *id = yyjson_obj_get(root, "id");
yyjson_val *type = yyjson_obj_get(root, "type");

if (yyjson_is_uint(id)) {
    uint64_t value = yyjson_get_uint(id);
}

yyjson_doc_free(doc);
```

实际工程中需要根据所使用的 yyjson 版本确认 API 和编译选项，但整体处理模式就是这样。

如果每条报文的格式固定，例如：

```json

```

而且只需要读取 `id`、`temperature`、`state` 等少量字段，可以考虑：


这种方式的内存开销更低，也可能有更稳定的延迟，但开发工作明显更多：

- 自己遍历 token；
- 自己处理字符串和数字转换；
- 自己校验字段类型；
- 自己生成输出 JSON；
- 自己处理数组和嵌套对象。

```text
业务线程/发送线程
```

不要在 socket 接收线程里执行过重的业务逻辑，也不要让无限制的生产速度把内存队列撑爆。

### 2. 尽量避免“解析—修改—重新打印”整个 JSON

如果只需要提取几个字段，不要这样做：

```text
JSON → 完整对象树 → 修改一个字段 → 整个 JSON 重新序列化
```

更高效的方式是：

```text
JSON → 提取字段 → 生成新的固定格式 JSON
```

对于输出结构固定的报文，甚至可以使用 `snprintf()` 或自定义 writer，而不是构造完整 JSON 树。

### 3. 不要开启格式化输出

生产环境使用紧凑输出：

```json
{"id":123,"state":1}
```

而不是：

```json
{
    "id": 123,
    "state": 1
}
```

格式化输出会增加 CPU 消耗和输出字节数。

### 4. 不要用日志拖慢测试结果

测试 JSON 性能时不要在每条报文中执行：

```c

```

串口输出、磁盘日志和 syslog 可能比 JSON 解析本身慢很多，容易导致错误判断。

### 5. 重点测 p95 和 p99

不要只测平均吞吐量，建议至少统计：

- 单条解析耗时；
- 单条序列化耗时；
- p50；
- p95；
- p99；
- 峰值内存；
- 每秒 `malloc/free` 次数；
- 丢包数量；
- 队列最大深度。

```text
持续 60 秒

```

## 2. 解析 JSON

`main.c`：

```c
#include <stdio.h>
#include <stdint.h>
#include <stddef.h>
#include <string.h>

#include "yyjson.h"

int main(void)
{
    const char *json =
        "{"
        "\"id\":1001,"
        "\"name\":\"terminal-01\","
        "\"enabled\":true,"
        "\"temperature\":25.6,"
        "\"records\":["
            "{\"timestamp\":1710000000,\"value\":12.5},"
            "{\"timestamp\":1710000060,\"value\":13.2}"
        "]"
        "}";

    /* 解析 JSON */
    yyjson_doc *doc = yyjson_read(json, strlen(json), 0);

    if (doc == NULL) {
        fprintf(stderr, "JSON parse failed\n");
        return -1;
    }

    /* 获取根节点 */
    yyjson_val *root = yyjson_doc_get_root(doc);

    if (!yyjson_is_obj(root)) {
        fprintf(stderr, "root is not an object\n");
        yyjson_doc_free(doc);
        return -1;
    }

    /* 读取整数 */
    yyjson_val *id_val = yyjson_obj_get(root, "id");
    if (yyjson_is_int(id_val)) {
        int64_t id = yyjson_get_int(id_val);
        printf("id = %lld\n", (long long)id);
    }

    /* 读取字符串 */
    yyjson_val *name_val = yyjson_obj_get(root, "name");
    if (yyjson_is_str(name_val)) {
        const char *name = yyjson_get_str(name_val);
        printf("name = %s\n", name);
    }

    /* 读取布尔值 */
    yyjson_val *enabled_val = yyjson_obj_get(root, "enabled");
    if (yyjson_is_bool(enabled_val)) {
        bool enabled = yyjson_get_bool(enabled_val);
        printf("enabled = %s\n", enabled ? "true" : "false");
    }

    /* 读取浮点数 */
    yyjson_val *temperature_val = yyjson_obj_get(root, "temperature");
    if (yyjson_is_num(temperature_val)) {
        double temperature = yyjson_get_num(temperature_val);
        printf("temperature = %.2f\n", temperature);
    }

    /* 遍历数组 */
    yyjson_val *records_val = yyjson_obj_get(root, "records");

    if (yyjson_is_arr(records_val)) {
        yyjson_arr_iter iter;
        yyjson_arr_iter_init(records_val, &iter);

        yyjson_val *record;

        while ((record = yyjson_arr_iter_next(&iter)) != NULL) {
            yyjson_val *timestamp_val =
                yyjson_obj_get(record, "timestamp");

            yyjson_val *value_val =
                yyjson_obj_get(record, "value");

            if (yyjson_is_uint(timestamp_val) &&
                yyjson_is_num(value_val)) {

                uint64_t timestamp =
                    yyjson_get_uint(timestamp_val);

                double value =
                    yyjson_get_num(value_val);

                printf("timestamp = %llu, value = %.2f\n",
                       (unsigned long long)timestamp,
                       value);
            }
        }
    }

    /* 释放文档 */
    yyjson_doc_free(doc);

    return 0;
}
```

## 3. 构造并序列化 JSON

yyjson 的可修改文档使用 `yyjson_mut_doc` 和 `yyjson_mut_val`。

```c
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>

#include "yyjson.h"

int main(void)
{
    yyjson_mut_doc *doc = yyjson_mut_doc_new(NULL);

    if (doc == NULL) {
        return -1;
    }

    /* 创建根对象 */
    yyjson_mut_val *root = yyjson_mut_obj(doc);

    if (root == NULL) {
        yyjson_mut_doc_free(doc);
        return -1;
    }

    yyjson_mut_doc_set_root(doc, root);

    /* 添加基本字段 */
    yyjson_mut_obj_add_uint(doc, root, "id", 1001);
    yyjson_mut_obj_add_str(doc, root, "name", "terminal-01");
    yyjson_mut_obj_add_bool(doc, root, "enabled", true);
    yyjson_mut_obj_add_real(doc, root, "temperature", 25.6);

    /* 创建数组 */
    yyjson_mut_val *records = yyjson_mut_arr(doc);

    if (records == NULL) {
        yyjson_mut_doc_free(doc);
        return -1;
    }

    yyjson_mut_obj_add_val(doc, root, "records", records);

    /* 添加第一个数组元素 */
    yyjson_mut_val *record1 = yyjson_mut_obj(doc);

    yyjson_mut_obj_add_uint(doc, record1,
                            "timestamp", 1710000000);

    yyjson_mut_obj_add_real(doc, record1,
                            "value", 12.5);

    yyjson_mut_arr_add_val(records, record1);

    /* 添加第二个数组元素 */
    yyjson_mut_val *record2 = yyjson_mut_obj(doc);

    yyjson_mut_obj_add_uint(doc, record2,
                            "timestamp", 1710000060);

    yyjson_mut_obj_add_real(doc, record2,
                            "value", 13.2);

    yyjson_mut_arr_add_val(records, record2);

    /* 序列化为紧凑 JSON */
    size_t json_len = 0;

    char *json = yyjson_mut_write(doc, 0, &json_len);

    if (json == NULL) {
        fprintf(stderr, "JSON write failed\n");
        yyjson_mut_doc_free(doc);
        return -1;
    }

    printf("json length = %zu\n", json_len);
    printf("%s\n", json);

    /*
     * yyjson_mut_write() 返回的字符串由 yyjson 分配，
     * 需要使用 free() 释放。
     */
    free(json);

    yyjson_mut_doc_free(doc);

    return 0;
}
```

## 4. 解析错误处理

生产代码中建议使用 `yyjson_read_opts()` 获取错误位置和错误原因：

```c
#include <stdio.h>
#include <string.h>

#include "yyjson.h"

int parse_json(const char *data, size_t len)
{
    yyjson_read_err err;

    yyjson_doc *doc = yyjson_read_opts(
        (char *)data,
        len,
        0,
        NULL,
        &err
    );

    if (doc == NULL) {
        fprintf(stderr,
                "JSON parse error: %s, position=%zu\n",
                err.msg,
                err.pos);

        return -1;
    }

    yyjson_val *root = yyjson_doc_get_root(doc);

    if (!yyjson_is_obj(root)) {
        yyjson_doc_free(doc);
        return -1;
    }

    yyjson_doc_free(doc);
    return 0;
}
```

对于网络报文，建议至少检查：

```c
if (data == NULL || len == 0 || len > MAX_JSON_SIZE) {
    return -1;
}
```

## 6. 大报文场景的推荐写法

对于你前面提到的 20～40 KB 报文，通常采用：

```c
#define MAX_JSON_SIZE (64 * 1024)

static char rx_buf[MAX_JSON_SIZE];
```

收到完整报文后：

```c
yyjson_doc *doc = yyjson_read(rx_buf, rx_len, 0);

if (doc == NULL) {
    /* 记录错误，丢弃当前报文 */
    return -1;
}

/* 读取字段 */

yyjson_doc_free(doc);
```

如果输入缓冲区可以被 yyjson 修改，可以考虑原地解析：

```c
yyjson_doc *doc = yyjson_read_opts(
    rx_buf,
    rx_len,
    YYJSON_READ_INSITU,
    NULL,
    &err
);
```

但要注意：

- `rx_buf` 必须是可写内存；
- 解析过程中不要修改或复用 `rx_buf`；
- `doc` 释放前不要释放 `rx_buf`；
- 解析完成后，字符串指针只在对应缓冲区和文档有效期内有效；
- 不能把 `yyjson_get_str()` 返回的指针长期保存到下一次接收缓冲区复用之后。

## 7. 高吞吐场景的关键注意事项

### 避免重复查找字段

这种方式会反复按键查找：

```c
yyjson_obj_get(root, "device");
yyjson_obj_get(root, "device");
yyjson_obj_get(root, "device");
```

可以先保存中间节点：

```c
yyjson_val *device = yyjson_obj_get(root, "device");

if (yyjson_is_obj(device)) {
    yyjson_val *id = yyjson_obj_get(device, "id");
    yyjson_val *state = yyjson_obj_get(device, "state");
}
```

### 不要用修改文档读取数据

读取报文时使用：

```c
yyjson_read()
```

或：

```c
yyjson_read_opts()
```

只有构造输出 JSON 时才使用：

```c
yyjson_mut_doc
```

### 对固定格式的输出，考虑直接写缓冲区

如果输出结构固定，没必要每次构造一个完整可修改 JSON 树，可以直接使用：

```c
int len = snprintf(
    tx_buf,
    tx_buf_size,
    "{\"id\":%u,\"state\":%d}",
    id,
    state
);
```

这样通常会比“创建可修改 JSON 树再序列化”更省内存。

### 浮点数尽量减少

对于设备报文中的测量值，可以使用定点整数：

```json
{
    "temperature": 256
}
```

表示：

```text
25.6 ℃
```

C 代码中：

```c
int temperature_x10 = 256;
double temperature = temperature_x10 / 10.0;
```

这有助于减少浮点转换开销，也能避免不同平台上的浮点格式差异。

## 最适合你的基本模式

对于你的应用，我建议采用：

```text
网络线程：
    接收完整报文到固定缓冲区

JSON线程：
    yyjson_read()
    提取必要字段
    复制到业务结构体
    yyjson_doc_free()

业务线程：
    使用业务结构体处理数据
```

如果报文中只有少量字段需要使用，则进一步考虑：

```text
YAJL 流式解析
```

如果需要访问很多字段、数组和嵌套对象，则使用：

```text
yyjson 只读解析
```

不要直接使用 cJSON 对 20～40 KB 报文构造完整动态树，除非实际测试证明 CPU、内存和延迟都满足要求。
