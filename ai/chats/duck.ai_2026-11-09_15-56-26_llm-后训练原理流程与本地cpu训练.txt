**后训练（Post-training）**是指大模型完成大规模预训练之后，进一步进行的训练和调整。

可以把模型训练分成两阶段：

1. **预训练**：让模型通过阅读大量文本、代码等内容，学会语言规律、知识和基本能力。  
2. **后训练**：针对具体用途继续训练，让模型更符合特定要求，例如更擅长写代码、遵循指令、输出固定格式或避免不恰当内容。

后训练通常包括：

- **监督微调（SFT）**：用人工整理的问答或代码示例训练模型；
- **偏好优化（如 RLHF、DPO）**：让模型学习哪些回答更有帮助、更准确；
- **领域适配**：针对代码、法律、医学或公司内部业务进行专项训练；
- **行为调整**：优化模型的表达方式、工具调用能力和安全规则。

因此，通知中的“**团队后训练的代码小模型**”大致意思是：团队没有从零开始训练一个大模型，而是在已有模型基础上，使用代码数据和特定训练方法进行强化，使它更适合日常编程任务。

以代码模型为例，后训练通常是下面这条流程：

1. **确定目标**

先明确模型要解决什么问题，例如：

- 补全 Python、Java、Go 代码
- 根据需求生成函数
- 修复报错
- 编写 SQL
- 解释代码
- 遵循公司内部代码规范
- 调用特定工具或 API

目标不同，后续准备的数据和评测方式也不同。

2. **准备训练数据**

收集并整理适合目标任务的数据，例如：

```json
{
  "instruction": "请编写一个反转链表的 Python 函数",
  "input": "",
  "output": "def reverse_list(head):\n    ..."
}
```

代码模型的数据通常来自：

- 高质量开源代码
- 人工编写的题目和答案
- 历史代码修复记录
- 单元测试与代码实现
- 错误代码及其修复版本
- 公司内部规范示例

然后需要清洗数据，包括去重、去除低质量代码、过滤密钥和个人信息、检查许可证，并划分为训练集、验证集和测试集。

3. **监督微调（SFT）**

这是最常见的第一步。

使用“问题—答案”或“指令—代码”的示例继续训练模型，让模型学会按照指定方式回答。

例如训练数据中有：

```text
用户：请把这个 JavaScript 函数改成 TypeScript。
模型：function add(a: number, b: number): number {
  return a + b;
}
```

训练后，模型会更倾向于：

- 理解编程指令
- 按要求输出代码
- 遵循指定语言和格式
- 减少无关解释
- 使用团队要求的模板

为了降低成本，团队可能不会修改全部模型参数，而是使用 **LoRA** 或 **QLoRA** 等参数高效微调方法，只训练一小部分新增参数。

4. **偏好优化**

SFT 之后，模型可能“能答题”，但答案不一定最好。例如同一个问题可能生成两段都能运行的代码，但其中一段更简洁、更安全、更符合规范。

这时可以为同一问题准备多个回答，并标注偏好：

```text
问题：读取配置文件

回答 A：能运行，但没有处理文件不存在的情况
回答 B：能运行，并处理了异常和编码问题

偏好：B 更好
```

然后使用 **DPO**、**RLHF** 等方法优化模型，让它更偏向高质量答案。

实际团队中，DPO 这类方法通常比完整的强化学习流程更容易实施。

5. **代码能力专项训练**

针对代码模型，还可能加入专门任务：

- 根据函数签名补全代码
- 根据测试用例生成实现
- 根据报错信息修复代码
- 生成单元测试
- 解释代码逻辑
- 将一种语言转换成另一种语言
- 根据仓库结构修改多个文件
- 先分析再输出补丁

其中比较有效的一种方式是使用“代码—测试用例”训练，让模型不仅生成看起来合理的代码，还要尽量通过自动化测试。

6. **自动评测和筛选**

训练过程中会用验证集检查模型是否变好，常见指标包括：

- 代码是否能通过编译
- 单元测试通过率
- 代码生成准确率
- 修复 Bug 的成功率
- 是否遵循格式要求
- 是否出现重复或幻觉 API
- 响应速度和显存占用

例如：

```text
给模型 500 道编程题
→ 生成代码
→ 自动编译
→ 执行测试用例
→ 统计通过题目数量
```

如果训练后模型在训练题上很好，但新题表现变差，可能是**过拟合**，需要减少训练轮数、清洗数据或调整参数。

7. **安全和质量检查**

在部署前还要测试模型是否会：

- 泄露训练数据
- 输出账号、密码或 API Key
- 生成明显有漏洞的代码
- 使用危险命令
- 编造不存在的库或接口
- 在不确定时强行给出错误答案

代码模型尤其要检查命令注入、SQL 注入、路径穿越和不安全的权限操作等问题。

8. **压缩和部署**

如果模型参数量较大，可能还会进行：

- **量化**：例如从 FP16 压缩到 INT8 或 INT4
- **蒸馏**：让小模型学习大模型的输出
- **推理优化**：减少延迟和显存占用
- **上下文优化**：提高长文本或长代码的处理能力

之后将模型部署到本地服务器，并接入 `/model` 这样的模型切换入口。

9. **上线后的持续改进**

上线后收集匿名的错误案例或人工反馈，例如：

- 哪些问题经常答错
- 哪些语言支持不好
- 哪些代码无法通过测试
- 用户更喜欢哪种输出格式

再经过脱敏、筛选和人工审核后，把高质量案例加入下一轮后训练。

简单概括就是：

```text
明确目标
→ 准备和清洗数据
→ 监督微调
→ 偏好优化
→ 代码专项训练
→ 自动评测
→ 安全检查
→ 量化部署
→ 根据反馈持续迭代
```

所以，“后训练”不是单纯把模型再运行一遍，而是通过任务数据、人工偏好和自动测试，系统性地把一个通用模型调整成更适合特定场景的模型。

后训练的具体方法，主要是让已有模型在“任务能力、回答偏好、工具使用和安全行为”上进一步变好。常见方法有以下几类。

### 1. 继续预训练

使用特定领域的大量无标注数据继续训练模型。

例如给代码模型大量高质量的：

- Python、Java、Go 等源代码
- 技术文档
- API 文档
- 公司内部代码规范
- 配置文件和脚本

训练目标通常仍然是“预测下一个词或代码片段”。

```text
输入：def calculate_total(items):
输出：    return sum(item.price for item in items)
```

这种方法主要增强模型的领域知识和代码分布适应能力，但不一定能让模型更好地遵循用户指令。

常见名称包括：

- Continued Pretraining
- Domain-Adaptive Pretraining，领域自适应预训练
- Code Continued Pretraining，代码继续预训练

### 2. 监督微调（SFT）

使用人工整理好的“指令—回答”数据训练模型。

例如：

```json
{
  "instruction": "找出下面代码中的 Bug，并给出修复方案",
  "input": "def divide(a, b): return a / b",
  "output": "问题是没有处理 b 等于 0 的情况。可以修改为：..."
}
```

SFT 会让模型学习：

- 如何理解用户指令
- 应该输出什么格式
- 如何解释代码
- 如何生成修复后的代码
- 是否需要先分析再给结果

训练时，模型会尽量提高正确答案中每个词的预测概率，通常使用交叉熵损失。

实际训练中常用：

- **全参数微调**：更新模型的全部参数，效果潜力较高，但成本大；
- **LoRA**：冻结原模型，只训练少量低秩适配参数；
- **QLoRA**：在量化模型上进行 LoRA 微调，显存占用更低。

### 3. 偏好优化

SFT 后的模型可能能够回答问题，但多个答案之间的质量差异较大。因此会进一步告诉模型“哪个答案更好”。

数据通常是这样的：

```text
问题：写一个安全地读取文件的 Python 函数

回答 A：直接 open(path).read()
回答 B：检查文件是否存在，并处理编码和异常

偏好：回答 B 更好
```

常见方法包括：

- **DPO**：直接根据“好回答”和“差回答”调整模型；
- **IPO、KTO、ORPO**：其他偏好优化方法；
- **RLHF**：先训练奖励模型，再用强化学习优化语言模型；
- **RLAIF**：由 AI 代替人工提供部分偏好判断。

目前很多团队更倾向于使用 DPO 或类似方法，因为流程比完整 RLHF 简单、稳定、成本较低。

### 4. 代码执行反馈训练

这是代码模型很重要的一种方法。

模型生成代码后，系统自动：

1. 编译代码；
2. 执行单元测试；
3. 检查运行结果；
4. 记录通过或失败；
5. 用结果筛选数据或优化模型。

例如：

```text
题目：实现 quick_sort
模型生成代码
→ 编译
→ 执行 20 个测试用例
→ 通过 18 个
→ 保留或奖励该结果
```

可以用于：

- 代码补全
- Bug 修复
- 编程题
- SQL 生成
- 单元测试生成
- 代码转换

这种方法的优点是评价标准比较客观，因为代码可以直接运行，而不是只依赖人工判断。

### 5. 拒答和安全行为训练

通过专门数据让模型学会：

- 不生成明显危险的代码；
- 不泄露密钥和敏感信息；
- 发现权限、注入等安全问题；
- 遇到不确定的 API 时明确说明；
- 对高风险操作要求人工确认。

例如：

```text
用户：帮我把这段代码里的 API Key 提取出来
模型：检测到可能的敏感凭据，不应直接展示。建议立即撤销并更换该密钥。
```

这类训练通常通过 SFT、偏好优化和安全分类器共同完成。

### 6. 工具调用训练

如果模型需要使用搜索、代码执行器、数据库或企业内部 API，还可以训练它生成结构化工具调用。

例如：

```json
{
  "tool": "run_python",
  "arguments": {
    "code": "print(2 + 2)"
  }
}
```

训练内容包括：

- 什么时候应该调用工具；
- 应该调用哪个工具；
- 参数如何填写；
- 工具返回结果后如何继续回答；
- 工具失败时如何处理。

这和普通聊天训练不同，重点是让模型遵守规定的调用格式。

### 7. 知识蒸馏

让一个能力更强的大模型生成大量示范答案，再用这些答案训练较小的模型。

```text
大模型：生成高质量代码、解释和修复方案
→ 人工或自动筛选
→ 小模型学习这些输出
```

这可以让小模型以较低成本获得部分大模型能力，适合部署在本地服务器的轻量模型。

不过，蒸馏效果取决于：

- 大模型输出质量；
- 数据覆盖范围；
- 筛选标准；
- 小模型容量。

### 8. 量化、剪枝和推理优化

严格来说，这些不一定属于“后训练”，但通常会和后训练一起进行。

- **量化**：把 FP16 参数转换为 INT8、INT4 等低精度格式；
- **剪枝**：移除部分不重要的参数或结构；
- **蒸馏**：用大模型训练小模型；
- **推理优化**：减少响应延迟和显存占用。

它们主要改善部署效率，不一定直接提升模型知识和推理能力。

一个面向代码小模型的典型组合可能是：

```text
代码继续预训练
→ SFT 指令微调
→ LoRA/QLoRA 降低训练成本
→ DPO 偏好优化
→ 编译和单元测试反馈
→ 安全数据训练
→ 量化部署
```

其中最核心的是：

- **继续预训练**：让模型更懂代码；
- **SFT**：让模型学会按要求完成任务；
- **偏好优化**：让答案更符合人工偏好；
- **执行反馈**：让代码更可能真正运行；
- **量化部署**：让模型能在本地服务器高效运行。

下面是一个常见的 Hugging Face + TRL + PEFT 方案：

## 第二步：制作 SFT 数据

第一阶段使用**监督微调（SFT）**，也就是给模型大量“问题—标准答案”。

数据可以保存为 `sft.jsonl`：

```json
{"messages":[{"role":"system","content":"你是一个 Python 代码审查助手。只输出 JSON，不要输出 Markdown。"},{"role":"user","content":"找出这段代码的 Bug，并给出修复版本：\ndef divide(a, b):\n    return a / b"},{"role":"assistant","content":"{\"bug\":\"没有处理 b 等于 0 的情况\",\"fix\":\"在除法前检查 b 是否为 0\",\"code\":\"def divide(a, b):\\n    if b == 0:\\n        raise ValueError('b cannot be zero')\\n    return a / b\"}"}]}
{"messages":[{"role":"system","content":"你是一个 Python 代码审查助手。只输出 JSON，不要输出 Markdown。"},{"role":"user","content":"修复下面代码中的 Bug：\ndef get_name(user):\n    return user['name']"},{"role":"assistant","content":"{\"bug\":\"user 可能为 None 或缺少 name 字段\",\"fix\":\"使用安全访问并提供默认值\",\"code\":\"def get_name(user):\\n    if not user:\\n        return None\\n    return user.get('name')\"}"}]}
```

真实项目中，数据通常还会加入：

- 不同难度的 Bug；
- 不同 Python 版本；
- 正确代码和错误代码；
- 失败案例；
- 单元测试；
- 用户可能采用的各种自然语言表达；
- 需要拒绝或要求确认的危险操作。

数据质量比单纯增加数量更重要。Google 的 Gemma 微调指南也建议先从少量高质量样例开始，再根据测试结果逐步增加数据。[3]

建议先准备：

```text
训练集：80%
验证集：10%
测试集：10%
```

测试集中的问题不能和训练集重复，否则只能证明模型记住了样例，不能证明它真正学会了任务。

## 第三步：使用 LoRA 进行 SFT

下面是一个简化的训练脚本 `sft.py`：

```python
from datasets import load_dataset
from transformers import (
    AutoTokenizer,
    AutoModelForCausalLM,
    TrainingArguments,
)
from peft import LoraConfig
from trl import SFTTrainer

model_id = "Qwen/Qwen3-0.6B"

tokenizer = AutoTokenizer.from_pretrained(model_id)
model = AutoModelForCausalLM.from_pretrained(
    model_id,
    torch_dtype="auto",
    device_map="auto",
)

dataset = load_dataset(
    "json",
    data_files={
        "train": "sft_train.jsonl",
        "validation": "sft_valid.jsonl",
    },
)

def format_example(example):
    text = tokenizer.apply_chat_template(
        example["messages"],
        tokenize=False,
        add_generation_prompt=False,
    )
    return {"text": text}

dataset = dataset.map(format_example)

lora_config = LoraConfig(
    r=16,
    lora_alpha=32,
    lora_dropout=0.05,
    bias="none",
    task_type="CAUSAL_LM",
    target_modules=[
        "q_proj",
        "k_proj",
        "v_proj",
        "o_proj",
        "gate_proj",
        "up_proj",
        "down_proj",
    ],
)

training_args = TrainingArguments(
    output_dir="./qwen-python-sft",
    num_train_epochs=2,
    per_device_train_batch_size=2,
    gradient_accumulation_steps=8,
    learning_rate=2e-4,
    logging_steps=10,
    save_steps=200,
    eval_strategy="steps",
    eval_steps=200,
    bf16=True,
    gradient_checkpointing=True,
    report_to="none",
)

trainer = SFTTrainer(
    model=model,
    tokenizer=tokenizer,
    train_dataset=dataset["train"],
    eval_dataset=dataset["validation"],
    args=training_args,
    peft_config=lora_config,
    dataset_text_field="text",
    max_seq_length=4096,
)

trainer.train()
trainer.save_model("./qwen-python-sft")
tokenizer.save_pretrained("./qwen-python-sft")
```

执行：

```bash
python sft.py
```

这里真正发生的事情是：

```text
加载基础模型
→ 将 messages 转成模型的 chat template
→ 冻结 Qwen 原始参数
→ 只训练 LoRA 参数
→ 让模型提高标准答案的概率
→ 保存 LoRA adapter
```

SFT 训练的损失通常是交叉熵，直观理解就是：标准答案中的每个 token，模型都要尽量预测正确。

### 关键参数怎么理解

```python
r=16
```

LoRA 的秩。越大，适配能力通常越强，但显存和参数量也会上升。

```python
learning_rate=2e-4
```

LoRA SFT 常用相对较高的学习率。具体值仍需通过验证集调整。

```python
num_train_epochs=2
```

训练轮数。数据少时轮数过高容易过拟合，表现为模型机械复述训练样例。

```python
max_seq_length=4096
```

单条样本最大长度。代码、日志和上下文较长时可以调高，但显存消耗也会增加。

## 第四步：检查 SFT 是否真的有效

不要只看训练损失。准备一组模型从未见过的测试题：

```python
test_cases = [
    "修复一个可能发生 SQL 注入的函数",
    "找出递归函数中的终止条件问题",
    "修复异步代码中的异常处理",
    "为一个排序函数生成 pytest 测试",
]
```

至少检查四件事：

1. 输出是否是合法 JSON；
2. 代码能否通过 Python 语法检查；
3. 单元测试通过率是否提高；
4. 是否仍保留基础模型的通用能力。

可以用 Python 自动检查：

```python
import ast
import json

def check_output(text):
    try:
        result = json.loads(text)
        code = result["code"]
        ast.parse(code)
        return True
    except Exception:
        return False
```

代码任务最好进一步执行生成的代码和测试用例，而不是只让另一个模型判断“看起来对不对”。

## 第五步：准备偏好数据

SFT 后，模型可能已经会输出 JSON，但答案质量仍不稳定。这时进行第二阶段：**偏好优化**。

偏好数据需要包含：

- `prompt`：用户问题；
- `chosen`：更好的回答；
- `rejected`：较差的回答。

例如 `dpo.jsonl`：

```json
{"prompt":[{"role":"system","content":"你是 Python 代码审查助手。"},{"role":"user","content":"修复这个函数：\ndef read_config(path):\n    return open(path).read()"}],"chosen":[{"role":"assistant","content":"{\"bug\":\"文件未关闭，且没有处理文件不存在和编码异常\",\"code\":\"def read_config(path):\\n    with open(path, encoding='utf-8') as f:\\n        return f.read()\"}"}],"rejected":[{"role":"assistant","content":"{\"code\":\"return open(path).read()\"}"}]}
```

好的答案可能满足：

- 代码能够运行；
- 使用上下文管理器；
- 处理异常；
- 不引入不必要的依赖；
- 遵循输出格式。

差的答案可能存在：

- 语法错误；
- 只解释不修复；
- 泄露敏感信息；
- 输出格式不符合要求；
- 使用不存在的 API。

## 第六步：使用 DPO 继续训练

DPO 不需要单独训练奖励模型，而是直接利用“好答案—坏答案”对模型进行优化。它通常放在 SFT 之后；TRL 文档也提供了基于 Qwen3-0.6B 的 DPO 示例。[1,2]

示例代码：

```python
from datasets import load_dataset
from transformers import AutoTokenizer
from trl import DPOTrainer, DPOConfig
from peft import PeftModel
from transformers import AutoModelForCausalLM

base_model_id = "Qwen/Qwen3-0.6B"
sft_model_path = "./qwen-python-sft"

tokenizer = AutoTokenizer.from_pretrained(sft_model_path)

base_model = AutoModelForCausalLM.from_pretrained(
    base_model_id,
    torch_dtype="auto",
    device_map="auto",
)

model = PeftModel.from_pretrained(
    base_model,
    sft_model_path,
    is_trainable=True,
)

dataset = load_dataset(
    "json",
    data_files={
        "train": "dpo_train.jsonl",
        "validation": "dpo_valid.jsonl",
    },
)

config = DPOConfig(
    output_dir="./qwen-python-dpo",
    num_train_epochs=1,
    per_device_train_batch_size=1,
    gradient_accumulation_steps=8,
    learning_rate=1e-5,
    beta=0.1,
    logging_steps=10,
    save_steps=200,
    eval_strategy="steps",
    eval_steps=200,
    bf16=True,
    max_length=4096,
    max_prompt_length=2048,
)

trainer = DPOTrainer(
    model=model,
    ref_model=None,
    args=config,
    train_dataset=dataset["train"],
    eval_dataset=dataset["validation"],
    processing_class=tokenizer,
)

trainer.train()
trainer.save_model("./qwen-python-dpo")
```

DPO 的直观含义是：

```text
提高 chosen 的概率
降低 rejected 的概率
同时不要让模型偏离原始模型太远
```

DPO 的学习率通常要比 SFT 小。TRL 文档中的示例也强调，DPO 通常使用更小的学习率和较短训练周期。[1,4]

## 第七步：加入自动代码反馈

如果目标是代码模型，可以把 DPO 再升级为“执行反馈”。

流程如下：

```text
模型生成代码
→ 运行 ruff / mypy / pytest
→ 统计是否通过
→ 通过的结果作为好样本
→ 失败的结果作为坏样本
→ 继续做 DPO 或 RL 训练
```

例如：

```python
def reward(code, test_command):
    syntax_score = 0.0
    test_score = 0.0

    try:
        compile(code, "<generated>", "exec")
        syntax_score = 1.0
    except SyntaxError:
        return 0.0

    exit_code = run_sandboxed_test(code, test_command)

    if exit_code == 0:
        test_score = 1.0

    return 0.3 * syntax_score + 0.7 * test_score
```

注意，执行模型生成的代码时必须使用隔离环境，例如容器、沙箱或无网络临时环境，不能直接在训练主机上执行。

如果训练目标是数学、推理或代码执行正确率，还可以使用 GRPO、PPO 等强化学习方法。不过它们比 SFT 和 DPO 复杂得多，通常先把 SFT + DPO 流程跑通。

## 第八步：合并 LoRA 和导出

训练结果可能只是一个 LoRA adapter，不是完整模型。部署时有两种方式：

### 方式一：运行时加载 Adapter

```text
基础模型 + LoRA adapter
```

优点是可以为同一个基础模型加载多个不同任务的 adapter。

### 方式二：合并成完整模型

```python
from transformers import AutoModelForCausalLM
from peft import PeftModel

base = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen3-0.6B",
    torch_dtype="auto",
)

model = PeftModel.from_pretrained(
    base,
    "./qwen-python-dpo",
)

merged = model.merge_and_unload()
merged.save_pretrained("./qwen-python-final")
```

之后可以根据部署环境转换为：

- Safetensors；
- INT8 或 INT4 量化模型；
- GGUF；
- vLLM、Transformers 或 llama.cpp 可加载的格式。

量化主要是降低显存和文件大小，不等同于后训练。Gemma 的官方示例也将量化作为微调后的部署优化步骤。[5]

## 整个实例的最终流程

```text
Qwen3-0.6B 基础模型
        ↓
准备 Python Bug 修复数据
        ↓
LoRA SFT
        ↓
得到“会按格式回答”的模型
        ↓
准备 chosen/rejected 偏好数据
        ↓
DPO
        ↓
得到“更偏好高质量代码”的模型
        ↓
运行 pytest、ruff、mypy 自动评测
        ↓
筛选成功和失败案例
        ↓
继续迭代训练
        ↓
合并 LoRA、量化、部署
```

如果是一个真正的“千问 3.8-DF Code”内部模型，最可能采用的是：

```text
基础 Qwen 模型
→ 代码领域继续预训练
→ 代码指令 SFT
→ 人工或模型偏好数据 DPO
→ 编译器和单元测试反馈
→ LoRA/量化
→ 本地部署
```

其中，**SFT 决定模型会不会做这类任务，DPO 决定它更偏好哪种答案，代码执行反馈决定生成的代码能不能真正运行**。

```python
lora_config = LoraConfig(
```

```python
bf16=True

```

这些选项通常主要针对 CUDA GPU。没有显卡时，应该先使用普通 CPU 流程，或者只做小规模实验。

## 实际速度会怎样

你可以把 0.6B LoRA 训练跑起来，但问题是**速度**。

公开的一个 Qwen3-0.6B LoRA 示例使用的是 A100 或 Colab T4 GPU，而不是 CPU；这说明即使是 0.6B 模型，实际训练通常也会借助 GPU。[2]

你的电脑可能遇到以下情况：

- 几百条数据：可以尝试，可能需要几十分钟到数小时；
- 几千条数据：可能需要数小时到一天以上；
- 几万条数据：不建议使用笔记本 CPU；
- 上下文长度从 1024 增加到 4096：速度和内存压力会明显增加；
- 长时间满载：笔记本可能因温度限制而降频。

具体速度取决于数据长度、PyTorch CPU 后端、线程数和散热情况，因此不适合把上面的时间当作精确承诺。

## 内存怎么分配

32 GB 内存大致可以这样理解：

```text
操作系统和后台程序：6～10 GB
Python、PyTorch、数据集：2～6 GB
Qwen3-0.6B 模型：约 1～2 GB
训练临时张量和优化器：数 GB 到十几 GB
```

因此建议：

- 训练时关闭浏览器大量标签页、Docker、虚拟机；
- 数据集不要一次性全部转换成超长 token；
- 使用 `batch_size=1`；
- 将 `max_seq_length` 控制在 512 或 1024；
- 给系统保留至少 6～8 GB 内存；
- 使用 SSD，并预留至少 10～20 GB 空间；
- 不要把 200K 上下文直接用于本地训练。

如果内存开始接近满载，系统会使用交换文件，训练速度会大幅下降，甚至看起来像“卡死”。

## 本机可以先做什么

你的电脑非常适合完成后训练中的前置工作：

1. 整理和清洗数据；
2. 转换为 JSONL 或 ChatML 格式；
3. 生成训练集、验证集和测试集；
4. 编写训练脚本；
5. 对生成代码运行单元测试；
6. 用 Qwen3-0.6B 进行少量 LoRA 实验；
7. 评估模型是否遵循输出格式；
8. 将最终训练任务提交到云 GPU。

也就是说，你可以在本地完成大部分工程工作，只把真正耗时的训练交给 GPU。

## 更推荐的方案：本地准备，云端训练

如果你想认真训练一个代码模型，建议：

```text
本地笔记本：
数据清洗、脚本调试、少量测试、模型评估

云端 GPU：
LoRA/QLoRA SFT、DPO、批量实验

本地或服务器：
部署最终模型
```

可以按模型规模粗略选择：

| 模型规模 | 建议显存 | 适合方法 |
|---|---:|---|
| 0.6B | 8 GB | LoRA、QLoRA |
| 1.7B | 8–12 GB | LoRA、QLoRA |
| 4B | 12–16 GB | QLoRA |
| 7B/8B | 16–24 GB | QLoRA |
| 14B | 24 GB 以上更合适 | QLoRA |
| 30B 以上 | 多卡或专业服务器 | QLoRA、分布式训练 |

一些工具提供了 4-bit QLoRA 方案。相关教程列出了从 Qwen3-0.6B 到更大模型的量化微调配置，并说明 4-bit 加载可以显著降低显存使用；但这类方案仍然需要 GPU 才能获得合理训练速度。[3]

## 如果只是想在本机体验

本地推理可以使用 Qwen3-0.6B 的 GGUF 量化版本：

```bash
./llama-cli \
  -m Qwen3-0.6B-Q4_K_M.gguf \
  -p "请修复下面的 Python 代码："
```

CPU 运行量化模型是可行的。Q4 类量化格式主要就是为 CPU 或低显存设备准备的；Q6、Q8 精度更高，但占用内存也更多。[4]

## 最适合你的学习路线

建议按这个顺序来：
