## 1. 结论先行

**可以把“云端强模型规划 + 本地小模型执行”跑起来，但不要指望本地小模型原样驱动 opencode 做完整开发。**

- 云端旗舰模型训练和运行成本极高，不会原封不动搬进笔记本；端侧走的是 **MoE 稀疏化、极致量化、存储层次扩展、专用 NPU** 的平行路线。
- 你的 i7-13700H CPU 算力足够跑小模型，真正限制是 **Visual Studio 和网页占用后只剩 10–12GB 内存**。
- 纯 CPU 本地模型优先选 **GGUF + Q4_K_M 量化**，用 **Ollama / LM Studio / llama.cpp** 运行。
- 代码 Agent 对上下文有硬门槛：**opencode 至少 64K tokens**；Pi agent 推荐 64K，压缩器可支持 32K 但会丢历史细节。我此前推荐的极小型模型不适合直接接入这些 Agent。
- 更现实的路线是：**DeepSeek 负责代码分析、架构设计、任务拆分；本地 1.5B–3B 模型负责补全、解释、单文件修改、摘要等低上下文任务**。
- 推荐从 **nvHive 的 Tier 0/1“云端规划器 + 本地执行器”模式** 或 **opencode-orchestrator** 开始；轻量方案可用 **Aider `--architect`** 或 **Pi Agent `prewalk`**。

## 2. 为什么云端旗舰模型不能直接塞进笔记本

讨论中明确了一个基本判断：训练一个云端旗舰模型需要几十亿到上百亿美元，运行需要数千万美元设备。这类模型不会原样进入笔记本。端侧模型是“新物种”，不是云端模型的简单缩小版。

端侧可行的技术路径包括：

- **MoE 架构**：总参数很大，但每次推理只激活一小部分专家。例如讨论中提到的 Edge0-145B，总参数 1450 亿，每步仅约 100 亿参数参与计算，MacBook Pro 上峰值内存约 29GB。
- **极致量化**：4-bit、甚至 1.58-bit 三值量化，把权重压到极低精度。
- **存储层次扩展**：热专家放 GPU 内存，冷专家放系统内存，词汇数据放 SSD；已有方案让 32GB 核显笔记本运行 120B 参数模型。
- **硬件演进**：统一内存 AI PC、NPU 专用推理。

但对你当前这台机器而言，这些“大容量端侧方案”仍偏重。更务实的是 **10GB 内存以内的小模型 + 云端规划**。

## 3. 你的真实瓶颈：不是 CPU，而是可用内存

你的配置：

| 项目 | 情况 |
|---|---|
| CPU | Intel i7-13700H，16 核，纯 CPU 推理够用 |
| 总内存 | 32GB |
| 日常占用 | Windows + Visual Studio + 网页约 20 多 GB |
| 可用于模型 | **约 10–12GB** |
| GPU | 无独立 GPU，纯 CPU 推理 |

因此选型原则是：

1. **模型权重 + KV Cache 控制在 10GB 以内**，最好 2–6GB，给 VS 留余量。
2. 优先 **4-bit GGUF**，不要跑 FP16。
3. 普通对话场景限制上下文长度，例如 `num_ctx=4096` 或 `8192`，减少 KV Cache。
4. Agent 场景要按工具要求配置上下文，必要时关闭 VS 插件或浏览器标签腾内存。

## 5. 关键矛盾：小模型上下文短，能接 opencode / Pi agent 吗？

**直接回答：以你剩余 10–12GB 内存，用极小型短上下文模型原样接入 opencode 或 Pi agent 做完整代码开发，基本不可行。**

### 5.1 opencode 的硬门槛

opencode 要求**至少 64K tokens 上下文**。低于这个值会报错或静默截断代码和对话历史，导致 Agent 行为错乱。模型本身加 64K KV Cache 的开销，在你的内存余量下非常紧张。

### 5.2 Pi agent 的妥协空间

Pi agent 推荐 64K 起步；系统提示和工具定义在对话开始前就占约 4K tokens。它有**上下文压缩器**，可把 32K 窗口模型当“一等公民”支持，但压缩会丢历史细节，复杂多文件任务记忆力下降。

### 5.3 更现实的轻量 Agent

| 工具 | 定位 | 内存/上下文 |
|---|---|---|
| **qai-cli** | 为本地 CPU 运行的 Qwen2.5-Coder 1.5B 设计 | 32K 上下文，约 2GB RAM，内置工具结果裁剪、旧对话摘要、工作区文件列表注入 |
| **xcoding** | 小模型 Agent | 默认 Qwen2.5-3B，纯 CPU 约 2GB 权重；开发者经验：**3B 是 Agent 实际用工具的底线**，1.5B 时好时坏，0.5B 不可靠 |

所以，如果坚持“本地小模型直接做 Agent”，应从 **xcoding 的 3B 默认配置** 或 **qai-cli 的 1.5B + 32K 优化方案** 开始，而不是把 0.5B/1.5B 塞进 opencode。

## 6. 可行架构：DeepSeek 做规划，本地小模型做执行

你的思路是对的：**用订阅的 DeepSeek 做代码分析、架构设计、任务拆分；本地小模型完成上下文要求小的任务。** 这能同时利用云端推理能力和本地零边际成本。

典型分工：

| 角色 | 模型 | 任务 |
|---|---|---|
| 规划器 / 架构师 | DeepSeek（云端） | 代码分析、架构设计、任务拆解、生成待办列表、审查结果 |
| 执行器 / 编辑器 | 本地 Qwen2.5-Coder 1.5B/3B 或 Qwen2.5-3B | 单文件修改、代码补全、解释片段、生成 docstring、摘要、简单重构 |
| 验证器（可选） | DeepSeek 或本地 3B | 检查执行结果、运行测试、回归验证 |

关键原则：

- **规划阶段不需要把整个代码库塞给本地模型**；DeepSeek 输出明确子任务和文件范围。
- **执行阶段只给本地模型当前文件或选中片段**，控制上下文。
- **本地模型不负责长程记忆**；由 Agent 的编排器保存任务图和中间结果。
- 本地模型用 **GGUF Q4_K_M + Ollama/LM Studio**，便于切换和限制上下文。

## 7. 支持“自动拆解 + 切换模型”的 Agent 工具对比

| 工具 | 核心机制 | 与你的思路的契合点 | 硬件/内存考量 |
|---|---|---|---|
| **opencode-orchestrator** | 编排器-工作者扩展；编排器把提示拆成子任务依赖图，分配给专用角色 | 与 opencode 生态结合；角色可配不同模型/上下文；自动拆解彻底 | 内置 **VRAM 感知模型池**，LRU 淘汰，防止本地模型撑爆内存；API 模型如 DeepSeek 绕过池 |
| **nvHive（`nvh agent`）** | “计划 → 执行 → 验证”；强模型规划，本地模型执行文件和 shell 工具，规划器验证 | 明确支持 **云端规划器 + 本地执行器**；有 **Tier 0/1** 硬件分级，无 GPU/入门 GPU 默认就是该模式 | Tier 0/1 直接匹配你的配置，如 Cloud planner + Qwen Coder 7B；你可换更小本地模型 |
| **Pi Agent（`prewalk`）** | 一次性模型交接：强模型规划并生成 todo、编辑项目文件后，保存工具调用批次，自动切到目标本地模型继续同一对话 | 强模型规划后自动切本地执行；支持角色化路由（如 `smol` 角色对应小模型） | 依赖本地 Ollama 等；注意上下文压缩带来的细节损失 |
| **Aider（`--architect`）** | 架构师模型推理并描述方案；编辑器模型生成精确 diff 并应用 | 经典“推理/编辑分离”，成熟稳定，成本优化 | 分别配置云端架构师和本地编辑器模型；本地编辑器可选 1.5B–3B |
| **Antigravity SDK** | 架构师-构建者框架；云端架构师掌握全局，仅凭任务描述和文件名拆解，不访问源码；本地多个专用构建者执行 | 系统性隐私保护；理念完全一致 | 推荐 24GB+ 显存/统一内存，你的配置处于门槛边缘，需实测 |

**选择建议**：

- 想最直接落地：**nvHive Tier 0/1**。
- 已用 opencode：**opencode-orchestrator**。
- 想轻量、在现有工具上试：**Aider `--architect`** 或 **Pi Agent `prewalk`**。
- 想系统化、隐私优先：**Antigravity SDK**，但先小规模实测内存。

## 8. 推荐落地方案

### 方案 A：稳妥起步（推荐）

| 组件 | 选择 |
|---|---|
| 云端规划 | DeepSeek 订阅 |
| 本地执行 | **Qwen2.5-Coder 1.5B 或 Qwen2.5-3B，GGUF Q4_K_M** |
| Agent | **nvHive Tier 0/1** 或 **opencode-orchestrator** |
| 运行时 | Ollama / LM Studio |
| 内存策略 | 本地模型权重控制在 2–3GB；Agent 运行时关闭 VS 多余插件和浏览器标签 |

适合：日常单文件修改、补全、解释、简单重构、测试生成。

### 方案 B：轻量双模型

| 组件 | 选择 |
|---|---|
| 架构师 | DeepSeek |
| 编辑器 | 本地 Qwen2.5-Coder 1.5B/3B |
| 工具 | **Aider `--architect`** |
| 优点 | 成熟、配置简单、成本可控 |
| 缺点 | 不如编排器自动拆解彻底 |

### 方案 C：小模型专用 Agent

| 组件 | 选择 |
|---|---|
| 本地 Agent | **xcoding（默认 Qwen2.5-3B）** 或 **qai-cli（Qwen2.5-Coder 1.5B + 32K 优化）** |
| 云端 | 可选 DeepSeek 做复杂规划，人工把子任务交给本地 Agent |
| 适合 | 不想引入复杂编排器，接受半自动任务拆分 |

### 方案 D：后台辅助，不做 Agent

用 **Qwen2.5-1.5B** 通过 Continue.dev 等 VS Code 插件做代码补全、解释选中片段、生成 docstring。上下文需求低，纯 CPU 响应可接受，几乎不抢内存。

## 9. 实施步骤与注意事项

### 9.1 实施步骤

1. **安装 Ollama 或 LM Studio**，拉取本地模型：
   ```bash
   ollama run qwen2.5-coder:1.5b
   # 或
   ollama run qwen2.5:3b
   ```
2. **确认 GGUF 和 Q4_K_M 量化**；不要用 FP16。
3. **配置云端 DeepSeek API** 到所选 Agent 的规划器/架构师角色。
4. **配置本地模型** 到执行器/编辑器角色。
5. **设置上下文**：普通对话 `num_ctx=4096/8192`；Agent 场景按工具要求，必要时用压缩器或子代理降低主会话消耗。
6. **先小任务验证**：单文件加注释 → 单函数重构 → 生成测试 → 多文件小任务，逐步加复杂度。
7. **监控内存**：任务管理器观察提交内存；本地模型加载后系统剩余内存低于 2–3GB 就换更小模型或关 VS 插件。

### 9.2 注意事项

- **3B 是 Agent 工具使用的现实底线**；1.5B 时好时坏，0.5B 不适合 Agent。
- **opencode 的 64K 硬门槛**不要硬绕；绕过后行为错乱比报错更麻烦。
- **上下文压缩会丢细节**；复杂多文件任务优先用云端规划器保留任务图。
- **纯 CPU 速度单位是 token/s**：1.5B 可近实时，7B 明显等待。
- **三值量化、2-bit 量化**在复杂推理上可能有质量折损，先实测再用于关键任务。
- **Antigravity SDK 对你的配置偏重**，先小规模验证内存。
