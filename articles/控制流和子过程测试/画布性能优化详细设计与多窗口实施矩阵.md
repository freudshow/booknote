# 可视化配置画布性能优化：详细设计与多窗口实施矩阵

> 目的：把当前画布的性能瓶颈、优化目标、线程边界、缓存/持久化协议及可并行实现任务写成可独立交付、可验收的工程方案。本文是实施设计，不代表相关优化已经实现。
>
> 适用项目：`visualconfig/LogicEngineConfigTool`，WPF、.NET Framework 4.8、RegressionTests 自定义回归程序、C# 7.3。

## 1. 结论摘要

卡顿并非单一“鼠标事件太多”，而是 WPF UI 线程上的多项开销叠加：大量 Canvas 子项及控件的布局/命中测试、每次缩放触发整画布 `LayoutTransform`、连线路由的高复杂度障碍搜索、全量删除再创建 Polyline/Polygon、以及事件路径中的调试输出和全图枚举。应按以下顺序治理：

1. **先限定工作量**：空闲鼠标移动不做画布级命中测试/逻辑；拖动期间只移动元件本体并按帧合并位置更新，放下后只更新受影响的连接。删除、连接等按连接索引做增量更新。
2. **把路由变成纯计算并降低算法复杂度**：以不可变 DTO 快照提交到后台线程；路由计算不接触 WPF、ViewModel、可变模型。先修复障碍判定和端口逃逸，再采用空间索引、稀疏可见图、带方向状态的 A* 和稳定堆。
3. **WPF 仍由 UI Dispatcher 独占**：后台线程只读快照、产生不可变路线结果；UI 线程检查版本号后一次批量提交 `PointCollection`/箭头/Canvas children。不要跨线程操作 `Canvas`、`Polyline`、`DependencyObject` 或编辑器模型。
4. **将 `.editor.json` 作为可丢弃的派生缓存**：`c0757.json.editor.json` 可缓存路由点、版本、文档摘要、算法版本等；主配置仍是元件/端口/连接/位置的权威来源。缺失、哈希不匹配、格式不支持或校验失败时忽略缓存并从主配置重算，不影响主配置加载/保存。
5. **仅对较长操作展示进度**：进度显示在画布视口下方；能确定进度的后台任务显示百分比，否则显示不确定进度；完成/取消/失败后延迟短暂时间自动隐藏。拖动这种持续交互不应常驻显示进度条。

建议实现顺序：基线与路由测试 → 纯路由/正确性 → 索引与增量渲染 → 输入事件节流 → 后台调度/进度 → sidecar 缓存 → 集成性能验收。

## 2. 现有实现调查（代码事实与影响）

调查范围：`LogicEngineConfigTool/ViewModels/VisualEditorViewModel.cs`、`VisualEditorNewElements.cs`、`Views/VisualEditorView.xaml(.cs)`、`Controls/VisualElementControl.xaml(.cs)`、`Models/ElementModel.cs`、`Services/EditorStatePersistenceService.cs`。

### 2.1 鼠标事件及拖动

- `Views/VisualEditorView.xaml` 的 Canvas 直接订阅 `PreviewMouseLeftButtonDown`、`PreviewMouseMove`、`PreviewMouseLeftButtonUp`。左右键菜单另由 code-behind 注册；鼠标移动处理因此是持续热路径。
- `Canvas_MouseMove` 当前分支包含复制预览位置更新、临时连线 Polyline 更新及端口命中检查/可能调用 `ConnectElements`、框选矩形更新、拖动时位置更新和调试日志。端口连接可能在 MouseMove 悬停时即触发，MouseUp 还有一次连接提交路径，存在重复提交/行为竞态风险，须在实现时统一提交时机。
- 元件拖动过程中调用 `UpdateElementPosition(..., false)` 移动控件及更新模型位置，但连线不实时更新；MouseUp 最终调用 `RedrawConnections()` 全量清除、重算、重建全部线和箭头。用户给出的“放下后只更新相关线”方向符合现状缺口。
- `UpdateElementPositionCore` 已能单独定位移动元件；`RedrawConnectionsForElement` 已存在并按该元素输入及输出收集关联线，但它仍先 `GetAllElementBounds()`，且任一元件移动可能影响其周边线避障，因此不能简单地只重画端点相连线而忽略路线受阻变化。
- Canvas MouseMove 中的 `Debug.WriteLine` 在拖动热路径执行；规模大/调试器连接时会放大开销。生产性高频日志应移除、条件化或限频。

### 2.2 全图绘制和可视对象

- `_connectionPolylines`、`_connectionArrows` 为字典索引，具备单连接移除/替换基础；但 `RedrawConnections()` 会 `RemoveAllConnectionVisuals()` 后遍历所有元素输入，再逐条运行路由并重建所有 UI 对象。
- `UpdateCanvas()` 重建元件控件、组框并全量重绘所有连接。加载配置最终会调用它。
- `DeleteElement` 默认在结束时调用全量 `RedrawConnections()`；批量删除虽然延迟到最后，但最后仍全量重绘。单连接删除已有单条清理路径，可以进一步接入连接索引、缓存失效。
- 每条连接由 `Polyline` 和箭头 `Polygon` 构成；`AddConnectionJumpovers` 当前仅输出调试信息，并未实现交叉跳线。路由避交叉和绕障并非同一个约束，设计验收不要把“无障碍”误称为“无交叉”。
- `VisualElementControl` 对每个元件建立独立 Canvas 和控件树，主边框含 `DropShadowEffect`，端口及标签也生成多个元素。元件数量扩大时，视觉树、布局、命中测试成本随元素数增长。优先保留交互能力，性能实测后再决定是否改成 DrawingVisual/虚拟化，不能把大范围重写列为首批必要项。

### 2.3 当前绕障算法和复杂度风险

`FindObstacleFreePath` 位于 ViewModel 中，当前过程可归纳为：膨胀所有元件矩形 → 快速尝试固定正交折线 → 生成障碍边界/插值坐标 → 横纵坐标笛卡尔积生成候选点 → 构造同横/纵可见邻点图 → A* 搜索 → 路径简化。

重要实现细节：

- 每条线调用时会线性取得/处理障碍集合；一次全图重绘会对多条连接重复处理同一批元件边界。
- 坐标候选数分别随障碍数增长，候选点是 X/Y 笛卡尔积，最坏候选点数近似 `O(B²)`；每点对障碍过滤再乘一层 `O(B)`。建边和碰撞测试又重复扫描障碍。
- A* 使用 `HashSet` 保存 open 集合，每轮通过 `OrderBy(fScore).First()` 线性筛选/排序；节点多时搜索部分也会有较高成本。
- 方向改变代价 120 通过当前节点的前驱推算，搜索状态只用 `PointKey`，不同进入方向的代价没有作为不同状态保存；这不能保证“路径长度 + 转弯代价”全局最优。
- 源/目标相关膨胀障碍按“矩形包含端点/逃逸点”从 `pathObstacles` 整体排除，可能误排第三方矩形或过度放行；逃逸点检查、快速路径障碍集合与后续完整障碍集合不完全一致。返回的简单 fallback 路径没有最后的完整障碍验证。
- 当前检查主要是矩形相交，不是对复杂形状的精确避障；这些边界应在新路由契约中明确，并通过最终路径验证防止明显穿越元件。

### 2.4 缩放、画布与侧文件

- `ZoomLevel` 调用 `ApplyZoom()`，对整个 Canvas 设置 `LayoutTransform = new ScaleTransform(...)`；Ctrl+滚轮已按鼠标点修正滚动偏移，但布局变换会触发全树布局/extent 更新。后续比较 `RenderTransform` 的收益和 ScrollViewer extent 行为后再替换，不能未经验证直接换 transform。
- 元件逻辑坐标及连接模型已在主配置模型中；`ElementBase` 含 `X/Y`，端口模型中保存来源/目标关系。位置、连接关系不应在 sidecar 成为另一份互相冲突的权威数据。
- `EditorStatePersistenceService` 已使用 `<主文件路径>.editor.json`，现有 sidecar schema v1 储存积分/存储元件配套关系，并以主配置 SHA-256 做匹配；加载异常时隔离 sidecar 而不阻止主文件加载。任何路由缓存扩展必须兼容这一契约，不能覆盖/丢失 `IntegralStoragePairs`。
- 该 sidecar 在主配置成功保存后写入，不能宣称两文件原子事务。路由缓存写入失败应标记缓存缺失/脏，主配置提交仍成功。

## 3. 目标、边界与验收原则

### 3.1 用户可见目标

- 空闲移动鼠标时，不触发全画布扫描、路由计算、配置序列化或状态刷新。
- 单元件拖动期间，鼠标移动仅更新拖动预览/元件位置；连线不全量重绘，不对每条线运行路由算法。可选只绘制拖动元件的半透明预览或隐藏相关连线，提交后刷新。
- 元件放下后只更新必须失效的路径：端点相关连接，加上被移动元件/旧位置/新位置影响的路线；不相关路线保持原视觉对象实例及路径。
- 加载、批量删除、布局重算等耗时工作不阻塞 UI；WPF 视觉树更新分批/单次批量应用，避免每条线完成后重复布局。
- 鼠标滚轮缩放保持缩放中心体验；缩放不重算逻辑连线，缩放只改变显示变换。
- sidecar 可用时加载路线缓存，不可用时回退现有主配置动态路由；缓存损坏不得破坏主配置。

### 3.2 非目标/约束

- 不改变主配置 JSON 中的协议字段、端口编号、执行顺序、元素 ID、连接含义或运行时逻辑。
- 第一阶段不将全部 UI 绘图改为自绘控件，不改变 WPF/.NET Framework 版本，不引入第三方路由库或测试框架。
- 不允许后台线程访问 WPF `DependencyObject`、Canvas children、当前可变 `IElementModel` 或集合；不在后台写主配置。
- “鼠标移动不捕获事件”不等于删除所有 MouseMove：框选、拖动、拖线、复制预览仍需交互更新。真正目标是**空闲 MouseMove 零重工作、活动手势按帧合并且只执行必要工作**。

### 3.3 性能测试口径

首先增加可重复基准场景，记录元件数、连接数、障碍数、加载耗时、路由耗时分布、拖放后的失效线数/总线数、鼠标移动 UI 更新数、放大缩小完成时间、UI Dispatcher 延迟与内存。建议场景：50/100/250/500 元件，低/中/高连接密度、狭窄绕障和密集端口案例。项目当前单任务最大元件数限制为 500，可用作规模上界，但基准数据应由执行实测产生。

验收必须比较同一硬件/配置下的优化前后基准。硬目标：拖动期间重路由次数为 0；放置后不相关路径不重建；空闲鼠标事件不触发画布扫描/序列化；后台结果不覆盖较新文档版本。帧率/毫秒目标由基线后设定，不以未经实测的数字伪造承诺。

## 4. 目标架构与执行流

### 4.1 模块职责与数据边界

1. **Gesture/UI 层**（`VisualEditorView.xaml(.cs)`）：识别点击、拖动、框选、拖线等手势；仅活动手势订阅/执行 MouseMove 处理；向调度器提交意图，不做路线搜索。
2. **Editor state/index 层**（VM 或独立 service）：在 UI Dispatcher 上维护模型、元素边界索引、连接邻接索引、文档版本 `DocumentVersion`、路由版本；创建只含值类型的 `RoutingSnapshot`。
3. **Routing 层**（新建纯 C# Services/CanvasRouting）：输入快照、取消令牌/版本；输出 `RouteResult`（ConnectionId、点坐标、诊断、处理状态），不引用 WPF 类型。函数可在 RegressionTests 运行，不依赖窗口/Dispatcher。
4. **Scheduler 层**：后台任务合并、取消、过期结果丢弃、进度通知；任务结束通过 Dispatcher 返回 UI 层。
5. **Renderer 层**（UI Dispatcher）：检查文档/视口/算法代次；用结果批量更新连接视觉对象、箭头和字典，不跨线程创建 WPF 几何对象。
6. **Persistence 层**：主配置仍按现有流程保存；派生 editor sidecar 兼容 schema v1 字段，v2 加路由缓存，并保持主配置 SHA-256 匹配逻辑。

### 4.2 调度与线程同步协议

- 所有模型修改、`_elements`/控件字典/Canvas 操作都在 UI Dispatcher 完成。
- 每次结构/位置/连接变化时递增 `DocumentVersion`；空间索引或路由参数变化时递增 `RoutingVersion`。快照包含两代号、ConnectionId、端口身份、起终点、边界矩形及算法配置。快照必须深拷贝这些值，不能引用 mutable model。
- 后台计算可使用 `Task.Run`；大量任务应按连接分块/限制并发，单任务支持取消。新拖放、再次加载、删除/关闭视图时取消或替换旧工作。
- 结果回 UI 后同时检查 `DocumentVersion`、`RoutingVersion`、连接仍存在且端点身份一致；不匹配的路线丢弃，不得将过期结果绘制到新状态。不要使用锁保护 WPF controls，也不要依赖后台修改共享集合。
- 使用单调 `operationId` 避免旧任务完成事件把新操作的进度条隐藏；任务取消、异常也必须进入统一完成路径。
- 快速单连接增删/移动可低于后台阈值时同步计算，但仍通过统一 scheduler/route API；阈值以基准配置，不复制两套算法。

### 4.3 手势事件策略

- 按下时进行一次命中测试/操作判定。点击（左/右键）、右键菜单、快捷键、有效端口和拖放均保留。
- 只有进入活动拖动/拖线/框选/复制预览状态才执行 MouseMove 分支；活动期间以 `CompositionTarget.Rendering` 或 `DispatcherPriority.Render` 合并多次输入，每个渲染周期最多更新一次目标位置/预览，避免为所有原始 MouseMove 逐条做开销。
- 拖动元件时优先更新 UI 位置（可采用 RenderTransform 临时位移；与 Canvas 坐标同步策略须验证），结束时一次性提交模型位置、标记障碍索引变更并调度路线失效。拖动取消则恢复起点，不触发配置持久化/路由。
- 连线预览只更新临时线末端；不要在 MouseMove 命中端口后提交真实连接。真实 Connect 在 MouseUp/点击确认时仅提交一次，保留连接规则、错误提示、IF/控制流数据一致性。
- 连接、删除、移动和批量操作更新连接索引及失效集。右键删除、快捷键删除、上下文菜单多选删除都走同一批量服务。

### 4.4 缩放与渲染层

- 连接路线始终存储逻辑坐标；zoom 变化不调用 Router，也不更改 sidecar 路由缓存。
- 评估将 Canvas `LayoutTransform` 替换为外层绘制层 `RenderTransform`（或 RenderTransform + 明确 extent 尺寸/滚动范围）。必须验收 ScrollViewer 可滚动范围、鼠标锚点、边界矩形、拖拽坐标转换、控件命中测试、画布自动扩张。未经验证，保持当前 LayoutTransform 是安全回退。
- 连接更新采用批量提交：先在普通集合生成结果；UI 一次移除/替换受影响的线路对象；避免每条连线调用全局重建。可见性/裁剪优化作为性能基线后的独立增强，不改变选取语义。

## 5. 增量更新和连线失效规则

只更新端点相关线路不足以保证避障正确：移动的元件可能挡住任何一条不相连的线，也可能清除其旧位置处障碍。实现时维护空间索引并对移动前后包围盒（含安全边距）求并集，做路线包围盒查询，取并集：

`invalidated = incidentConnections(movedElement) ∪ routesIntersecting(oldBoundsInflated ∪ newBoundsInflated)`。

- incident 索引：`ElementId -> ConnectionId[]`（作为源或目标）；连接从源输出到目标输入，单一权威结构由 UI 线程维护。模型的 Input/Output 双写仍沿用既有规则，并在连接变更时同步索引。
- 元件删除：先取关联集并解除模型连接，再移除元素/控件/空间索引，重算旧边界影响集，批量处理失效线路；批量删除先合并失效集，避免逐个删除后反复重算。
- 新建连接：仅计算新路线；若多路线交叉优化以后启用，需要显式把因连接顺序受影响的线纳入失效集，不能默认全局路由稳定。
- 被影响路线重算完成前，建议保留旧路线并标识 stale（或暂时隐藏），避免整图闪烁/白屏。新结果提交应与文档代号一致。
- 路线缓存保存路线逻辑点及版本/连接身份；UI 的 PointCollection、Stroke、Polygon Arrow 不序列化。

## 6. 新避障路由算法设计

### 6.1 API 建议

在纯计算服务暴露类似接口（命名可按代码风格调整）：

- `RouteRequest`: immutable start/end、source/target element IDs+port IDs、所有相关障碍值矩形、clearance/portEscape、算法版本、连接稳定 ID。
- `RouteResult`: ConnectionId、逻辑坐标 `PointValue[]`（自有简单值结构，不用 `System.Windows.Point`）、成功/失败状态、是否 fallback、诊断、算法版本。
- `RouteBatchRequest/Result`: 用于加载或大规模修改，一次构建空间索引/障碍表示并处理多线。

### 6.2 几何正确性要求

- 障碍是带 ElementId 的矩形记录，膨胀只对实际障碍生效。源元件只允许从输出端口沿输出方向穿过源本体到安全走廊；目标只允许从安全走廊进入输入端口。不得因起终点恰好落在某膨胀 Rect 内就移除整个矩形障碍。
- 所有路径段（包括端口引线及 fallback）必须经过同一规则的最终碰撞验证。若找不到有效路由，返回显式 `NoRoute` 或受控提示路径；不静默返回穿越障碍的路径。
- 快速直角路线通过与通用验证器一致的碰撞规则即可直接返回。优先选择长度 + 转弯数 + 稳定性惩罚最小的路线，避免随 Dictionary/HashSet 枚举顺序变化而闪跳。
- 端口方向和间距固定为 Router 输入配置并纳入算法版本；当前源向右、目标向左逃逸的行为应保留/验证，不因重构翻转连接方向。

### 6.3 可扩展搜索策略

- 障碍空间查询采用均匀网格/区间索引/R-tree-like 简单空间索引之一，先对连接局部影响区域筛选候选障碍。索引必须正确处理矩形横跨多个桶、边界坐标和旧/新 bounds；实现复杂度过高时先用包围盒过滤+排序，测量后扩展。
- 用障碍边缘可见坐标构建稀疏正交可见图，不生成全部 X×Y 点；或使用稀疏坐标网格并对每个节点只连接最近可视邻居。路线空间大时设置候选上限和取消检查。
- A* 状态为 `(node, incomingDirection)`，方向状态纳入 visited/g/f；使用自实现二叉最小堆（.NET Framework 4.8 无内置 `PriorityQueue<T>`）并加入稳定 tie-breaker。启发式至少为 Manhattan 距离，惩罚项保证一致/可接受；权重在算法文档中明确。
- 为避免同一组障碍在每条连接重复生成全部边界/索引，batch 中共享只读索引；某次元件移动只更新空间索引局部条目。
- 路由缓存键包括 schema/version、算法版本、clearance/port escape 参数、端点ID/端口ID及起终点坐标、相关障碍签名。任何输入变化都必须失效；缓存只是性能优化，不参与模型语义。
- 必须有小规模最短性/障碍性质测试、随机矩形属性测试、极端同坐标/重叠元件/近端口/无通路/大坐标测试。只比较视觉截图不足以验证正确性。

## 7. Sidecar `.editor.json` 设计

### 7.1 定位与兼容性

- 路径仍为 `<mainPath>.editor.json`，由现有 `EditorStatePersistenceService.GetSidecarPath` 管理。
- 主配置含权威元件、位置、端口/连接、执行结构；sidecar 的新增 `CanvasRouteCache` 是派生数据。即便后续 sidecar 中包含 viewport/UI state，也须有明确 optional/read-only 语义，不反向覆盖主配置权威关系。
- schema v1 当前 IntegralStoragePairs 必须原样保留；升级 schema 时实施显式 v1→v2 迁移。未知 schema 应忽略 sidecar 元数据并报警，而非拒绝主配置。
- Sidecar 匹配主文件已有 SHA-256；SHA 不匹配时**不能用旧缓存**。保存成功后基于主文件实际提交的字节生成 hash。编辑器状态版本变化令 sidecar dirty；路由 cache 可以异步/延迟保存，但要防止旧版本写入覆盖新版本。

### 7.2 建议 schema v2（示意）

```json
{
  "SchemaVersion": 2,
  "DocumentId": "...",
  "MainConfigSha256": "...",
  "IntegralStoragePairs": [],
  "CanvasRouteCache": {
    "AlgorithmVersion": 1,
    "CoordinateSpace": "Logical",
    "Routes": [
      {
        "ConnectionId": "Connection_1_0_2_0",
        "SourceElementId": 1,
        "SourcePortId": 0,
        "TargetElementId": 2,
        "TargetPortId": 0,
        "InputSignature": "...",
        "Points": [{ "X": 160.0, "Y": 50.0 }, { "X": 196.0, "Y": 50.0 }]
      }
    ]
  }
}
```

上例为字段建议而非最终 ABI。加载需校验：大小上限、点数上限、所有坐标 finite、路径最少点数、connection ID/端点一致、每端口确实存在且连接与主配置一致、算法版本匹配、输入签名匹配。单条记录坏时可隔离该条并动态重算，不必丢掉全部合法配套。缓存文件写临时文件再 replace/move，妥善处理 Windows 文件占用；缓存失效/保存失败保留主文件成功状态并显示非致命诊断。

### 7.3 保存时机

- 打开：读主文件、构造模型与 index；sidecar 能匹配时校验并安装可用缓存；未命中路由进入动态计算。 UI 可先显示元件/有效缓存路线，未命中部分异步补齐。
- 配置修改：route cache 只在相关路线重新计算后更新内存副本；取消/旧计算完成不可污染最新 cache。
- 保存主文件成功：使用确切提交 bytes 得到 hash，排队写入同一版本的 sidecar。若主配置在缓存完成前再次变更，丢弃旧写请求。
- 另存为：sidecar 写入新路径，`DocumentId`/hash/缓存关联需按产品预期处理；禁止复制原路径 sidecar 后误命中。
- 主配置无 sidecar：保持当前加载流程，回退路由计算并在后续保存时可新建 sidecar；不能要求用户手动生成副本。

## 8. 进度 UI 设计

- 在右侧画布区域的底边增加固定高度状态区域（画布滚动视口之外），不随 Canvas zoom 缩放，也不覆盖画布内容。
- ViewModel 提供可绑定状态：`IsCanvasOperationInProgress`、`CanvasOperationMessage`、`CanvasOperationProgress`（0..1；null/负值表示不确定）、`OperationId`。每个重型任务在后台/调度器报告进度，Dispatcher 上节流更新（建议不高于每 50–100ms 一次，数据由实测调整）。
- 自动隐藏：成功/取消/失败统一结束；如果连续任务接续则维持显示，不闪烁；结束后延时约 500–1000ms 隐藏，`OperationId` 确保旧 timer 不隐藏新操作。失败另留诊断/错误提示，不只靠进度条表达。
- 仅启用后台批量路由、复杂加载/批删计算等重任务；短连接动作无必要时不显示。拖动中不能持续显示工作进度；如需状态只提供微弱拖动反馈。
- 确保 `ProgressBar` 进度 UI 更新不会被大量逐条事件淹没。关闭视图/更换文档时取消任务，重置可见状态。

## 12. 风险及决策记录

1. **局部重绘可能让其他线路穿元件**：需用空间索引查询旧/新障碍边界附近路线，不止 incident connections。
2. **RenderTransform 不等同 LayoutTransform**：ScrollViewer extent 和自动滚动范围可能不对；未通过 UI 测试不能替换。
3. **线程化不保证快**：若结果准备/视觉树批量添加仍在 UI 线程花费很长，仍会卡顿。先降低算法量、合并 UI commits，再决定是否进一步虚拟化/自绘。
4. **缓存可能增大 sidecar**：限制每条路径点数、缓存总量、文档大小；过期缓存可全量丢弃。不可因缓存保存阻塞主配置保存。
5. **哈希不匹配与已有 sidecar 协议**：主配置每次序列化可能字节变化；必须以文件实际提交字节 hash 作为依据。schema migration 必须保留积分配套 metadata。
6. **过期后台结果/进度错乱**：版本戳、operationId、取消令牌均是必需条件，不是可选优化。
7. **连线“避障”与“避交叉”不同**：当前跳线函数不实际绘制跳线。第一期验收只保证元件障碍和端口逃逸，不承诺无连接交叉。
8. **回滚策略**：Router、新缓存或 RenderTransform 出错时可切回旧动态路径/当前变换；sidecar cache 无法解码时忽略缓存。不能回滚主配置数据或改写协议字段。
