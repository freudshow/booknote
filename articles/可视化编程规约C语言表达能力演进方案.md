# 可视化编程规约 C 语言表达能力演进方案

> 原稿日期：2026-09-25；本次修订：2026-10-27。
>
> 面向读者：配置工具开发者、嵌入式运行时开发者、策略开发者和测试维护人员。
>
> 文档性质：基于现有源码的设计建议，不代表功能已经实现，也不是现场投运许可。

## 1. 结论与阅读路线

建议保留现有图形配置和存量运行路径，新增一套具有明确类型、作用域、数组、函数和结构化控制流的策略语言。图形和文本先编译成同一份结构化中间表示，再生成经过独立验证的执行指令。嵌入式设备执行这些指令，而不是现场编译任意 C 源码。

目标不是复制 C 的所有语法，而是让策略开发者具备三类能力：用变量和数组保存数据，用分支和循环表达算法，用函数和有状态功能块复用策略。同时，设备必须能拒绝不兼容、超预算或未经授权的程序。

“任何现场策略都能配置”应改成可验收的目标：**在已声明的设备接口、数据规模、计算预算和安全权限范围内，常见策略无需修改固件；新增设备或新的基础能力通过受控接口扩展；超出范围时给出明确诊断，而不是勉强运行。**

先固定语言和执行语义，再增加语法和元器件。否则，同一段策略可能在编辑器、仿真器和设备上产生不同结果。

### 1.1 本方案区分的三种内容

- **当前事实**：能在本次读取的源码中定位；不等同于已经在目标设备上验证。
- **推荐设计**：供开发立项和接口评审采用；文中的 VCL、IR 字段、模块名和错误码均为建议，除非明确标为现有名称。
- **待确认事项**：需要设备实测、接口方确认或项目决策，不能当作已满足的前提。

### 1.2 阅读路线

1. 负责人先读目标边界、关键决策和分期验收。
2. 双端开发者重点阅读语言语义、编译与执行、兼容和热加载。
3. 策略和测试人员重点阅读示例、状态机、测试矩阵和投运步骤。
4. 需要核查现状时，查文末源码证据索引。

### 1.3 主要术语

IR 是中间表示，用来保存编译后的程序语义；VM 是执行受限指令的虚拟机；AST 是解析文本得到的语法树；RTDB 是实时数据库。Host API/FFI 指程序调用固件能力的接口，本方案只开放白名单能力。YK/YT 分别指遥控和遥调，SOC 指储能荷电状态，PCS 指储能变流器。Legacy 指保留旧格式和旧语义的兼容路径；Profile 指某一目标版本的能力与资源档案；generation 指一次激活的程序代次。

### 2.2 配置端：已有基础比原稿更完整，但还不是通用编程语言

配置软件是经典 WPF / .NET Framework 4.8 项目。回归项目明确设置 C# 7.3；主项目没有显式 `LangVersion`，不能据此把主项目有效编译语言版本也写死为 7.3。[H1]

目前应当区分两条编译和保存路径：

1. **旧平面路径**：规范化连接、提取控制描述、分析区域、安排数据依赖、生成执行顺序和 `NextID`；`TransactionalConfigSaveService` 在副本上应用计划，写临时文件并读回比较，最后 Replace/Move。该入口拒绝新工程和非 Legacy 契约。[H2]
2. **分层工程路径**：保存 `EditorDesign` 的任务、画布和子过程，展开后构建独立运行图，分配运行身份，记录 `CompilationInfo.SourceMap`，再经 `RuntimeConfigAdapter` 投影运行 JSON。工程保存与运行导出已有独立入口；编译失败的工程可以保存为草稿，不能由此推断它可部署。[H3、H4]

当前也不只是原稿中的五种控制元件：已有 `ALGO_INTEGRAL`、`DEBUG_PRINT`、`SAVE_DATA`、`JUMP`、`SUBPROCESS` 等设计和契约。`LoopContinue`、`LoopExit` 已有结构化目标解析；子过程目前通过展开实现，不是带运行栈的函数调用。[H5、H6]

`FOR` 已有初始化、条件、迭代三个表达式槽和控制目标编译，但未见其三阶段完整执行语义在指定固件中实现。新版 WHILE 的配置端还能生成入口复位辅助节点，并区分首次进入与 continue；这属于另一个版本的契约，不能自动套到原稿的循环模型。[H5]

### 2.3 两端的“类型”不是同一回事

- 配置端 `PortDataTypeEnum` 是端口允许连接的数据类型集合；连接通常检查位掩码交集。它不是完整的变量类型、数值提升或转换规则。
- 配置端端口 `Value` 是字符串，普通参数 `Value` 是 `object`；`FLOAT` 显示标签不能证明数值一定按 float32 储存。
- 当前固件通用端口值和通用数值参数槽为 `double`，但私有参数还有整数、结构和字符串；RTDB 接口也可能经过 `float`。不能把整个系统概括为“所有东西都是 double”。[H7、R1、R5]

因此，新语言必须定义自己的值类型，不能只把已有类型枚举直接暴露成语言类型。

### 2.4 指定固件：只有 IF 注册，且存在版本契约差异

本次读取的 `LogicEngineV2_RegisterBaseElements` 注册了 **34 种 Type**，控制流专用类型只有 `IF`；没有注册 `SWITCH`、`WHILE`、`FOR`、`DO_WHILE`、`JUMP`、`SUBPROCESS`，也没有独立积分、日志打印和数据存储元件。注册表中的极值名称是 `MAX/MIN`，与配置端名称和适配结果必须逐项对照。[R2]

未知 Type 会导致整份候选配置加载失败，**不是跳过该元件**。但是，根对象的版本号并未在实际加载路径中形成有效的兼容校验。配置端已有目标 Profile 和契约证据机制，不等于这份固件实现了它声明的全部能力。[R3、H4]

当前资源限制也有具体含义：[R1、R3]

| 项目 | 当前行为 | 设计影响 |
| --- | --- | --- |
| 每链路任务 | 1～10 个；超限拒绝 | 新格式需明确同样还是新的上限 |
| 每任务元件 | 固定容量 500；超过时截取前 500 | 新格式必须拒绝超限，不能截断程序 |
| 元件 ID | 范围 0～499，任务内唯一 | 不能把任意外部 ID 直接用作数组下标 |
| 通用端口和参数槽 | 16 入、16 出、32 参数 | 不等于每个具体元件都有这么多合法端口 |
| 表达式文本 | 200 字节缓冲，最多保留 199 字节 | 新脚本不能复用这个缓冲保存整段代码 |
| 执行入口 | `Elements[0]` | 不是“Id=0”，新格式应提供显式入口 |

这些是源码中的容量和处理规则，不是性能测试结果。

### 2.5 运行语义：按调用更新，而非完整扫描快照

实际调度器是 `VisualProg_TaskThread`。它从数组首元件开始，同步调用 `Execute`，再按执行后的 `config.nextId` 跳转。IF 在执行中改写自身 `nextId`。普通流程结束或元件返回非零后，线程等待扫描间隔，再从入口开始。[R4]

由此有五个重要限制：

1. 正常轮次的入口间隔约为“执行耗时＋轮末等待＋调度开销”，不是固定周期。
2. 输入元件在被执行时分别读取 RTDB；同一轮不是统一输入快照。
3. 未选分支没有被执行，其缓存和私有状态通常保留；没有统一“本轮有效”的标记。
4. 执行器没有累计步骤和时间预算；`NextID` 回边可持续运行。不过每步会检查停止标志，不能说普通计算循环完全无法停止。
5. `TIMER_DELAY` 会在 `Execute` 内 `usleep`，部分 YK/YT 公共调用也可能等待；停线程使用无超时 `pthread_join`，因此不能保证有界停止。[R4、R6]

普通 `NextID` 有加载期引用检查；IF 私有真假目标未经过相同完整检查，且执行器在映射读取前缺少动态 ID 范围检查。这是应优先修复的源码风险，尚未在本次进行异常配置注入复现。[R3、R4]

### 2.6 表达式：已有自定义语言，但不能作为新语言的正确性标准

配置端解析器能构建带位置的 AST，主要用于语法诊断，未见通用类型推导和执行器。它支持部分算术、关系、逻辑、位运算、固定数学函数和 RTDB 赋值，但不支持语言级变量、数组、语句块和用户函数。[H8]

固件 `eval.c` 的若干实际行为与 C 或配置端校验不一致：[R5]

| 项目 | 已核查的源码行为 | 对新设计的要求 |
| --- | --- | --- |
| `&&`、`\|\|` | 两侧都会求值 | 新语言明确采用短路；旧表达式留在独立兼容模式 |
| 除法 | 数值按 double 计算，且先算除数 | 不把旧求值顺序复制到新语言 |
| 位运算 | double 转有符号 `long` 后运算 | 新语言固定宽度，检查移位和范围 |
| 函数 | 配置端只统一限制最多两个参数；C 端按函数实际参数个数检查 | 建立同一份函数签名清单 |
| `max/min` | C 求值器有；配置端该解析器白名单没有 | 不能笼统说双端函数表一致 |
| RTDB 赋值 | 可以在表达式内部立即写库，写入结果未可靠传递 | 新语言的表达式保持纯计算，写入改为显式操作 |
| 错误 | NULL、NaN、日志、返回码和非有限值处理混用 | 定义独立错误结果，不用 NaN 代替状态码 |

此外，源码中的三角函数常量折叠会覆盖角度换算结果，而动态求值做了角度换算；常量与点位参数可能采用不同单位。此项应作为缺陷候选单独测试，不应写成新语言必须继承的行为。[R5]

### 2.7 热加载已有基础，但不是完整事务

已有流程包括 inotify、5 秒稳定检查、MD5、临时快照和独立候选对象。候选解析失败时，正常情况下旧任务继续运行；候选加载通过后，停止旧任务，再逐个创建新线程。[R7]

新线程可能在其他线程尚未创建成功前执行输出；创建失败时恢复的是保留的旧对象，而不是精确的程序位置和外部状态。成功升级也没有通用状态迁移。因此，“完全复用热加载”和“失败不产生任何影响”都不成立。能复用的是候选隔离思路，激活屏障、输出授权和状态迁移仍需设计。

### 2.8 现有测试能证明什么

回归程序已有 `--verify-group` 分组入口，覆盖序列化、事务保存、源映射、循环编译和目标契约等；部分时段纯函数也有求值断言。不能继续写“没有测试选择器”或“完全没有求值测试”。[H9]

但没有发现覆盖任意图逐扫描执行、真实积分、设备副作用和热加载状态迁移的完整通用仿真器。配置测试中的合成目标证据也不是设备执行证明。本方案后续仍需增加独立运行语义与目标板验证。

## 3. 目标、非目标与策略覆盖

### 3.1 “接近 C 的表达能力”具体指什么

| 能力 | 目标 | 边界 |
| --- | --- | --- |
| 控制抽象 | 顺序、条件、选择、循环、提前退出 | 每轮执行有预算；不能靠无限运行等待设备 |
| 数据抽象 | 有类型变量、定长数组、结构化记录 | 不开放裸指针、任意地址和无界分配 |
| 过程抽象 | 参数、返回值、局部作用域、库复用 | 无递归、无函数指针，调用关系可静态分析 |
| 时间与状态 | 跨扫描状态、定时器、持续时间、状态机 | 不在扫描线程中 sleep 等待反馈 |
| 设备交互 | 输入快照、品质、受控输出请求、反馈 | 权限由接口白名单控制；设备联锁独立保留 |
| 扩展能力 | 新 Host API 和版本化库 | 新协议驱动、硬件操作仍需固件开发和验收 |

有循环并不意味着应当追求“严格图灵完备”。有限内存、有限执行预算的现场系统，不承诺完成无界计算。这里追求的是工程上足够通用的程序结构，以及可预测的拒绝和故障行为。

### 3.2 明确不做的事

- 不直接执行用户提交的原生机器码，不在现场调用编译器并加载任意动态库。
- 不提供 C 指针、union、内联汇编、预处理宏、可变参数和用户线程。
- 不开放文件系统、Shell、网络套接字或任意系统调用。
- 不用 VM 代替继电保护、紧急停机和设备侧最终闭锁。
- 不承诺任意文本程序都能恢复为原来的元器件布局。
- 不把读取成功、图编译成功或离线对拍成功当作现场安全证明。

### 3.3 用策略场景而非语法数量验收

首批场景至少包括：多测点统计与选择、限幅和死区、SOC 约束下的功率分配、时段调节、PI 调节、持续越限确认、设备轮换和带反馈的顺控请求。每个场景都要给出输入点表、状态、输出契约、资源上限和故障用例。

对于通信协议栈、保护级快速响应、无界优化计算或动态加载第三方原生算法，应明确归入固件扩展或独立控制器，而不是通过放宽脚本权限解决。

### 3.4 现场需求如何落到语言和接口

| 策略需求 | 语言需要提供什么 | 运行时或设备还必须提供什么 |
| --- | --- | --- |
| 从几十个测点中寻找最大值、越限数量 | 定长数组、循环、函数、明确的空集合处理 | 点表快照、品质过滤和数据新鲜度 |
| 按 SOC 和额定容量分配功率 | 数值类型、数组、限幅、纯函数 | 单位和正负号、设备能力、功率输出白名单 |
| 多种策略竞争同一 PCS | 状态与优先级表达 | 唯一输出所有者和统一仲裁，而不是最后写入者获胜 |
| 过压持续一段时间后调节 | 有状态功能块、持续时间和死区 | 单调时钟、扫描间隔、许可撤销时的复位规则 |
| 转供、孤岛、恢复并网请求 | 状态机、请求标识、反馈和超时分支 | 已验收的设备侧顺控、保护闭锁、人工许可 |
| 新增一种设备规约 | 稳定的符号绑定和版本化接口 | 新驱动和 Host API 适配；仅增加脚本语法不能完成 |

渡口村现有说明文档可用来提取“优先级、功率方向、稳定确认、反馈和回退”的需求，但不能直接作为本次运行时版本的行为证明。先确认项目、设备和点表版本，再将其中的策略转成测试向量；不直接沿用示例中的容量、阈值或地址。

## 4. 原稿需要修正的结论

原稿“图形＋脚本＋统一执行模型”的方向可以保留，以下表述和路线应调整：

| 原稿表述或本次需要防止的误解 | 本次修订 |
| --- | --- |
| “表达式接近 C 的 80%” | 删除无法核验的比例，改用能力和语义差异表 |
| 依据9月原稿认定过程和跳转都要从零开始 | 配置端已有子过程内联、LoopContinue/LoopExit、SourceMap；仍缺通用运行函数栈 |
| “P0 先在旧引擎补齐所有循环，风险低” | P0 先做兼容核对和安全加固；新循环集中实现到新执行核心，避免重复维护两套语义 |
| “现有结构化区域可直接当完整 IR” | 复用分析和身份映射，不把现有 mutation plan 当自足的类型化程序 |
| “IR 必须能无损反编译回图形” | 保存源工程；只对受支持的结构互转，不可还原部分保留为脚本块 |
| “所有元件 Execute 直接变 FFI” | 按纯计算、有状态、外部副作用分类适配，禁止裸虚表调用 |
| “除零、NaN 策略沿用现状” | 新语义重新定义；保留旧模式不等于固化已发现的缺陷 |
| 把循环超时后的安全处置理解成完整回滚 | 超时能阻止新输出，不能撤销已发动作；安全策略逐输出定义 |
| “热加载原样复用、逻辑零改动” | 保留 Legacy 隔离路径，但安全加固和重载改造需重新验收 |
| “ARM Linux 可以分配内存，所以 VM 无压力” | 以目标板实测资源、抖动、延迟和其他协议业务影响为准 |

原稿关于另一份旧目录“仅一个文件不同、其余 MD5 相同”的说法，本次没有重新逐文件核验，不再作为结论保留。改造只以用户指定的 `LinuxApp/linuxttu` 为基线。

## 5. 推荐架构与技术路线

### 5.1 三种产物分别负责什么

**源工程**保存图形、文本、符号和编辑信息，是用户继续修改策略的依据。**结构化 IR**描述已检查的策略语义，是图形与文本共用的编译输入。**执行包**保存固定格式的指令、类型、资源和接口引用，是设备加载的唯一运行依据。

不能把三者混成一份只有 NextID 的 JSON，也不能指望通过反编译执行指令恢复全部编辑信息。

```text
现有图形 / 新结构化图形 / VCL 文本
                |
                v
        解析、符号绑定和类型检查
                |
                v
          统一结构化语义 IR
                |
      静态分析、资源估算、确定性编译
                |
                v
     执行包：类型 + 指令 + 常量 + 接口 + 源码映射
          |                         |
          v                         v
    主机离线执行                设备独立验证
                                    |
                                    v
                    周期执行 + 状态暂存 + 输出仲裁

存量工程 ----------------> 现有 Legacy 执行路径
```

### 5.2 图形与文本如何共存

简单比较、逻辑和接线继续用图形。复杂计算使用脚本块，脚本块的输入、输出和状态声明形成明确接口。循环、函数和状态机可使用结构化子图，避免把大量回边铺在同一张画布上。

图形块的标识必须稳定，布局和文字说明单独保存。文本中不能图形化的代码保留为脚本块；不要悄悄拆解后丢失变量、注释或语句顺序。

同一段程序只允许一个权威编辑来源。图形编辑生成文本预览；文本编辑需要生成新的结构化节点或保留文本块，不得让两份可编辑源码长期各自变化。执行包过期时必须重新编译，不能继续发送旧指令。

首版 SCRIPT 的接口建议固定如下，不能直接复用现有端口位掩码来冒充数组类型：

| 签名内容 | 图形接口与执行边界 |
| --- | --- |
| 一个标量输入参数 | 一个同类型数据输入，绑定稳定 PortId，不按当前参数排列临时认身份 |
| `in T name[N]` | 一个新定义的定长数组输入，类型含元素类型和长度；不支持该端口的画布/目标明确拒绝 |
| 一个标量返回值 | 一个同类型结果输出；所有返回路径必须产生结果 |
| void 返回 | 无数据结果输出，只结束当前块；效果权限另行声明 |
| SCRIPT 内 return | 只结束当前块调用，图形后继继续；不能跳出所属任务 |
| 任务入口 return | 结束本轮计算，仍经过统一检查和提交 |

首版脚本不能直接写外部运行 ID 或跳到别的图形节点。签名修改必须迁移端口映射并诊断已有连线，不静默按新排列重新接线。

### 5.3 执行后端的选择

推荐先实现最小的类型化解释执行原型，验证语言、接口和资源约束；生产后端是否使用自研 VM，必须通过与成熟受限执行环境的对比评审。无论后端如何选择，源工程、类型规则、Host API 和测试向量都不能依赖某个解释器的偶然行为。

| 路线 | 优点 | 本项目需要付出的代价 | 建议 |
| --- | --- | --- | --- |
| 继续增加普通元器件 | 用户习惯和存量配置容易保留 | 变量、数组和函数难以靠端口连线清楚表达 | 保留为前端，不作为唯一语言机制 |
| 类型化小 VM | 指令、状态、预算和错误较容易按项目定义 | 必须自己维护验证器、执行器和工具链 | 推荐做首个有边界原型，经过测试门槛后再用于生产 |
| WebAssembly 等成熟后端 | 有标准化控制与内存验证机制 | 需实测 ARM 支持、体积、执行开销、调试和 Host API 集成 | 在原型阶段对照评估，不因“成熟”免除现场验证 |
| Lua 等嵌入式脚本 | 生态成熟，嵌入方便 | 动态类型、分配和回收行为需要额外约束 | 不作为默认语义；只有满足同样预算和类型要求时才考虑 |
| 生成原生 C | 便于复用部分算法和离线比较 | 编译工具链、原生代码权限、版本和回滚成本高 | 可作离线参考后端，不作为首期现场执行路线 |

不能用“硬件能 malloc”推出“运行 VM 没有压力”。原型必须报告程序大小、峰值内存、启动和重载时间、扫描延迟、Host API 最长耗时以及设备其他业务受影响的程度。

## 6. 实施前必须固定的语义

本节定义**推荐的新语义**，统称 VCL（Visual Control Language）。VCL 不是现有 `eval.c` 的别名，也不是 ISO C 实现；版本变化必须可识别。Legacy 保留单独的导入和执行模式，不默认按新规则解释。

### 6.1 首个生产子集

首版保留 C 风格的语句组织，但有意减少容易混淆的副作用写法：

| 分类 | 核心能力 | 约束 |
| --- | --- | --- |
| 类型 | `bool/i32/u32/i64/u64/f32/f64` | 平台未实现的类型按能力检查拒绝，不映射成 double |
| 数据 | 常量、局部变量、周期变量、任务状态、一维定长数组 | 类型和数组长度编译期确定 |
| 表达式 | 算术、比较、逻辑、无符号位运算、纯函数调用 | 表达式内部禁止赋值和外部写入 |
| 语句 | 声明、赋值、块、if/else、switch、for、while、do/while、break、continue、return | 每个循环有上限，每条路径受任务预算约束 |
| 过程 | 无递归的纯函数、有状态功能块 | 不开放用户函数指针或间接调用 |
| 领域交互 | 声明式输入、参数、时间、功能块、输出意图 | 只能调用版本化白名单接口 |

开发原型可先只实现 `bool/i32/u32/f64` 和基本分支，但不得提前宣称已经交付完整核心能力。`struct`、枚举、二维数组和受限字符串按后续阶段增加。

首版不需要 `++/--`、链式赋值、逗号运算符或表达式内赋值。使用 `i = i + 1;` 不会降低算法表达能力，却能减少隐含执行顺序。将来如加复合赋值，先限定为语句语法，并沿用同样的检查规则。

### 6.2 类型、转换与算术

1. `bool` 只能是 true/false，条件必须为 bool。数值需显式比较，不能沿用旧 IF 的 `>0.5` 判真规则。
2. 整数宽度固定，不依赖 C 的 `long`。位运算首版仅接受 `u32/u64`；右移为逻辑右移，不开放有符号移位歧义。
3. 不同类型不做隐式混合算术。调用和赋值要求类型匹配，或在源码中显式转换，例如 `f64(count)`。未标类型的字面量只在唯一明确的类型上下文中确定类型；歧义报错。
4. 同类型整数除法向零截断：`i32(5)/i32(2)=2`，`i32(-7)/i32(2)=-3`。余数满足 `a=q*b+r`，符号与被除数一致。浮点运算必须显式使用浮点值。
5. 整数加减乘和有范围变化的转换采用检查语义：溢出报错，不静默回绕或饱和。确需位模式回绕时，后续提供名字明确的专用内建，不复用普通 `+`。
6. 整数除零、最小有符号整数除以 `-1`、负下标和越界转换报错。浮点转整数向零截断，先检查有限性和可表示范围。
7. 浮点按 binary32/binary64 配置档案实现；非有限输入或结果默认产生运行错误，不传播到状态和输出。下溢、次正规数、舍入和乘加融合规则必须在目标档案中固定；没有一致实现证据时不开放依赖这些边界的算法。
8. 移位量要求 `0 <= n < 位宽`；左移丢失高位时按检查算术报错。需要截断移位时使用另一个明确命名的内建。

浮点不会因为统一类型名而自动逐位一致。基础算术应固定求值和舍入规则，禁用改变语义的 fast-math 和未经规范允许的融合；超越函数须区分“固定算法可逐位比较”和“已声明容差”。容差必须来自各函数测试和控制误差要求，不能统一写一个任意小数。

### 6.3 表达式顺序、短路和数学函数

- 普通二元操作数和函数实参从左到右计算。
- `&&/||` 短路；三元条件如后续加入，只计算选中的分支。未执行分支仍需通过静态语法和类型检查。
- 表达式不能写变量、RTDB 或设备；赋值仅作为语句。纯函数不能隐藏 I/O 或功能块更新。
- 函数声明记录参数个数、类型、单位、返回类型、定义域和错误；数学库名字区分大小写。
- 新数学接口使用明确单位，例如 `sin_rad` 与 `sin_deg`，不把旧函数的偶然换算规则当约定。
- 常量折叠与运行时必须调用同一语义实现或同一验证向量。常量声明、数组长度和 case 等必须常量求值的位置，求值失败则编译拒绝。普通表达式中，只有按语言顺序必然求值的常量子式才提前报告求值错误；静态已知不会执行的短路/条件分支不求值，但仍检查语法、符号和类型。该规则独立于是否启用优化。

例如 `false && (i32(1)/i32(0) > i32(0))` 合法且为 false；`false && unknown_name()` 仍因符号不存在而拒绝。编译器不得通过折叠把前者变成编译错误，也不得把可能执行的错误子式悄悄删除。

运算符优先级可按 C 的常见子集定义，但必须随语法版本固化；`^` 一直表示位异或，乘方使用函数。VCL 的赋值语句不参与表达式优先级。

### 6.4 作用域与生命周期

| 对象 | 生命周期 | 初始化和故障行为 |
| --- | --- | --- |
| `local` | 一次函数或脚本块调用 | 读取前必须初始化；非 void 函数所有可达返回路径赋值 |
| `cycle` | 一个任务扫描 | 每轮按声明初始化，不跨轮保持 |
| `state` | 一个任务或功能块实例 | 加载、显式复位时初始化；正常跨轮保留；执行先写工作副本 |
| `retain` | 跨进程或设备重启 | 默认不启用，后续以持久化能力单独批准 |
| 只读常量/参数 | 当前程序代次或参数版本 | 周期开始冻结版本；不得执行中被后台线程任意改写 |

同名变量遮蔽首版禁止或作为错误处理，以免现场审阅错认。任务私有状态禁止其他任务直接访问；公共数据通过只读快照或版本化邮箱交换。函数库复用代码，不共享隐含全局状态。

`retain` 不等于给每次赋值写文件。需要定义检查点频率、闪存寿命、断电一致性、schema 变更、恢复失败默认值和人工复归，完成后才可启用。

### 6.5 数组与函数

数组长度是正的编译期常量，容量计入资源预算；常量越界编译拒绝，动态下标每次检查。数组不能隐式退化为 C 指针。

建议首版采用：标量按值传参；定长数组使用只读 `in` 视图；返回一个标量。可写数组参数、切片和结构体返回等在确有需求后扩展，并提前定义别名和复制成本。只读视图只能在本次调用内使用，不能存进 state 或返回给调用者。

函数的调用图必须无环，禁止直接和间接递归。库代码随工程固定版本和内容摘要；运行时不按名称临时下载代码。跨任务复用相同纯函数只共享不可变代码。

### 6.6 分支和循环

- `switch` 只接受整数或枚举；case 是编译期同类型常量，值唯一。首版禁止隐式 fall-through，每个 case 必须明确结束或 return；default 必须存在或编译器生成确定的空分支。
- `for` 严格按“初始化一次→条件→循环体→迭代→条件”执行。
- `continue` 在 for 中先到迭代段，在 while 中到条件段，在 do/while 中到尾部条件段；`break` 结束最近的循环或 switch。
- `do/while` 至少执行一次，条件每轮重新计算，不能用旧输入端口缓存冒充重新求值。
- 动态循环需要显式最大迭代次数。首次循环条件为假不是故障；达到上限但仍需继续时产生 `LOOP_LIMIT`，不偷偷把它当正常 break。
- 不提供任意 goto。状态机和结构化的 break/continue 足以覆盖首批策略；如确需跳转，只允许经过分析的结构目标。
- `return` 离开当前函数；任务中的 `return;` 结束本轮计算并进入共同提交/故障检查，不绕开运行时清理。

### 6.7 有状态功能块不等于普通函数

定时器、PI、积分和变化检测需要实例身份、内部状态、初始化和复位契约。建议首版规定一个实例一轮最多 step 一次；重复调用报错，而不是隐式积分两次。多个独立用途应声明多个实例。

实例每轮是否调用、未使能时保持还是复位、跳过时是否继续计时，应由调用参数和功能块契约明确表达。新功能块使用任务提供的单调时间和受检 `dt`，不自行读取墙钟或假设名义周期已经过去。

积分方法、抗饱和、死区、首次采样、异常 `dt`、输入品质失效和复位都要有独立用例。不能用 PI 内部积分存在来证明独立积分元件的运行契约已经实现。

时间基线也必须明确：任务 dt 取本轮实际开始与上一实际开始之差，首次按已声明初始化策略处理；它是调度诊断，不随算法状态回滚。积分等实例 dt 取本次 step 与上次成功提交的实例采样时间之差，首次只建立基线、不累计；该采样时间与实例状态一起提交或丢弃。

若两次调用间隔超过实例 `maxDt`，默认不补算整段历史，而是本轮报 `INVALID_DT`、请求显式复位；复位后的首轮重新建基线。需要补积分、冻结或按真实持续时间计时的功能块必须分别声明，不能共用一个隐含规则。持续定时器使用已提交起始时间与单调 now 比较；漏轮后可在下一次合法调用观察到期，跳过调用时的 enable/复位规则仍按该实例契约执行。

## 7. 源工程、IR 与执行包

### 7.1 工程源必须完整保存

沿用当前“工程原图与运行投影分离”的基础，新增脚本源、语言版本、符号表、库依赖和类型声明。现有未知字段保留、白名单反序列化和克隆路径应继续使用；不要重新调用有损的旧式逐字段复制方法。[H3、H10]

工程文件允许保存未编译成功的源码，状态为 draft。运行导出必须重新编译当前源与目标能力，不能把历史 `ready` 或上一轮平面缓存当作当前程序。工程文件和执行包禁止覆盖同一路径。

源码映射需要扩展为：

```text
源摘要 + 任务/画布/元件/端口/脚本字节区间
    -> 结构化 IR 节点与调用实例路径
    -> 函数编号和指令区间
```

映射是多对多的。内联、辅助节点和优化消除都要保留生成角色；不能将指令 PC 塞进现有 `RuntimeElementId`。只有执行包而没有源工程时，最多提供只读派生视图。

### 7.2 统一 IR 记录的是语义，而不是数组位置

建议至少包含以下对象：

- `Program`：语言和语义版本、目标能力、常量、类型、任务与函数。
- `Symbol`：稳定身份、类型、作用域、生命周期和初始值。
- `Expression`：已绑定符号、运算类型、纯函数签名和源码位置。
- `Region`：顺序、条件、switch、循环、脚本和功能块调用。
- `Loop`：首次入口、条件、循环体、迭代段、回边、出口和次数上限。
- `Effect`：读输入、更新实例、生成输出意图等具有先后关系的操作。
- `SourceOrigin`：来源画布、元件、脚本区间和生成角色。

前端先生成结构化表示，后端再展开为基本块和显式终结指令。控制流和数据依赖分别分析；禁止把数据连线直接视为执行边。纯计算可以按依赖复用，有状态和副作用调用不能为了满足拓扑序被复制或提前执行。

分支合流时，每个本轮需要的值必须在所有可达前驱上赋值；否则报错。确需跨周期值时显式读取 state，不把“该元件在线性列表中靠前”当作本轮有效的证明。循环条件和更新的数据依赖按迭代重新计算。

### 7.3 执行包的内容和版本

建议首期使用可读 JSON 容器，指令对象采用数字索引和已定义的操作码；后续再增加二进制编码。逻辑结构相同，不能直接把 C 结构体内存写盘。

下列是**建议的容器结构示意，不是完整可执行包，也不符合现有旧加载器格式**：

```json
{
  "Format": "vcl-executable",
  "SchemaVersion": "1.0",
  "LanguageVersion": "vcl/1",
  "SemanticVersion": "vcl-semantics/1",
  "BytecodeVersion": "vcl-bc/1",
  "HostApiVersion": "control-host/1",
  "TargetProfileId": "offline-reference",
  "RequiredCapabilities": ["bool", "i32", "u32", "f64"],
  "SourceDigest": "",
  "CompilerVersion": "",
  "Constants": [],
  "Functions": [],
  "Tasks": [],
  "Bindings": [],
  "ResourceRequirements": {}
}
```

正式 schema 必须规定必填项；上述空值仅用于展示字段，真实包不能以空版本、空入口或缺失摘要通过验证。执行包摘要放在发布清单中，覆盖确切文件字节；如果另有语义摘要，应单独标识，不定义一个循环包含自身的哈希字段。

工程 schema、语言、语义、字节码、Host API、元件契约、编译器和固件 build 分别管理。完整性摘要防止字节损坏；发布者认证和执行授权由受控发布渠道或签名策略实现，不能以 MD5 相同替代。

数值和索引编码建议如下：

| 内容 | 推荐约定 |
| --- | --- |
| opcode | 固定编号，编码宽度 u16；保留和未知编号拒绝 |
| 函数、槽、常量、指令索引 | u32；实际数量由 Profile 限制 |
| 小整数和资源数量 | JSON 整数，严格校验类型与范围；不接受小数、布尔或数字字符串冒充 |
| i64/u64 常量 | 带类型的规范十进制字符串，不能经 double 中转 |
| f32/f64 常量 | 带类型的规范十进制文本，按目标类型直接解析；拒绝非有限值 |
| 内部时间与累计值 | 受检 u64；JSON 如需携带完整 u64，使用专用字符串字段 |
| 程序结束 | 显式 RET/TASK_END；不复用负 NextID 哨兵 |
| 源身份 | 稳定 ID，与执行期稠密编号分开 |

例如 `{"type":"u64","value":"18446744073709551615"}` 必须精确保留。即使 VM 支持 u64，RTDB 绑定端若只能表示 float，也应拒绝不兼容绑定或要求显式的有损转换，不承诺端到端精度。

### 7.4 指令集不按图形元件逐个照搬

推荐以类型化栈机作为首个实现：局部槽和状态槽承载跨块值，基本块边界操作数栈为空，便于验证。指令按下列类别定义，不预先承诺“约 20 条”：

- 常量、局部槽和工作状态的读写。
- 类型化算术、比较、逻辑和受检转换。
- 条件/无条件分支、静态函数调用、返回和任务结束。
- 定长数组读写和下标检查。
- 输入快照读取、功能块 step 和输出意图生成等受控宿主操作。

IF、switch、for、while、do/while 可展开成基本块，不必每种结构都有专属 opcode。循环界限和任务预算由 VM 强制检查，不能靠用户程序主动调用 CHECK 才生效。

### 7.5 设备加载器独立验证

加载器应按顺序验证，任一失败都不进入激活阶段：

1. **容器**：文件大小、编码、JSON 层级、重复键、尾随内容、字段类型、字符串字节数和数量上限。超限拒绝，不截断。
2. **版本与能力**：必需版本、类型、opcode、Host API 和目标产品匹配。未知必需能力拒绝，不能忽略后继续执行。
3. **解码与引用**：完整解码并建立指令边界，所有跳转都位于本函数的合法指令起点；函数、常量、槽、实例和绑定索引存在。
4. **类型和数据流**：传播每条路径的栈类型，检查欠栈、超栈、返回类型和局部变量确定赋值；合流时类型一致。不可达指令首版拒绝，由编译器先删除。
5. **调用和循环**：调用图无递归，计算调用深度与峰值帧；验证循环界限及所有回边路径的计量，调用不能重置父任务预算。
6. **资源**：受检计算数组、栈帧、状态、输入快照、写集、指令和队列需求，避免长度乘加溢出；分配失败完整释放候选。
7. **接口和权限**：解析最终点位、单位、写入范围、回调白名单、任务写者和冲突；初始化/校验禁止外部动作。

静态验证通过后，执行器仍检查数组索引、运行时除零、整数溢出、预算、代次句柄和输出许可。即使执行包不是本项目编译器生成，也不能绕开这些规则。

### 7.6 VM 内存和错误结果

加载和准备阶段可以有受限分配；扫描期间不得 malloc、扩栈或增长容器。所有工作槽、调用帧、实例状态和写集在激活前计算并分配上限。C 执行器使用带标签或由验证器保证类型的值槽，不用一个 double 保存全部整数。

失败结果至少包含 `generation/task/cycle/function/pc/source/error`。建议错误类别包括 `TYPE_MISMATCH`、`BOUNDS`、`DIV_ZERO`、`NUMERIC_OVERFLOW`、`LOOP_LIMIT`、`STEP_BUDGET`、`DEADLINE`、`STALE_INPUT`、`DENIED`、`QUEUE_FULL`、`HOST_FAILURE`。错误对象与数值分离，不能用 NaN 同时表示合法数据和失败。

故障默认中止本轮，丢弃尚未提交的算法状态和输出意图；诊断与故障计数仍保留。下一轮是否自动重试、连续失败多少次停用由任务策略定义。带动作的故障不能不核查请求状态就从入口盲目重试。

## 8. 周期执行、状态和设备输出

### 8.1 输入快照和品质

每次执行绑定不可变的输入快照，至少记录 `snapshotId/cycleId/parameterVersion`。点值携带品质、源采样时间（如可取得）、本机单调接收时间和更新序号。执行中读取同一快照，不让 HostCall 偷偷重读最新 RTDB。

RTDB 可采用有界读锁、版本副本或有限次数的版本校验来构建快照。取不到一致数据时本轮失败，不能无限自旋。**同一 RTDB 发布版本不代表现场同时采样**，策略仍需限制最大陈旧时间和点间采样时差。

旧接口缺少品质或源时标时，明确标为 UNKNOWN；不能用本次读取时刻伪造采样时间，也不能把读取失败的默认 0 当有效测量。输入失效按点位契约拒绝、降级或使用已批准替代值。

### 8.2 调度和时间

新模式按单调时钟的绝对释放点调度：`r(k)=r(0)+k*T`。同一任务不重入；上一轮未完成时，首版默认跳过过期节拍，累加 `missedTick`，不连续补跑历史轮次。若后续支持最多合并一轮，也必须是显式选项。

单调时间用于预算、超时、持续时间、输入陈旧和积分 dt；RTC 用于日程与审计。校时前跳或回拨不能改变 VM 的执行预算。日程在校时后的重复/跳过行为另行配置。

可以先保留每任务一个线程，不必同时改为全新调度框架；但周期等待应可唤醒，同任务的执行互斥、预算和取消必须统一。Legacy 的轮末等待作为独立兼容模式，不能无提示改成固定周期。

### 8.3 单轮执行和提交

建议的新路径为：

```text
取得输入/参数快照
  -> 初始化 cycle/local，建立 state 工作副本
  -> 执行计算和功能块 step，生成输出意图
  -> 检查预算、品质、数值、权限和输出冲突
  -> 接受状态更新、内部输出和命令记录
  -> 异步发送获准的命令
  -> 在后续周期读取发送/确认/失败反馈
```

提交前失败时，丢弃工作副本和未接受意图；已记录的诊断不会丢弃。提交后驱动失败时，不能删除“曾经接受/发送”的事实。算法状态、命令队列和动作账本需在明确的宿主提交边界保持一致；如果跨介质无法原子提交，必须定义崩溃后的对账规则。

旧 `Execute` 已经修改 privateData 或发动作的路径不能享受这项事务承诺。首期应标为兼容行为，不进入“提交前零副作用”的新执行档案，直到逐类改造完毕。

### 8.4 宿主接口分三类

Host API 是 VM 能调用的、由固件提供的白名单接口。它不是开放任意 C 函数的入口。

| 类别 | 典型操作 | 契约 |
| --- | --- | --- |
| 纯计算 | 数学、限幅、格式受限的数值处理 | 无外部读写，耗时有界 |
| 有状态实例 | PI、定时、积分、变化检测 | 句柄含代次和类型版本，同实例串行，读工作状态 |
| 外部效果 | RTDB 写、YK/YT 请求、参数持久化、日志 | 分别授权，有界暂存或入队，明确返回与最终确认 |

句柄不能是裸指针；销毁和重载后旧代次失效。接口描述应记录参数/返回类型、单位、实例状态大小、最大调用次数、效果类别、错误和成本等级。

已有 `Execute(t_LogicElement*)` 依赖 `ptFirst`、连接索引和 privateData；只给它调用 SetInput 不一定能改变真实输入。可提取纯计算内核复用，但要为依赖图或立即副作用的元件编写适配器。[R6]

### 8.5 非阻塞命令和结果未知

新命令接口只做有界校验与入队，返回 requestId，不在扫描线程里等待设备。队列满明确拒绝；日志可按已声明策略丢弃并计数，设备命令不可静默覆盖。

动作状态至少区分：

```text
NOT_SENT -> ACCEPTED -> SENT
ACCEPTED -> FAILED       （能证明尚未发送）
SENT -> CONFIRMED        （明确成功反馈）
SENT -> FAILED           （明确失败反馈，另记录是否部分完成）
SENT -> UNKNOWN          （已发送但无法确认结果）
UNKNOWN -> 确定结果      （通过反馈或对账确认，不盲目重发）
```

接收、发送和现场完成是不同状态。取消只能可靠删除尚未发送的请求；已发送动作需要设备反馈或另行审批的补偿。没有设备侧幂等支持时，不承诺“恰好一次”。

现有 YK 可能直接调用 `CommonYkOperation`，YT 可能通过回调写文件、等待或重复发送；表达式也能写 RTDB。影子模式和撤权必须覆盖这些出口，不能只替换 `g_DataInterface`。[R6]

不可中断的原生回调放进有界工作池，也不会因此变成可取消。长时间不返回的调用要隔离或禁止，不允许无限增加线程来维持表面可用。

### 8.6 输出所有权、仲裁和安全策略

默认一个物理控制对象只有一个获权写者。跨任务、跨链路、实时库别名以及其他控制程序的同点写入都要识别；若只管理 VM 内写者，必须明确这不是全系统仲裁。

需要多个策略时，先生成各自意图，再由唯一仲裁器按明确优先级和有效期选择。冲突默认拒绝并告警，不使用“最后到达者胜”。人工/远方/就地模式和保护闭锁以设备及业务规约为准。

每个输出必须规定：单位与方向、正常范围、变化速率、所有者、许可、有效期、冲突行为、反馈、通信失效行为、保持时限和安全策略。**安全态不一律为零**：有的设定值需受控降额，有的请求应禁止新动作，有的设备应转自身安全模式。

VM 超时、进程退出或网络中断不能保证安全命令送达；设备侧必须有独立失联策略和闭锁。保护跳闸、并离网切换、黑启动等高风险动作首期只开放到已验收的顺控请求接口。

### 8.7 资源和时间预算

至少配置并由固件限制：最大执行步骤、单轮截止时间、循环次数、调用深度、操作数栈、局部/状态/数组内存、HostCall 次数、输出意图数、日志字节和队列容量。嵌套调用共享整轮预算，不重新领取额度。

指令数预算提供可重复的计算限制，时间预算发现系统过载；两者都需要。时间检查的响应速度仍受最长不可中断步骤限制，不能用外包计时保证阻塞 C 调用中途返回。

预算方法可用下列关系，数值必须在目标平台测量后填写：

```text
单任务预算 = 快照成本 + 最大步骤数 × 步骤成本预算
           + HostCall成本 + 提交/审计成本

峰值内存 = 基础运行时 + 活跃程序 + 候选程序 + 必要回退对象
         + 快照 + 工作状态 + 队列 + 线程栈 + 余量

端到端延迟 = 采集 + 等待下一轮 + 调度/计算 + 仲裁/排队
           + 传输 + 设备完成时间
```

单核必要容量检查可以看 `Σ(Ci/Ti)`，但利用率小于 1 不是截止期证明。普通 Linux 的调度、中断、共享锁和驱动等待仍需实测及系统分析。不要把 VM 的平均执行耗时当作现场动作上界。

## 9. 双端改造与兼容

### 9.1 C# 配置端接入点

以下新增模块名称只是建议，现有路径是本次核查的接入位置。

| 工作项 | 现有接入位置 | 交付要求 |
| --- | --- | --- |
| 脚本源、变量和库模型 | `Models/Editor/`、`EditorDesignModel`、共享序列化器 | 保存完整源码、稳定身份、语言版本和未知扩展；新类型纳入项目和 binder 白名单 |
| SCRIPT 元件和属性编辑 | `Elements/ElementFactory.cs`、`ElementModel` 枚举、契约目录、编辑器 | 显式签名生成端口，禁止只增加枚举而没有目标支持检查 |
| 前端与类型检查 | `ExpressionSyntax`、`ExpressionParser` 旁新增语句/类型模块 | 旧表达式模式与 VCL 模式分开；复用诊断位置，不强行扩展旧 evaluator 语义 |
| 图形到语义 IR | `HierarchicalCompilationService`、`RuntimeGraphBuilder` | 从源副本导入，保留子过程和结构身份；不直接篡改权威原图 |
| 新后端和映射 | `CompilationInfo`、`SourceMap` | 增加函数/PC/脚本区间、类型和资源统计，所有依赖参与摘要 |
| 保存与导出 | `EditorProjectSaveService`、`RuntimeConfigAdapter` | 源保存允许 draft，部署重新检查；旧和新执行包独立选择 |
| 离线运行与调试 | 建议 `Services/Simulation/` | 注入快照、时钟、命令 stub；按 cycle 查看变量、状态和意图 |

仿真可以先使用 C# 语义解释器，同时把 C VM 编成隔离的桌面测试宿主重放同一执行包。双端各自实现会产生漂移，共享一份文法也不能解决全部问题；需要共享类型/操作/函数签名表、机器可读向量和跨实现对拍。

调试界面至少显示源码位置、循环计数、预算剩余、输入品质、当前状态和未提交输出。在线现场只读追踪为默认；暂停任务、单步、改状态和强制输出只能在明确的离线或维护模式下开放。

### 9.2 C 运行时接入点

建议新增 `src/logicengine/vm/`，遵循当前 C99 和产品编译约束，按模块边界实现：

| 建议模块 | 职责 |
| --- | --- |
| `vcl_package` | 读取不可变包，检查 schema/能力/大小并管理候选所有权 |
| `vcl_verify` | 指令、类型、控制流、调用、资源和绑定验证 |
| `vcl_vm` | 类型化执行、边界检查、共享预算、错误与取消 |
| `vcl_state` | 实例状态、工作副本、复位和受控迁移 |
| `vcl_host` | 快照、时间、功能块和效果白名单 |
| `vcl_effects` | 输出所有权、意图队列、代次撤权、动作账本 |
| `vcl_lifecycle` | READY 屏障、激活、健康观察、停止和回收 |

`logic_visual_programming.c` 保留规约入口、文件发布监听和 Legacy 分派，但不能把头文件中尚未实现的 `LogicEngineV2_*` 生命周期声明当成现成可调用接口。新增源码需同时进入实际产品构建；不能只在源码目录新增文件就认为固件已包含它。

### 9.3 单任务单执行引擎

首版同一任务要么走 Legacy，要么整体编译到 VCL VM。不采用“旧 NextID 走到 SCRIPT 后临时进 VM 再返回旧链”的方式，否则快照、状态、错误和预算会跨两套执行器，难以验证。

不同任务可以在新版固件显式分派到不同引擎，但必须共享输出仲裁和代次管理。指定旧固件没有这个新契约，不能通过添加一个会被忽略的 Engine 字段假装兼容。

### 9.4 目标能力与有限降级

部署前取得目标能力清单，至少包含实际固件 build、支持的 Type/元件契约、语言/字节码版本、数值和时间语义、Host API、资源限制和循环安全能力。离线 Profile 是声明，合成测试数据是测试桩，只有对应目标的验证记录才是设备证据。

旧固件不检查新版本字段，因此推荐新执行包采用明确的格式标识和独立分派入口；在完成固件识别前，不向旧 `c%02d57.json` 混入新执行语义。正式文件名、路径和规约发布方式在 P1 确认，不在文档里擅自占用新规约号。

降级只开放可证明等价的白名单。例如简单无状态数值块可以在相同类型、顺序和异常规则下尝试生成旧元件；含数组、函数状态、不同短路语义或无法保持效果次数的代码应拒绝旧目标部署。保留工程草稿，不静默近似、不删除不支持节点。

### 9.5 Legacy 的保留与修复

保留 Legacy 是维持已验收策略行为，不是永久保留缺陷。优先修复动态目标验证、索引前检查、超限截断、表达式构建失败仍接受、停止和副作用隔离等问题；每项修复都要说明行为变化并跑存量样例。

若实际交付急需某个旧循环元件，可以作为独立兼容项目：先固定语义和预算，再从统一 IR 做目标后端。它不应成为新核心上线前必须完整实现所有旧循环的前置条件。

## 10. 热加载与故障恢复

### 10.1 候选准备与激活分开

建议重载状态机如下：

```text
ACTIVE -> PREPARING -> READY -> QUIESCING
       -> ACTIVATED_OBSERVING -> COMMITTED

失败 -> REJECTED / ROLLBACK / ISOLATED_FAULT
```

各阶段含义：

1. **PREPARING**：统一发布入口排队；每次使用独立快照或一次读入的不可变字节，摘要覆盖真正解析的内容；完成纯校验和受限分配。
2. **READY**：候选线程/任务完成绑定与启动握手，停在屏障，无任何外部输出权限。第 N 个任务创建失败时只清理候选。
3. **QUIESCING**：旧版本在扫描安全点暂停，处理在途请求，导出允许迁移的状态；旧对象暂不销毁。
4. **ACTIVATED_OBSERVING**：在统一同步边界切换 activeGeneration 与输出授权代次，再放行候选；检查首轮完成、品质、队列、预算和命令结果。
5. **COMMITTED**：观察达到批准条件后记录为 last-known-good，最后释放已确认无人引用的旧对象。

这里能承诺的是程序和输出授权的确定切换点，不是多台设备物理动作同时发生。旧代次已发往设备或驱动的请求必须另行对账，不能仅凭 generation 变化就当作不存在。

### 10.2 停止超时不能靠强杀掩盖

扫描等待采用可唤醒的单调计时等待；设置 quiesce/stop 截止时间。停止超时后，不释放仍被线程引用的对象，不覆盖其所有权，不用 `running=false` 伪装停止成功。

不能确认旧版本静默时拒绝正常激活并报告隔离故障。已统一出口可以撤销后续发送权限，但仍不能撤回在途动作；存在绕过闸门的旧调用时，应转维护停机，不能宣称可安全热切换。不得用未经验证的线程强杀代替资源生命周期管理。

### 10.3 状态迁移规则

按稳定任务/实例身份、类型、状态 schema 和相关配置摘要判断是否可迁移，不按新旧执行数组下标匹配。禁止 `memcpy(privateData)`，其中可能混有指针、句柄、配置和历史。

| 状态 | 推荐迁移规则 |
| --- | --- |
| 纯计算临时值 | 不迁移，下一轮重算 |
| PI/积分 | 配置兼容时迁移有效数值；限幅/系数变化按明确规则修正或复位 |
| 边沿历史 | 点位与触发语义兼容才保留；否则重新建基线且首轮抑制动作 |
| 定时器/采样窗口 | 定义暂停期间计时是否继续；不跨系统重启复用旧单调时间坐标 |
| 请求与反馈 | 保留独立动作账本，不能随脚本状态丢弃 |
| retain | 按持久化 schema 迁移，失败进入已批准的复位/人工恢复路径 |

首个现场版本可以不支持通用状态热迁移，但必须明确“重载复位＋维护窗口”，不能在未实现前承诺无扰切换。

### 10.4 回退与掉电恢复

激活前失败丢弃候选，恢复旧版本的暂停状态。激活后失败先撤新版本权限，再检查设备状态和在途动作，判断旧状态是否仍可用；必要时重新建基线、限幅或人工接管。

持久保存已确认执行包、上一版本和激活记录。区分“准备中”“已激活未确认”“已确认”，定义每个写盘与内存切换窗口掉电后的处理。损坏、状态不兼容或动作结果未知时进入受控停用，不因目录中某个 JSON 更新较新就自动运行。

inotify 作为触发器，还需有界重试、watch 重建和周期对账。先建立监听再初次对账，避免初始化窗口漏更新。当前 MD5 只做变化检测；新版发布鉴权、完整性和代次身份另外处理。

## 11. 示例与测试

所有目标语言和执行包示例都应明确标注“建议格式，当前版本不能直接运行”。不将设计示例保存为现场配置，不使用猜测的点位和遥控地址。

### 11.1 顺控必须跨周期推进，不能在循环里等待

以下是**目标行为模型**，不是当前元器件配置，也不包含真实遥控地址：

```text
IDLE
  总许可、通信品质和设备健康连续满足确认时间
    -> 发布一次带 request_id 的顺控请求 -> WAIT_FEEDBACK

WAIT_FEEDBACK
  收到匹配 request_id 的成功反馈 -> COMPLETE
  收到失败反馈或等待超时 -> FAULT
  许可撤销 -> 发布撤销请求 -> CANCEL_PENDING

CANCEL_PENDING
  收到撤销确认 -> IDLE
  超时或无法确认 -> FAULT，并要求人工处置

COMPLETE
  按设备约定保持状态；明确复归条件成立后 -> IDLE

FAULT
  撤销本策略许可、记录原因；满足授权复位条件后 -> IDLE
```

每次扫描只计算一次状态迁移，不在 VM 内反复读取实时库等待反馈。延时和设备完成时间不是同一概念：发送成功只能说明请求已被接收，不能说明开关已经动作或设备已经切换模式。

撤销也不等于已撤回。设备可能已经开始执行，或者撤销请求也在途中。状态机必须能表达“结果未知”，不能在超时后自动重发相反动作。

### 11.2 验证要分层，不能用一个通过标记代替

1. **工程文件验证**：确认读取、保存、再打开不丢图形、符号和代码。
2. **编译验证**：确认语法、类型、控制流、资源分析和目标能力检查。
3. **执行包验证**：直接提交伪造或损坏的包，确认设备端独立拒绝；不能只测试上位机生成的合法包。
4. **语义对拍**：对固定输入、时间和反馈序列，比较状态、输出意图、错误、执行次数，而不只是最终数值。
5. **接口适配验证**：用影子实时库和模拟命令队列验证实际 C 适配层；纯 VM 测试替代不了它。
6. **目标设备验证**：测量资源和扫描延迟，覆盖通信中断、线程停止和重载失败。
7. **现场分步验收**：核实点表、量纲、极性、闭锁、反馈和人工回退。

每一层记录版本、用例、预期、实际、失败项和证据文件。下层通过不能自动授予上一层的通过结论。

### 11.3 建议的现场交付包

- 可编辑源工程、执行包和两者的哈希；明确编译器、语义版本和目标固件能力。
- 策略说明：场景优先级、启动与退出、死区、时延、状态迁移和异常分支。
- 最终点表：符号、地址、单位、缩放、极性、品质、新鲜度和输出权限。
- 输出契约：默认状态、保持条件、超时、撤销、回读、冲突仲裁和责任控制器。
- 已执行的离线、影子、设备和现场验证记录；未执行项必须列出。
- 投运和回退步骤；保存上一份可用源工程、执行包和必要状态快照。

### 11.4 分步投运

1. 在离线环境编译并对拍，所有控制接口使用模拟实现。
2. 在目标设备影子运行，只计算和记录输出意图，不发布实际命令。
3. 将输入绑定到最终点表，逐项核实单位、功率方向、遥信极性和品质。
4. 保持输出禁止或限幅为经批准的试验值，验证反馈、许可撤销和超时。
5. 经现场授权后，逐项开放普通调节；高风险顺控只开放到已验收的请求接口。
6. 观察期间发生方向错误、关键反馈缺失、超时或异常输出时，先撤销输出许可，再按设备契约回退。不能假设旧配置恢复后设备会自动恢复原状态。

回退测试必须在投运前完成。需要验证的不只是“旧文件能读”，还有旧程序能否接管当前设备状态、是否会重复发送启动命令，以及哪些过程必须人工复位。

### 11.5 目标脚本：四台设备按可用容量分配功率

下例是**建议的 VCL 目标语法，不是现有软件可执行代码**。它是无副作用的 SCRIPT 函数：图形输入负责提供同一轮经过品质检查的数组，图形输出将计算结果交给仲裁器；函数本身不读取 RTDB、不发遥调。

约定：`in T name[4]` 是只读定长数组视图；`local` 为调用局部变量；`@max_iterations(4)` 表示循环最多执行四次；`i32/f64` 是显式类型和值转换。输入数值需有限，功率同为 kW、非负；只演示单方向分配，不擅自规定现场充放电正负号。

```c
function f64 allocate_one(
    i32 selected,
    f64 request_kw,
    in f64 capacity_kw[4],
    in bool available[4])
{
    if (selected < i32(0) || selected >= i32(4)) {
        return f64(0);
    }
    if (request_kw <= f64(0)) {
        return f64(0);
    }

    local f64 total_kw = f64(0);
    local i32 i = i32(0);

    @max_iterations(4)
    for (i = i32(0); i < i32(4); i = i + i32(1)) {
        if (!available[i] || capacity_kw[i] <= f64(0)) {
            continue;
        }
        total_kw = total_kw + capacity_kw[i];
    }

    if (total_kw <= f64(0)) {
        return f64(0);
    }
    if (!available[selected] || capacity_kw[selected] <= f64(0)) {
        return f64(0);
    }

    local f64 accepted_kw = request_kw;
    if (accepted_kw > total_kw) {
        accepted_kw = total_kw;
    }
    return (accepted_kw / total_kw) * capacity_kw[selected];
}
```

集成时还需定义超总功率、负容量、总和溢出、最大变化速率和设备拒绝后的重分配策略。图中配置四个调用块，分别固定 selected 为0～3；每个块只有一个标量结果输出，不是一个标量签名自动生成四个输出。这种小规模重算不需要共享可写数组参数。

纯函数输入向量可先这样验收：

| 容量 / 可用 | 请求 | 预期 |
| --- | --- | --- |
| `[10,20,30,40]` / 全可用 | 50 | 四台分别 `5,10,15,20` |
| `[10,20,30,40]` / 全可用 | 150 | 限制为总计100，各台不超容量 |
| 任意容量 / 全不可用 | 50 | 全为0，输出层仍核查其安全策略 |
| `[10,20,30,40]` / 仅第0、1台可用 | 30 | `10,20,0,0` |
| 任意 / 含 BAD 品质 | 任意 | 调用前由快照校验拒绝或走已批准降级，不把 BAD 改成有效0 |

此示例体现数组、循环、continue、函数、类型和边界处理；“数值算对”还不包括真实点表和命令反馈验收。

### 11.6 黄金向量和错误用例

预期来自已批准的语言规则，不来自“旧 C 代码返回了什么”。C 参考实现必须使用受检算术和固定宽度，不用 C 未定义行为为 VCL 定义结果。

| 分类 | 输入/场景 | 新语义预期 |
| --- | --- | --- |
| 优先级 | `i32(1)+i32(2)*i32(3)` | 7 |
| 整数/浮点除法 | `i32(5)/i32(2)`、`f64(5)/f64(2)` | 2、2.5 |
| 负数除法 | `i32(-7)/i32(2)` | -3 |
| 类型 | `i32(1)+f64(2)` | 编译拒绝，需显式转换 |
| 短路 | `false && (i32(1)/i32(0) > i32(0))` | false；右侧不求值，仍做语法与类型检查 |
| 符号检查 | `false && unknown_name()` | 编译拒绝，不因短路忽略未知函数 |
| 算术边界 | 最大 i32 加1、u32的0减1、除零 | 对应错误，提交前无外部输出 |
| 位运算 | u32移位32位、超宽左移、有符号位操作 | 按规则拒绝或运行错误，不能宿主语言自动截断 |
| 初始化 | 读取未赋值 local | 编译拒绝 |
| 数组 | 长度4访问下标4或-1 | 编译拒绝或 BOUNDS |
| 常量精度 | u64最大值经执行包往返 | 完整保留；不经 double |
| 循环 | for 中 continue、do 首轮条件为假、嵌套 break | 迭代落点正确、do执行一次、只离开最近结构 |
| 循环限额 | 达到上限条件仍真 | LOOP_LIMIT，非正常结束 |
| 调用 | 间接递归、返回类型不符 | 编译和设备验证器都拒绝 |
| 预算 | 内层函数或循环耗尽父任务额度 | 共享预算，不通过调用重置 |
| 状态 | 第N步失败，之前修改 state 工作副本 | 未提交算法状态保持原值；错误计数保留 |
| 时间 | RTC回拨、错过节拍、同任务重复触发 | 单调超时不受影响；不重入、不无界补跑 |
| 实例dt | 成功一轮、失败两轮、再恢复 | 按上次成功提交时间计算实例dt；超过maxDt则拒绝补算并要求复位 |
| 实例dt | 未调用若干轮后恢复 | 按实例声明的跳过规则处理，不能把名义周期直接当实际dt |
| 分支 | 未选分支的旧缓存被本轮消费者引用 | 静态拒绝，或必须显式读state |
| 数学 | 常量/动态参数的 sin_deg、定义域错误 | 同规则和单位；误差按函数档案检查 |
| 命令 | 本轮提交前预算耗尽 | 本轮不接受/发送新命令，丢弃算法工作状态 |
| 命令 | 前轮命令已SENT，本轮预算失败 | 前轮动作账本保留，不随本轮回滚 |
| 命令 | 已提交后发送或确认异常 | 记录FAILED/UNKNOWN，不假装撤销；Legacy立即输出另列兼容测试 |

固定向量按“语言参考模型↔C#离线执行↔C VM宿主↔目标固件”对拍。整数、状态、控制轨迹、错误和效果次数精确比较；浮点按函数类别逐位或规定容差比较。必要时记录输入顺序、时钟和反馈回放，保证问题可复现。

### 11.7 故障注入与压力验证

至少覆盖以下组合，并在不同执行相位注入：

- 截断/超大配置、未知版本/opcode、假跳转、坏端口、重复标识、索引和长度溢出。
- 品质失效、采样过期、点间时间差、参数版本变化、队列满、日志限速和存储满盘。
- 多任务和多链路竞争同一物理输出，人工接管、就地模式和保护闭锁。
- 第 N 个候选启动失败、READY 前退出、旧任务阻塞、停止超时、迁移失败和 watch 丢事件。
- 激活后首轮失败、旧命令仍在途、确认丢失、掉电发生于激活记录的各写入窗口。

软件测试使用内存点表和记录式接口；目标板/HIL（硬件在环）测试测量真实延迟、抖动和故障处理。建议评审起点为：不少于10万轮软件状态回放、24小时目标负载运行、1000次自动重载/拒绝/回退组合。数量是建议测试规模，不是既有结果，也不能代替风险分析。

上线前为 `deadline/stopDeadline/inputAge/commandTTL/queueLimit` 等填入批准数值，要求限定工况内无越权动作、无同任务重入、无提前释放活对象、无跨代次授权重叠。测得的最大耗时仍是观察值，不自动成为已证明的最坏执行时间。

## 12. 分期路线与验收门槛

### 12.1 阶段计划

P0 的旧路径加固与 P1 的离线规范工作可以并行；P2 不等待在旧引擎上补齐所有循环。每阶段先交付可重复验证的纵向样例，再扩大语法或设备权限。

| 阶段 | 主要工作 | 退出门槛 | 回退边界 |
| --- | --- | --- | --- |
| P0 兼容基线与安全加固 | 固定双端版本；列Type/契约矩阵；修动态目标、越界、截断、表达式加载和直接副作用缺口 | 存量样例通过；坏配置明确拒绝；旧循环和停止风险有明确阻断策略 | 保留已验证旧固件/旧配置，不启用新增语义 |
| P1 规范与原型决策 | 冻结语言/数值/时间/状态/错误；定义源/IR/包、能力及Host API；比较执行后端 | 同一正反例可唯一判定；接口、格式和目标资源测量计划评审通过 | 只离线运行，不接现场输出 |
| P2 最小纵向执行 | SCRIPT输入输出、基本类型/变量/if、编译器、固件验证器和VM、预算、SourceMap、C#离线执行 | 从工程到执行包到模拟宿主完整贯通；非法包拒绝；缓存失效、读回、故障无未授权输出 | 新工程可draft保存，Legacy导出独立保留 |
| P3 核心表达能力 | 数组、无递归函数、全部结构循环、break/continue/return、类型扩展 | 黄金向量与回放一致；调用/栈/迭代有上界；复杂策略无需新增普通计算元件 | 未支持目标拒绝部署，不做近似降级 |
| P4 领域接口与状态 | 快照、PI/定时/积分实例、输出仲裁、非阻塞命令、真实C适配 | 每个开放接口有状态/时间/权限/故障测试；目标板压力与HIL通过 | 默认影子，按输出逐项放开 |
| P5 发布与有限投运 | READY屏障、代次切换、停止/状态迁移、持久版本、回退和审计 | 热切换/掉电/未知结果可恢复或受控停用；现场参数、闭锁和回退签认 | 可撤销许可并回到明确的维护或旧版接管流程 |
| P6 按需扩展 | struct/枚举、二维数组、受限字符串、retain、紧凑二进制、可选C生成 | 每项独立更新规范、能力和测试；有场景收益再加入 | 不改变未升级目标的原语义 |

“核心目标达成”至少需要 P3 的语言能力和 P4 的接口安全；要承诺现场可发布，还需 P5。不能把 P2 能执行脚本原型当作可满足现场任意策略的完成标志。

### 12.2 首个纵向样例的最小交付清单

P2 首个纵向样例建议使用“四个标量输入→无循环的加权/限幅计算→两个分支→一个影子输出”，带除零、类型/索引错误、预算耗尽和未知类型反例。P2 的 SCRIPT 入口封装不表示已经支持通用用户函数。第11.5节的数组功率分配作为 P3 扩展样例，再加入动态下标越界、for、continue和函数调用。每个样例一次交付以下内容，而不是只交一个编辑器窗口：

1. 版本化语言/类型/指令/接口定义和测试向量。
2. 可编辑工程，包含一个 SCRIPT、稳定端口身份和源码诊断。
3. 确定性编译器和执行包，附源映射、资源统计和摘要。
4. C#参考执行、C VM隔离宿主及设备端独立验证入口。
5. 记录式点表、时钟和输出桩，能重放周期、状态和错误轨迹。
6. 工程读回、包篡改拒绝、超限与预算测试记录。

样例完成后再决定生产后端，不在原型尚未测量时同时投入完整脚本编辑器、函数库商城、多维类型和二进制压缩。

### 13.2 必须采集的设备参数

- 设备型号、CPU 架构和主频、可用内存、内核版本、编译器和浮点选项。
