## 文档说明与术语约定

本文档基于上位机配置软件与嵌入式设备端当前源码，梳理现有系统的能力边界，并给出可视化编程规约向“受限 C 级表达能力”演进的完整技术方案与分期实施计划。

阅读本文时，建议留意三类内容的区分：

- **当前系统现状**（第 2 章与附录索引）：已从现有 C# 和 C 源码中确认的架构、元件与协议行为。
- **推荐演进设计**（第 3～8 章）：供评审与立项采纳的目标方案；文中的 `VCL` 语言、中间表示（IR）字段、模块名及错误码均为建议命名。
- **待确认与实测项**（第 7.3 节）：需要补充设备端硬件实测、接口规约确认或产品拍板的约束；正式投入现场运行前，仍需补齐目标板的性能测量与验收证据。

### 核心术语

| 术语 | 含义 |
| --- | --- |
| **VCL**（Visual Control Language） | 本方案拟议的受限策略脚本语言。沿用 C 风格语句组织，但剔除指针等不安全特性，并具有独立确定的数值与执行语义。 |
| **AST / IR** | AST 是解析文本源码得到的抽象语法树；IR 是剥离界面细节后、用来统一表达图形与文本语义的中间表示。 |
| **VM**（虚拟机） | 运行在设备端的受限指令执行引擎，负责在有限内存与步骤预算内执行经过独立校验的程序包。 |
| **RTDB**（实时数据库） | 设备内部保存遥信（YX）、遥测（YC）、电度（DD）和系统参数的共享数据区。 |
| **Host API** | 设备固件向 VM 开放的白名单宿主接口，涵盖纯计算库、带状态功能块及受控输出通道。 |
| **Legacy** | 保持当前配置格式、图元连接与 `NextID` 跳转语义的存量执行路径。 |
| **Profile** | 描述某一目标设备硬件能力、支持指令集、数值标准及资源上限的能力档案。 |
| **generation（发布代次）** | 每次程序热加载激活时递增的唯一代次编号，用于隔离新旧版本程序实例并管控设备输出权限。 |
| **YK / YT、SOC / PCS** | YK 指遥控（开关分合）、YT 指遥调（定值调节）；SOC 指储能荷电状态，PCS 指储能变流器。 |

## 1. 总体结论与核心设计取舍

### 1.1 一句话演进路线

**保留现有图形配置与存量运行链路，在画布中引入“受限文本脚本块（`SCRIPT`）”和“结构化子图”，让图形和文本在编译期汇入同一套有类型、有作用域、可分析控制流与数据依赖的语义中间表示（IR），再编译生成由设备加载器独立校验、在嵌入式虚拟机（VM）中按周期受控执行的程序包。**

不在现场设备端编译任意 C 源码，也不直接加载第三方原生动态库。

### 1.2 能力目标与边界

演进后的产品应当让微电网策略开发者获得完整的工程级程序结构，而不是为了追求“理论上的图灵完备”引入不可预测的运行时风险。可验收的目标可以归纳为：**在已声明的设备接口、数据规模、计算预算与安全权限范围内，常见现场策略通过配置即可完成，无需修改固件；新增设备规约或基础算法通过受控接口扩展；一旦策略超出预算或接口边界，由编译器和设备端给出明确的定位诊断，而不是勉强运行。**

| 能力维度 | 演进目标 | 工程边界与限制 |
| --- | --- | --- |
| **控制抽象** | 支持顺序、条件（`if/else`）、多路选择（`switch`）、结构化循环（`for/while/do-while`）及 `break/continue/return` | 每个循环必须绑定迭代上限，每条路径受单轮步骤与时间预算约束，不在扫描周期内通过死循环等待设备 |
| **数据抽象** | 支持显式宽度的基本类型、局部/周期/状态变量、一维定长数组（后续扩展结构体与枚举） | 不开放裸指针、`union`、任意地址读写与扫描期间动态内存分配 |
| **过程抽象** | 支持参数传递、返回值、局部作用域、纯函数复用与有状态功能块实例 | 调用图静态无环，禁止直接或间接递归，不提供函数指针 |
| **时间与状态** | 跨扫描保留任务状态，支持基于单调时钟的持续时间判断、定时与状态机 | 禁止在扫描线程内阻塞 `sleep` 等待现场开关反馈 |
| **设备交互** | 每轮基于不可变输入快照与点位品质计算，输出受控的动作意图并追踪异步反馈 | 接口调用严格限定在固件白名单内；设备侧保护闭锁与联锁独立保留 |
| **生态扩展** | 通过版本化的 `Host API` 与库机制扩展能力 | 新通信规约驱动、底层硬件操作及保护级快速响应仍需固件开发与验收 |

下列能力在演进规划中**明确不做**：

- 不直接执行原生机器码，不在设备端运行 C 编译器或 `dlopen` 任意动态库。
- 不提供 C 指针、预处理宏、内联汇编、可变参数或脚本内自定义线程。
- 不向脚本开放文件系统、Shell 命令、网络套接字或任意系统调用。
- 不用虚拟机替代继电保护、紧急停机或设备侧最终硬件闭锁。
- 不承诺任意文本脚本都能无损反编译为传统的元器件连线图。

### 1.3 关键设计取舍

1. **新控制结构与函数落在独立 VM，不在旧引擎中强行拼装**
   现存设备端引擎靠单步调用与 `NextID` 链表跳转驱动。若把 `for`、局部变量、数组和调用栈直接塞进旧元件模型，不仅双端需要重复维护两套复杂语义，还容易波及存量现场逻辑。因此，存量配置继续留在 Legacy 路径，先修复其已发现的边界缺陷；新表达能力统一在新的 VCL 编译链与 VM 中实现。
2. **保存完整源工程，图形与文本只做有限互转**
   源工程同时保存图形拓扑、文本脚本、符号表和布局注释。对于无法自然拆解为连线的带循环、带变量算法代码，在画布上保留为 `SCRIPT` 块，避免强行“图形化拆解”而丢失局部作用域与执行顺序。
3. **现有元件按三类适配为 Host API，不向脚本暴露旧虚表**
   现有嵌入式元件的 `Execute` 直接耦合了节点指针、端口缓存和即时外部动作（如发遥控、写文件）。演进时将其拆解为纯计算函数、有状态功能块和外部效果三类白名单接口，确保 VM 能够在提交前保持“零外部副作用”。
4. **周期超时或算术异常只能阻断本轮提交，不能撤销已发设备动作**
   如果程序在计算中途耗尽步骤预算或除零，VM 可以安全丢弃尚未提交的状态工作副本和输出意图；但对于前一轮已经下发给驱动的遥控命令，无法在物理上自动撤回。因此安全策略必须针对每个受控对象单独定义，并通过动作账本与设备反馈完成闭环。
5. **以目标板实测决定最终执行后端**
   首期建议实现一个结构简单、易于形式化验证的类型化小栈机作为原型，并与成熟受限运行环境（如 WebAssembly）对照评审。即便嵌入式 Linux 支持 `malloc`，仍需在目标 ARM 硬件上实测程序体积、内存峰值、启动重载时间、扫描抖动以及对其余业务规约的影响。

## 2. 现有系统盘点与演进约束

### 2.1 C# 配置端现状（`LogicEngineConfigTool`）

配置端是基于经典 WPF 与 .NET Framework 4.8 开发的桌面应用（回归测试工程固定为 C# 7.3）[H1]。当前已经具备较完备的图元体系与编译保存管线，但尚未构成通用编程语言：

- **元器件覆盖**：`ElementTypesEnum` 共定义了 52 个枚举值（含 `Type_Unknown` 以及尚未实现的左右括号预留项），通过反射工厂 `ElementFactory` 发现 49 个生产元器件类与 1 个未知兜底模型（共计 50 个 `IElementModel` 具体类）。
- **单文件事务保存与快照恢复**：正式保存采用“单文件、双表示”机制 [H3、H4]。`TransactionalConfigSaveService` 先在隔离克隆副本上执行连接规范化、控制流编译与计划应用，检验多态序列化往返、实时库存储顺序（`SAVEORDER001`）与持久化积分配对顺序后，将运行时投影与 gzip+Base64 编码的编译前编辑快照（根级 `EditorData`）写入同目录临时文件，经五重回读核验后通过 `File.Replace` 或 `File.Move` 原子提交。
  - 保存时，`BREAK`、`CONTINUE`、`JOIN` 和编辑态 `JUMP` 会投影为运行态 `JUMP`（携带 `NextID`、完整输入/输出端口数组以及带版本的原模型 `EditorOriginal`）。
  - 打开文件时，优先校验并恢复内嵌的 `EditorData`；若缺失，则按 `SndFile/` 优先于同目录的顺序兼容查找历史 `.editor.json` 侧车，再尝试按 `EditorOriginal` 或有限控制流推断恢复完整编辑图。若无法唯一恢复，仍允许对合法的运行投影调整画布布局，但绝不从 `NextID` 反向猜测数据连线。
- **控制流编译流水线**：桌面端支持 `IF`、`SWITCH`、`WHILE`、`FOR`、`DO_WHILE` 以及 `BREAK`、`CONTINUE`、`JOIN`、`JUMP` [H2、H5]。编译过程严格遵守“只读分析、计划先于变更”，依据每个任务持久化的 `CompilationSourceOrder` 保证重复保存顺序完全幂等。不过，当前突转解析器仅将 `BREAK` 归属到 `WHILE` 循环体或 `SWITCH` 分支，将 `CONTINUE` 归属到 `WHILE` 循环体；`FOR`（已具备初始化/条件/迭代表达式槽）与 `DO_WHILE` 在工具箱界面中默认屏蔽隐藏，尚未接入完整突转解析与设备执行。
- **表达式子语言与静态守卫**：`ExpressionParser` 能为长表达式和 `FOR` 表达式构建带源码位置（`TextSpan`）的 AST 用于语法检查 [H8]，支持算术/关系/逻辑/位运算、24 个区分大小写的内置数学函数与常量（不含 `max`/`min`），以及 `#点号` 和 `#(link,dev,reg)` 实时库读写；但不支持局部变量、数组、语句块或用户函数。同时，桌面端已经固化了一条重要的安全守卫规则 `SAVEORDER001`：只要 `SAVE_DATA` 写入了某个实时库点位，同一任务内所有引用该点位的消费元件，其每条可执行到达路径都必须先经过该 `SAVE_DATA`（禁止跨任务或带 `-1` 通配地址的模糊引用）[H6]。
- **回归测试体系**：独立控制台程序 `LogicEngineConfigTool.RegressionTests.exe` 提供无参全量主干与 42 个具名专题开关（例如 `--single-file-editor-snapshot-only`、`--control-flow-jump-only`、`--realtime-storage-order-only`）[H9]。需要注意两件事：第一，如果向 `Program.Main` 传入拼写错误的未知命令行参数，程序会穿透到默认尾部测试并返回 `0`，因此执行专题测试时必须确认参数准确并核对输出；第二，真实 WPF 控件交互（`--control-flow-real-wpf-only`）、原始草稿备份（`--raw-draft-only`）以及部分纯内存新元器件用例（`--new-elements-memory-only`）未包含在无参默认入口中，改动对应模块时须显式加跑。

### 2.2 嵌入式运行时现状（`linuxttu` 规约 57）

以下结论核查自 C0/C1 终端 `e9361app` 构建配置下的规约 57（`VisualProgramming_Thread`，配置文件为 `c%02d57.json`）[R2]：

- **元件注册与未覆盖项**：`LogicEngineV2_RegisterBaseElements` 共注册了 **40 个有效 `Type`**，涵盖逻辑门（4 个）、比较与最值（`COMPARE_*` 6 个 + `MAX`/`MIN`）、定时器（`DELAY`/`INTERVAL`/`OVERTIME`/`PERIOD`）、I/O 与数据类（9 个，含 `SAVE_DATA`）、算术与算法（10 个，含 `PI_CONTROLLER`/`RATE_OF_CHANGE`/`ALGO_INTEGRAL`）、控制流（`IF`/`SWITCH`/`WHILE`/`JUMP`）及日志输出（`DEBUG_PRINT`）[R2]。
  - 桌面端有而设备端未注册的运行类型包括：`FOR`、`DO_WHILE`、`EXTREME`（时间序列极值，不同于固件已注册的实时库多点比较 `MAX`/`MIN`）、`TIMER_TON`、`TIMER_TOF` 及代码内已注释的 `TIMER_TP`。桌面编辑辅助结构 `BREAK`、`CONTINUE`、`JOIN` 依赖保存时降级为 `JUMP`。
  - 设备加载器遇到未知 `Type` 会导致整份配置加载失败，而不是跳过单个元件 [R3]。头文件中声明的 `LogicEngineV2_Init/Start/LoadConfig` 等函数目前并无实现体，规约 57 实际运行入口位于 `logic_visual_programming.c`。
- **静态资源与容量规则** [R1、R3]：

| 限制项 | 固件当前实现 | 对新设计的启示 |
| --- | --- | --- |
| 每链路任务数 | 1～10 个；超限直接拒绝加载 | 新格式需明确沿用或调整上限，并严格拒绝超限 |
| 每任务元件数 | 固定数组容量 500；超过时静默截断保留前 500 个 | 截断程序极易引发严重逻辑错误，新格式必须整包拒绝超限 |
| 元件 `Id` 范围 | 仅允许 `0～499`，任务内唯一并直接作为映射下标 | 源工程稳定身份必须与运行期稠密索引分离 |
| 端口与参数槽 | 每元件最多 16 入、16 出、32 参数 | 属于静态上限，不代表每个元件都拥有这么多可用端口 |
| 表达式缓冲 | 200 字节字符数组（最多保留 199 字节有效文本） | 新脚本文本长度不可受限于这个固定缓冲 |
| 执行入口 | 固定从数组首元素 `Elements[0]` 开始执行 | 新格式应显式指定入口函数或入口 ID，不依赖位置巧合 |

- **调度语义与五个关键约束**：`VisualProg_TaskThread` 每个扫描周期从 `Elements[0]` 开始，同步调用当前元件的 `Execute`，然后按 `config.nextId` 跳转（`IF`、`SWITCH`、`WHILE` 在执行期间动态改写自身的 `nextId`）；当 `nextId < 0`、目标越界或元件返回非零值时结束本轮，调用 `usleep(scanInterval_ms * 1000)` 后开始下一轮 [R4]。这种机制带来五个局限：
  1. **扫描周期非固定节拍**：实际周期约为“计算耗时 + 轮末休眠 + 调度开销”。
  2. **无统一输入快照**：输入元件执行到自己时才读取 RTDB，同一扫描轮次前半段和后半段读到的现场状态可能不一致。
  3. **未选分支保留旧缓存**：条件分支未命中的一侧不执行，其输出端口仍保留历史数值，系统缺少“本轮是否有效产出”的数据流保护。
  4. **缺少计算预算且停止无界**：执行器没有指令步数或单轮超时预算（虽然每步会检查停止标志 `threadRunning`，但 `TIMER_DELAY` 内部直接调用 `usleep`，部分遥控/遥调公共回调也会阻塞等待，且停止线程采用无超时的 `pthread_join`，无法保证有界停止）[R4、R6、R6a]。
  5. **校验与时钟基准隐患**：加载期会对普通 `nextId` 做存在性检查，但 `IF` 的私有 `TrueNextID`/`FalseNextID` 未经过同等完整检查，且运行期 `arrIdToIndex[nextId]` 查表前缺少越界防御 [R3、R4]。此外，各元件时钟基准并不统一：`ALGO_INTEGRAL` 使用单调时钟 `CLOCK_MONOTONIC`，`TIMER_INTERVAL`/`TIMER_OVERTIME` 和 `RATE_OF_CHANGE` 使用受系统校时影响的墙钟 `gettimeofday`，而 `PI_CONTROLLER` 直接按名义配置周期 `scanInterval_ms` 计算积分步长 [R6]。
- **热加载基础与缺口**：`VisualProg_TryReloadConfig` 结合了 inotify 目录监听、5 秒文件稳定窗口、`/tmp` 快照、MD5 比对以及在临时上下文 `newCtx` 中预解析校验。然而，验证通过后的切换顺序是“**先停掉所有旧任务，再逐个启动新线程**”[R7]：不仅切换期间存在控制输出空窗，若第 N 个新任务创建失败只能回退启动保留的旧任务对象（无法恢复外部设备状态或精确断点），而且新旧版本之间没有通用的状态迁移机制。

### 2.3 双端类型、参数与表达式差异

1. **类型不是同一套概念**：桌面端 `PortDataTypeEnum` 是端口连接位掩码，主要检查连线两端位掩码交集非零，`OutputModel.DataType`（如 `"FLOAT"`）只是展示与辅助标签；固件通用端口与参数槽虽以 `double` 为主，但私有参数包含整数、结构体和字符串，RTDB 读写接口按 `float` 传递遥测/电度值 [H7、R1、R5]。因此，VCL 必须定义独立、封闭的语言类型系统，不能直接把现有枚举当成语言类型。
2. **已定位的参数契约差异**（改写或互操作前须在目标固件上对齐）：

| 场景 | 桌面端写出契约 | 当前固件源码行为 | 集成处理要求 |
| --- | --- | --- | --- |
| **遥控/遥调无条件执行** | `Method = 3`（每次执行均请求一次） | 读取不拒绝 `3`；执行时首轮建立基线，后续落入 `default` 分支报错返回 `1` [H11、R8] | 若目标固件未升级，部署检查应明确拒绝 `Method = 3` |
| **日志无条件执行** | `PrintEdge = 4`（受使能和周期约束） | 参数解析只接受 `0..3`，遇到 `4` 直接拒绝加载配置（`3` 表示关闭边沿触发，而非无条件）[H11、R8] | 目标固件未支持前明确拒绝 `PrintEdge = 4` |
| **积分计量间隔单位** | `IntervalUnit` 区分 `0`（毫秒）和 `1`（秒） | 加载期严格校验该字段必须为整数 `0` 或 `1`，缺少时拒绝加载（不默认毫秒），并检查毫秒换算溢出 [H11、R8] | 确保历史配置经桌面重存补全字段，实测零间隔与重启恢复 |
| **计次模式 `WHILE` 复位** | `Inputs[0]` 记录上游连线，编译后可能经 `JUMP` 回边进入 | 依据 `lastElemId == sourceElemId` 识别从上游进入以清零计数，经 `JUMP` 回跳不清零 [R4] | 重点实测经 `JUMP` 回边循环、跳出后重入时的计数复位与退出行为 |

3. **表达式求值器差异（`ExpressionParser` vs. `eval.c`）** [H8、R5]：

| 对比项 | 固件 `eval.c` 现状 | 对 VCL 新语言的要求 |
| --- | --- | --- |
| 逻辑运算符 `&&` / `\|\|` | 左右两侧操作数均会求值，**不短路** | VCL 严格采用标准短路语义；旧表达式留在兼容模式 |
| 除法求值顺序 | 按 `double` 计算，且**先算右操作数（除数）**再算左操作数 | VCL 统一规定从左到右求值 |
| 位运算 | 将 `double` 强转为有符号 `long` 后执行位运算与移位 | VCL 使用固定宽度无符号整数并检查移位范围 |
| 函数清单与参数校验 | `eval.c` 支持 `max`/`min` 且按函数固定参数个数校验；桌面 `ExpressionParser` 无 `max`/`min` 且统一限制最多 2 个参数 | 双端共享同一份签名清单（含参数个数、类型与单位） |
| 表达式内 RTDB 写入 | 求值过程中直接调用 `SetValueByRealNo` 按 `float` 写库，并忽略写入返回码；`#id` 在词法期查库，`#(l,d,r)` 在运行期解析 | VCL 表达式保持无副作用纯计算，写入必须通过显式输出语句完成 |
| 常量折叠三角函数缺陷 | `optimize_node`（`eval.c:2309-2322`）在计算角度/弧度换算后又执行了 `res = f1(vals[0]);` 覆盖了换算结果，导致常量与动态求值不一致 | 常量折叠与运行时必须调用同一套语义函数，且数学函数显式区分 `_deg` 与 `_rad` |
| 错误信号表达 | 混合使用 `NULL`、返回 `NaN`、打印日志与错误码 | VCL 用独立错误结果对象报错，不拿 `NaN` 兼作失败信号 |

## 3. 目标架构：图形与文本同源的三层产物

### 3.1 总体数据流与三层职责

新架构将配置生命周期解耦为三个逻辑层次，分别承担编辑、语义分析与设备运行职责：

```text
  传统图形元件 / 结构化子图 / VCL 脚本文本（SCRIPT）
                         │
                         ▼
          词法语法解析、符号绑定与静态类型检查
                         │
                         ▼
                 统一结构化语义 IR
                         │
              控制与数据流分析、资源预算、编译
                         │
                         ▼
     执行包（类型表 + 字节码 + 常量 + 接口绑定 + 源码映射）
            │                                  │
            ▼                                  ▼
      上位机离线仿真                    设备加载器独立校验
                                               │
                                               ▼
                                周期快照执行 + 状态暂存 + 输出仲裁

  存量工程 ─────────────────────────────────► Legacy 兼容执行路径
```

1. **源工程（给人编辑与版本管理）**：保存图形画布拓扑、VCL 脚本文本、语言版本、稳定端口/符号 ID、库依赖及注释布局。**允许保存语法或类型尚未通过的草稿**，以便工程师保存阶段性工作；但只有通过全部编译和目标能力检查的版本才能导出执行包。
2. **结构化语义 IR（图形与文本的共同后端输入）**：由语言前端和图形桥接层共同产出，剥离画布坐标与文本排版，只记录有类型的变量、函数签名、控制流区域、有序副作用及源码映射，并据此完成资源上界估算。
3. **执行包（给虚拟机加载与校验）**：独立路径存储的只读运行容器，包含固件执行所需的全部信息。新执行包在格式、版本和入口尚未得到目标固件识别前，绝不混发给旧加载器。

为保证修改可追踪、缓存不误用，桌面端需建立规范化的 **`SourceDigest`（源码语义摘要）** 与可定位的多对多 **`SourceMap`（源码映射）**：

- `SourceDigest` 覆盖语言版本、归一化后的脚本原文（含换行与注释，以固定诊断位置）、图拓扑、稳定端口/符号 ID、目标档案摘要及库摘要，**排除纯画布坐标挪动与界面临时选择**；一旦脚本、签名或目标能力变动，旧缓存立即失效，禁止继续发布旧执行包。
- `SourceMap` 把执行包中的 `(函数编号, 指令 PC 区间)` 关联回源工程中的 `(任务/画布/元件/端口 或 脚本文本 UTF-8 字节区间)`，使得设备端报出运行错误时，上位机能在源码或图元上高亮定位。如果只有执行包而没有源工程，工具仅提供只读派生视图。

### 3.2 `SCRIPT` 元件与图形画布的协作

复杂计算、循环和算法复用由画布上的 `SCRIPT` 元件承载，简单比较和逻辑门继续用图形连线；状态机和嵌套流程可通过结构化子图组织，避免把大量回边直接拉在同一张画布上。

- **单一权威编辑来源**：同一段逻辑只保留一种可编辑源。图形区域可以生成只读文本视图辅助阅读；如果用户将某块逻辑转为文本编辑，则演进为保留该 `SCRIPT` 块，避免“图形与文本双边各自修改导致同步失真”。
- **首版 `SCRIPT` 图形接口契约**：

| 脚本签名成分 | 对应画布端口与运行边界 |
| --- | --- |
| 标量输入参数（如 `f64 request_kw`） | 对应一个同类型标量数据输入口，通过持久化的 `ParameterId ↔ PortId` 绑定稳定身份，不随参数顺序临时改号 |
| 数组输入参数（`in T name[N]`） | 对应新定义的定长数组输入端口（携带元素类型 `T` 和长度 `N`），不借用现有位掩码端口冒充数组 |
| 标量返回值（如 `function f64 ...`） | 对应一个同类型数据输出端口，函数所有可达返回路径都必须返回结果 |
| `void` 返回值 | 不产生数据输出口，仅用于结束当前块；外部效果权限须通过白名单接口单独声明 |
| `SCRIPT` 块内 `return` | 仅结束当前脚本块调用，控制流返回图形后续节点；不能从脚本块内部直接跳出外层任务或跳转到任意外部元件 ID |
| 任务入口 `return` | 结束本轮任务计算并进入统一的提交校验流程 |

- **签名修改与图桥接策略**：当用户在属性面板修改 `SCRIPT` 签名时，先通过 `PreviewSignatureChange` 生成保留、新增、删除和冲突计划并提示影响。若仅改名或调整参数顺序而身份与类型不变，保留原有端口实例与外部连线；若类型或数组长度变动导致现有连线失效，必须在用户确认断线后在同一编辑事务中同步更新两侧端点（支持完整 `CanvasEditHistory` 撤销与重做，取消则零污染）。在 P3 阶段打通图形桥接（`GraphToTypedProgram`）时，仅接受完整可信的源图，复用现有规范化与区域分析思想，并拒绝语义不明的宽位掩码（`DataType_all`）与未定效果元件。

### 3.3 执行后端路线评估

| 候选路线 | 优势 | 在本项目的工程代价与风险 | 结论与建议 |
| --- | --- | --- | --- |
| 继续增加普通图形元件 | 沿用用户现有操作习惯和存量 JSON 路径 | 局部变量、数组和函数调用用端口连线表达极其繁琐，每加一种功能双端都要硬编码对接 | **保留作前端补充**，不作为通用表达核心 |
| **自研类型化栈式小 VM** | 指令语义、固定类型槽、步数预算、单调时间和错误处理完全按工控需求定制 | 需要团队自行实现并长期维护字节码验证器、解释器及调试工具链 | **推荐作为首个原型路径**，经测试与硬件测量达标后决定是否直接转生产 |
| **成熟受限后端（如 WebAssembly）** | 拥有业界成熟的沙箱验证、内存与控制流检查规范 | 需在目标 ARM 平台实测代码体积、运行时开销、调试体验及与现有 C 宿主接口的集成复杂度 | **原型阶段同步对比评估**，用实测数据决定最终选型 |
| Lua 等嵌入式动态脚本 | 生态成熟，C 集成简单 | 动态类型与垃圾回收引入非确定性延迟，需要额外做大量静态限制才能满足预算要求 | 不作首选，仅在满足同等类型与预算约束时备选 |
| 生成原生 C 代码 | 算法性能高，易于与离线参考对拍 | 现场交叉编译工具链、动态加载安全性、权限隔离及热回滚成本极高 | 仅作**离线仿真参考后端**，不作为设备端主路线 |

## 4. VCL 语言与执行语义规范（建议冻结）

### 4.1 分期子集与首版（P2）文法骨架

为降低落地风险，VCL 按阶段逐步开放表达能力：

- **P2（最小纵向原型子集）**：提供单个纯函数入口（`function T name(...) { ... }`）、四类基本标量（`bool`、`i32`、`u32`、`f64`）、按值只读形参、`local` 局部变量、独立赋值语句、语句块、`if/else` 与 `return`；不支持循环、数组、用户函数调用、状态变量和设备写入。
- **P3（完整核心语言）**：扩展 `i64`、`u64`、`f32`、无符号位运算、一维定长数组（`in T name[N]` 只读视图）、无递归的用户纯函数、完整的 `switch` / `for` / `while` / `do-while`（含 `break`/`continue`）及带限制的图形控制流桥接。
- **P4～P6（领域接入与按需扩展）**：分期引入跨轮 `state` 与有状态功能块、输入快照与输出意图接口，后续按真实场景需求补充 `struct`、枚举、二维数组、受限字符串和掉电保持 `retain`。

> 说明：首版刻意省略 `++`/`--`、链式赋值（`a = b = 1`）、逗号运算符及表达式内嵌赋值（用 `i = i + 1;` 替代），以此消除隐含的求值顺序歧义。

**P2 最小文法骨架**（`[ ]` 表示可选，`{ }` 表示零次或多次重复）：

```text
program = "function" type id "(" [param {"," param}] ")" block EOF
param   = type id
type    = "bool" | "i32" | "u32" | "f64"
block   = "{" {stmt} "}"
stmt    = block
        | "local" type id ["=" expr] ";"
        | id "=" expr ";"
        | "if" "(" expr ")" block ["else" block]
        | "return" expr ";"
atom    = id | literal | type "(" expr ")" | "(" expr ")"
```

**运算符优先级**（从高到低，二元同级均左结合）：
1. 原子与显式转换：`id`、`literal`、`type(expr)`、`(expr)`
2. 单目运算：`!`、`+`、`-`
3. 乘除取模：`*`、`/`、`%`（`%` 仅限同类型整数）
4. 加减：`+`、`-`
5. 关系比较：`<`、`<=`、`>`、`>=`
6. 相等判断：`==`、`!=`（`bool` 仅允许逻辑与相等/不等运算）
7. 逻辑与：`&&`
8. 逻辑或：`||`

（P3 开启位运算时，再固化位反、移位、`&`、`^`、`|`；其中 `^` 固定表示按位异或，乘方使用显式数学函数。）

**源码编码约定**：标识符首版限 ASCII 字母、数字和下划线（区分大小写），注释和工程标题支持 UTF-8；小数点固定为 `.`，不受操作系统区域设置影响；编译器内部以 UTF-8 左闭右开字节区间记录源码诊断位置，WPF 界面展示时转换为 UTF-16 字符偏移。

### 4.2 类型、转换、算术与求值顺序

1. **`bool` 严格独立**：条件表达式必须是 `bool` 类型；数值判真必须写成显式比较（例如 `x > f64(0)`），彻底废除旧引擎 `> 0.5` 的隐式阈值规则。`bool` 与数值之间不进行自动互转。
2. **固定整数位宽与检查算术**：整数宽度与平台无关（不依赖 C 的 `long`）。不同数值类型禁止隐式混合算术（如 `i32(1) + f64(2)` 报错），必须显式转换（如 `f64(count)`）；未标明类型的字面量仅在上下文类型唯一确定时推导，存在歧义时拒绝。
3. **除法与溢出规则**：
   - 同类型整数除法向零截断（`i32(-7) / i32(2) = -3`），余数符号与被除数一致。
   - 整数加减乘、左移失位及窄化转换均采用**受检算术（Checked Arithmetic）**：一旦溢出直接触发 `NUMERIC_OVERFLOW` 运行错误，不静默回绕或饱和。确需按位回绕时在后续版本提供名字明确的内建函数。
   - 整数除零、最小有符号整数除以 `-1`、负数数组下标以及越界浮点转整数一律报错。计算最小有符号整数边界时须按数学真值检查范围，防止取绝对值溢出。
   - 无符号位运算（P3 起开放）仅接受 `u32`/`u64`，移位量满足 `0 <= n < 位宽`，右移固定为逻辑右移。
4. **浮点纪律**：按目标档案规定的 `binary64` / `binary32` 与最近偶数舍入规则执行，禁用改变算术语义的 `fast-math` 与未声明的乘加融合（FMA）。除数为 `+0.0` 或 `-0.0` 均报 `DIV_ZERO`，其余非有限值（`NaN`、`Inf`）输入或计算结果默认报数值错误，禁止把非有限值传播进算法状态或设备输出。数学库超越函数按固定算法逐位比对或按控制误差要求声明容差。
5. **从左到右求值与短路检查**：
   - 二元操作数和函数实参一律从左到右依次计算；表达式内部严禁写变量、写 RTDB 或触发功能块更新。
   - `&&` 与 `||` 严格短路求值。**静态检查（语法、符号查找、类型检查）必须覆盖所有分支；但运行时求值错误（如除零）仅在路径按语言顺序必定求值时触发**（与编译器是否开启优化无关）。例如：
     - `false && (i32(1) / i32(0) > i32(0))` 编译合法且求值为 `false`；
     - `false && unknown_name()` 因右侧符号不存在而在编译期被拒绝。
   - 数学函数签名明确记录单位与定义域，例如用 `sin_rad` 与 `sin_deg` 明确区分弧度和角度，并在常量折叠和运行时共享同一实现。

### 4.3 作用域与生命周期

| 存储类别 | 生命周期 | 初始化与异常处理规则 |
| --- | --- | --- |
| `local` | 单次函数或脚本块调用 | 读取前必须保证在所有可达前驱路径上都已赋值；非 `void` 函数每条可达返回路径均须返回 |
| `cycle` | 单次任务扫描周期 | 每轮开始时按声明重新初始化，不跨周期保持 |
| `state` | 单个任务或功能块实例 | 程序加载激活或显式复位时初始化；计算期间在工作副本上修改，整轮提交成功才更新主状态 |
| `retain` | 跨进程或设备重启 | 默认不启用；需单独明确写盘寿命、掉电原子性、版本变更及人工复归流程后方可开放 |
| 只读常量/参数 | 当前程序代次或参数版本 | 在扫描周期边界冻结，执行期间不被后台线程改写 |

为降低现场审阅误判，VCL 禁止内层作用域变量遮蔽外层同名变量。不同任务之间的私有状态互相隔离，如需交换数据必须通过只读快照或带版本号的接口完成。

### 4.4 数组、函数与结构化控制流

- **数组与函数**：数组长度为编译期正整数常量，容量直接计入资源预算；常量下标越界在编译期拒绝，动态下标每次访问都做边界检查。首版数组传参统一使用只读视图 `in T name[N]`（仅限当前调用内读取，不可存入 `state` 或返回给外部）。函数调用图必须无环，禁止直接和间接递归。
- **分支合流规则**：在 `if/else` 或 `switch` 汇合点之后读取某个局部变量时，该变量必须在**每一条**可达前驱分支中都已被赋值；只要有一条分支漏赋值，前端数据流检查即拒绝编译。若需跨周期保持上一轮计算值，必须显式使用 `state` 变量，不能借助“元件在列表中排在前面”来隐式沿用旧值。
- **控制结构规则**：
  - `switch` 仅接受整数（支持枚举后可扩展枚举），`case` 常量不可重复；每个分支结束自动跳出 `switch`，不向下一分支穿透；缺省 `default` 时生成空分支。
  - `for` 严格按“初始化一次 → 条件 → 循环体 → 迭代 → 条件”执行；`continue` 在 `for` 中跳至迭代段，在 `while` 中跳至头部条件，在 `do/while` 中跳至尾部条件；`break` 跳出最近外层的循环或 `switch`。
  - 所有动态循环都必须声明显式最大迭代次数（如 `@max_iterations(N)`）；若首次判断条件为假直接退出属正常结束，但当迭代达到上限而条件仍为真时，报告 `LOOP_LIMIT` 运行故障并中止本轮，绝不伪装成正常完成。
  - 禁止任意 `goto`；任务入口内的 `return` 结束本轮逻辑计算，但仍进入统一的提交校验与清理流程。

### 4.5 有状态功能块与时间基线

定时器、PI 调节、积分器和变化检测等需要跨周期记忆的功能块，与无状态的纯函数有本质区别，必须绑定实例身份与独立的状态事务规则：

- **单轮最多步进（step）一次**：建议规定同一个功能块实例在同一个扫描轮次内最多执行一次 `step`，避免逻辑分支意外重调导致积分加倍或计时错乱；存在多路独立控制需求时，应显式声明多个实例。
- **统一的跨轮时间基线**：所有功能块均由任务容器注入单调时钟 `now` 与受检时间步长 `dt`，不再自行读取系统墙钟或假设名义周期不变：
  - **任务调度 `dt`**：取本轮实际开始时刻与上一轮实际开始时刻之差（首轮按初始化策略处理），用于调度监控，不随某轮算法失败回滚。
  - **实例采样 `dt`**：取本次 `step` 时刻与**上次成功提交**时的实例采样时刻之差，首轮仅建基线而不累计；该采样时间戳随实例状态一起提交或丢弃。
  - **超长间隔保护**：若两次有效步进间隔超过实例声明的 `maxDt`（例如任务连续故障恢复或被长时间跳过），默认放弃补算整段历史，本轮报告 `INVALID_DT` 并请求显式复位；复位后的首轮重新建基线。需要按真实流逝时间计时的持续定时器，应记录已提交的起始单调时刻并与当前 `now` 比较，跳过呼叫时的复位规则仍在功能块契约中明确声明。

## 5. 执行包格式、独立验证与虚拟机执行

### 5.1 容器结构与精确数值编码

首期采用可读性好、跨语言易调试的 JSON 容器格式，后续可在保持逻辑结构完全一致的前提下追加紧凑二进制编码（不直接将 C 内存结构体按字节写盘）。以下为执行包容器的结构示意（正式包必须填写全部有效版本、摘要与绑定项，空值不能通过验证）：

```json
{
  "Format": "vcl-executable",
  "SchemaVersion": "1.0",
  "LanguageVersion": "vcl/1",
  "SemanticVersion": "vcl-semantics/1",
  "BytecodeVersion": "vcl-bc/1",
  "HostApiVersion": "control-host/1",
  "TargetProfileId": "offline-reference",
  "RequiredCapabilities": ["bool", "i32", "u32", "f64"],
  "SourceDigest": "<sha256-of-canonical-source>",
  "CompilerVersion": "vcl-compiler/1",
  "Constants": [],
  "Functions": [],
  "Tasks": [],
  "Bindings": [],
  "ResourceRequirements": {}
}
```

- **版本与清单管理**：工程 Schema、语言语义、字节码版本、Host API 契约与目标硬件档案各自独立管理，首版采用显式白名单组合检查；发布清单在外部记录完整文件字节的加密摘要，不定义自包含的循环哈希字段。
- **精确数值与索引编码**：

| 字段类别 | 编码约定与校验要求 |
| --- | --- |
| 操作码（opcode） | 固定 `u16` 数值编号；拒绝保留或未知编号 |
| 函数、槽位、常量与指令索引 | `u32` 无符号索引；上限受目标 Profile 控制 |
| 资源计数与小整数 | 严格校验为 JSON 整数，拒绝浮点数、布尔值或字符串数字混入 |
| `i64` / `u64` 常量与时间值 | 采用带类型标签的规范十进制字符串（如 `{"type":"u64","value":"18446744073709551615"}`），防止经过 JSON `double` 解析丢精度 |
| `f32` / `f64` 常量 | 按目标浮点精度直接解析十进制文本，拒绝 `NaN`/`Infinity` |
| 程序终止 | 使用显式 `RET` / `TASK_END` 指令，不再沿用 `-1` 负 `NextID` 哨兵 |

### 5.2 指令集设计原则

推荐采用**类型化栈式虚拟机（Typed Stack VM）**：每个基本块的入口与出口保持操作数栈为空，跨基本块或分支汇合的值全部通过显式类型槽传递，从而大幅简化设备端静态类型与栈深校验。首版按职责划分五大类指令：

1. **数据读写**：常量压栈、标量输入读取、局部槽与状态工作副本的读写。
2. **受检计算**：类型化算术、溢出检查、关系比较、逻辑取反（`&&`/`||` 展开为条件跳转块，不设为单一求值指令）及显式类型转换。
3. **控制转移**：基本块内无条件跳转、条件跳转（弹出栈顶唯一的 `bool` 值）、静态函数调用、函数返回与任务结束。
4. **定长数组（P3 起）**：数组元素读取与编译期/运行期边界检查。
5. **宿主操作（P4 起）**：输入快照读取、有状态功能块 `step`、输出意图生成与日志记录。

执行计数与预算强制内嵌在 VM 解释循环中，由虚拟机自动计量，不依赖编译器或用户程序插入检查指令。

### 5.3 设备端七步独立验证

不管执行包是否由本项目配套上位机生成，设备加载器都必须将其视为不受信任的输入，按顺序通过以下七步校验后才能产出只读的 `VerifiedProgram` 句柄（任一步失败立即释放全部候选分配）：

1. **容器格式校验**：校验总字节数、UTF-8 编码、JSON 嵌套深度、禁止重复键与尾部多余字符、字段类型及数组上限；超限一律整包拒绝，不截断。
2. **版本与能力匹配**：校验协议版本组合、必需能力列表、opcode 集和目标产品型号；遇到未知必需能力直接拒绝。
3. **指令解码与引用检查**：建立完整指令边界，确保所有跳转目标都落在本函数合法的指令起点，且函数、常量、槽位、实例和点位绑定索引均不越界。
4. **栈类型与确定赋值验证**：沿每条控制流路径模拟操作数栈类型，拒绝欠栈、超栈、返回类型不符与不可达死代码；分支汇合时类型必须一致，且局部变量确定赋值集合取可达前驱的**交集**。
5. **调用深度与循环计量验证**：确认调用图无递归且不超过最大深度；在 P3 阶段，设备加载器需独立识别循环嵌套与回边，要求每条能反复进入循环体的路径必经唯一的准入检查点，禁止从外部跳入循环体或在循环内部重置迭代计数器（退出循环后再合法重新进入可重计次，但任务总步骤预算绝不重置）。
6. **资源防溢出重算**：忽略包中自报数字，基于实际指令、数组与帧结构用防溢出整数算术重算所需槽位、栈帧、状态与队列容量；若包内自报值小于重算值，或重算结果超出目标 Profile 上限，直接拒绝。
7. **接口绑定与权限审查**：解析最终 RTDB 地址、单位量纲、写入范围、白名单回调、唯一写者所有权及潜在冲突。

### 5.4 VM 内存纪律与统一故障处理

- **扫描期零内存分配**：程序激活前按加载器算出的上限预先分配好全部栈帧空间、工作槽、状态副本、快照区与输出暂存区；进入周期扫描循环后**禁止执行 `malloc`、动态扩栈或扩容容器**。C 端使用带类型标签或经验证器静态确保类型一致的值槽，不用一个 `double` 容纳所有整数。
- **统一检查优先级**：为了保证离线对拍与设备运行时在多重故障同时发生时表现完全一致，每条指令开始前严格按以下顺序检查：
  1. 是否收到任务取消/停止信号；
  2. 单调时钟是否达到本轮截止时间（`now >= deadline`）；
  3. 扣减本条指令的步骤预算（不足则报 `STEP_BUDGET` 不再执行）；
  4. 执行指令自身的动态检查（数组越界 `BOUNDS`、除零 `DIV_ZERO`、算术溢出 `NUMERIC_OVERFLOW`、循环超限 `LOOP_LIMIT` 等）；
  5. 若为宿主接口调用，先检查该类操作的剩余专用次数配额，返回后再复核是否超时（超时阻断整轮提交，不宣称强行打断了原生调用）。
- **标准故障处理**：故障对象携带 `generation / task / cycle / function / pc / source / error`，划分 `TYPE_MISMATCH`、`BOUNDS`、`DIV_ZERO`、`NUMERIC_OVERFLOW`、`LOOP_LIMIT`、`STEP_BUDGET`、`DEADLINE`、`STALE_INPUT`、`DENIED`、`QUEUE_FULL`、`HOST_FAILURE` 十一类错误码。任何运行故障默认立即中止本轮计算，丢弃工作副本上未提交的状态修改和输出意图，同时保留诊断记录与故障计数；带有外部交互的任务不会在故障后未经核查就从入口盲目连续重试。

## 6. 运行时周期执行、设备交互与热加载

### 6.1 不可变输入快照与品质处理

每个扫描周期开始时，调度器先构建一份只读的不可变输入快照（至少标记 `snapshotId`、`cycleId` 与 `parameterVersion`），任务内所有读取均基于该快照完成，禁止计算中途擅自重读实时库造成同一轮内数据撕裂。

- 数据点携带值、品质位、本机单调接收时间、更新序号以及源采样时间（若驱动提供）。读取快照采用有界锁或有限次版本重读校验，若无法取得一致快照则本轮直接失败，禁止无限自旋等待。
- 同一快照虽然在计算逻辑上是冻结的，但不同采集规约上传点位的时间并不一定同步，因此关键策略仍需设置**最大陈旧时间**与**点间最大采样时差**门槛。
- 当底层旧驱动缺少品质或源时标时，快照必须将其诚实标记为 `UNKNOWN`，不得用读取时刻伪造现场采样时间，也不得把读取失败的默认值 `0` 当成有效测量值。

### 6.2 单调时钟绝对节拍调度

新运行模式按单调时钟绝对节拍触发执行：`r(k) = r(0) + k * T`。

- 同一任务严格禁止重入（同时最多只有一个正在运行的周期）。如果上一轮耗时过长导致错过既定节拍，首版默认累加 `missedTick` 并跳过已过期节拍，对齐下一个未来节拍执行，不连续补跑历史欠账。
- 周期超时、预算计算、持续时间判定、输入陈旧度和积分 `dt` **一律使用单调时钟**；系统墙钟（RTC）仅用于投运日程与审计日志，保证后台校时前跳或回拨不破坏执行预算。
- 架构上可暂保留每个任务对应一个线程，但周期休眠必须改用可立即唤醒的等待原语（如条件变量带单调时钟超时），以便热加载停止时快速响应退出。

### 6.3 单轮事务提交与三类 Host API

```text
  获取不可变输入快照与冻结参数
        │
        ▼
  初始化 local / cycle 变量，建立 state 工作副本
        │
        ▼
  执行 VM 计算与功能块 step，暂存输出意图（尚未生效）
        │
        ▼
  校验预算、数据品质、数值范围、输出权限与多策略冲突
        │
        ├── 任一检查失败 ──► 丢弃工作副本与暂存意图，记录故障诊断
        │
        ▼
  在同步提交边界：更新主 state、状态对外可见、预留并释放发送队列
        │
        ▼
  异步发送获准的控制命令，在后续周期观察发送/确认/失败反馈
```

虚拟机能够调用的 `Host API` 严格分为三类，采用带代次（`generation`）与类型版本校验的逻辑句柄（禁止裸指针）：

| 接口类别 | 典型操作 | 核心契约 |
| --- | --- | --- |
| **纯计算** | 数学函数、限幅、格式受限数值处理 | 不读写外部状态，耗时有上界 |
| **有状态实例** | PI 调节、定时器、积分器、变化检测 | 实例句柄校验代次与版本，同实例单轮最多 step 一次，修改写入工作副本 |
| **外部效果** | 写 RTDB、YK/YT 请求、写日志、参数持久化 | 独立授权限额，计算期仅生成意图进入暂存队列，经提交校验后异步执行 |

针对存量 C 元件代码（如直接调用 `CommonYkOperation`、在回调中写文件或直接调用 `SetValueByRealNo` 的旧路径），必须完成适配器解耦或明确将其标记为不支持提交前零副作用事务的 Legacy 档案；影子模式与权限撤销也必须彻底拦截这些直接出口，不能只替换 `g_DataInterface` 的函数指针。

### 6.4 非阻塞控制命令、输出仲裁与安全策略

- **非阻塞命令与状态机**：扫描线程发出遥控或遥调请求时，效果接口仅执行有界的参数校验与入队，立即返回 `requestId`，不在扫描线程内阻塞等待设备回执。队列满时明确拒绝并返回 `QUEUE_FULL`（日志可按策略计数丢弃，设备控制命令严禁静默覆盖）。请求生命周期至少区分六种状态：

```text
  NOT_SENT ──► ACCEPTED ──► SENT ──► CONFIRMED  （收到明确成功反馈）
                  │          │
                  │          ├─────► FAILED     （收到明确失败反馈，记录是否部分完成）
                  │          └─────► UNKNOWN    （已发出但超时或失联，结果未知）
                  │
                  └────────────────► FAILED     （有确定证据证明尚未交给驱动发送）
```

  只有“已接收但确定尚未发出”的请求才能可靠取消；一旦交给底层驱动（即使尚未等到超时返回或处于 `UNKNOWN` 状态），在缺乏设备侧幂等支持的情况下不能断言动作未发生，也不得自动重发相反指令，而应保持该物理对象隔离，等待后续反馈或人工核对对账。

- **唯一写者与多策略仲裁**：默认一个物理控制对象只允许一个获权写者（识别并隔离跨任务、跨链路或实时库别名写入；若部分外部程序不在 VM 管辖内，应明确仲裁边界）。当同一台设备存在多种竞争策略时，各策略只输出带优先级与有效期（TTL）的控制意图，由统一仲裁器择优裁决，默认遇到同等冲突直接拒绝并告警，废除“后写者覆盖前写者”。
- **逐对象安全策略**：每个物理输出绑定须在投运前明确定义单位、正负方向、允许范围、最大变化速率、所有权、许可条件、有效期、冲突处理、反馈点位、通信失联保持时限及安全回退态。**安全态不等于一律清零**：有的功率设定值应受控降额，有的顺控应禁止新发动作，有的设备则由其自身保护逻辑接管。对于并离网切换、故障转供、黑启动等高风险操作，只通过已验收的设备侧顺控请求接口触发。

### 6.5 资源与时间预算模型

有效运行时上限按 `有效上限 = min(目标硬上限, 程序声明限额, 本次授权限额)` 取交集，必须为正数的限额字段缺失或为零时一律拒绝（不解释为无限制）。同时执行**指令步骤预算**（保障计算复杂度可重复）和**单调时间预算**（捕获平台过载），在目标平台测得基准参数后按以下关系核定容量：

```text
单任务扫描预算 = 获取快照成本 + 最大允许步骤数 × 单步成本上界 + HostCall 成本 + 提交审计成本

系统峰值内存   = 基础运行时 + 当前活跃程序 + 待激活候选程序 + 必要回退对象
               + 快照区 + 工作状态区 + 命令与日志队列 + 线程栈 + 安全余量

端到端响应延迟 = 现场采集 + 等待下一扫描节拍 + 调度与计算 + 仲裁与排队 + 通信传输 + 设备动作时间
```

需注意，单核总利用率 $\sum (C_i / T_i) < 1$ 只是满足调度的必要条件，常规嵌入式 Linux 的内核调度、中断及驱动阻塞仍须通过目标板长时压力测试检验最坏观察延迟。

### 6.6 热加载生命周期与状态迁移

为解决现有热加载“先停旧再逐个启新”带来的控制断档、失败回退盲区和状态丢失问题，新运行时采用单协调器入口，将**候选准备**与**在线切换**彻底分离：

```text
  ACTIVE ──► PREPARING ──► READY ──► QUIESCING ──► ACTIVATED_OBSERVING ──► COMMITTED
                │            │           │                   │
                ▼            ▼           ▼                   ▼
             REJECTED    REJECTED   ISOLATED_FAULT   ROLLBACK / 受控停用
```

| 阶段转换 | 核心动作 | 失败与超时处置 |
| --- | --- | --- |
| `PREPARING → READY` | 从统一入口读入一次性不可变字节，校验 SHA-256 摘要并执行加载器七步验证；完成工作内存与线程创建握手，**所有候选线程停在屏障前且不持有任何输出权限** | 任一检查或第 N 个任务创建失败，仅撤销并回收候选资源；原运行代次不受任何影响 |
| `READY → QUIESCING` | 通知旧版本任务在安全点停止接纳新周期（利用可唤醒等待设置停止截止期）；盘点在途设备命令并导出可迁移状态，暂不销毁旧对象 | 若旧线程在截止期内未确认停止（例如阻塞在旧原生调用），将其隔离标记为 `ISOLATED_FAULT`，**绝不强杀线程、覆盖对象或用 `running=false` 伪装停止成功，并禁止激活候选** |
| `QUIESCING → ACTIVATED_OBSERVING` | 在同一个同步锁边界内切换活跃代次 `activeGeneration` 并撤销旧版本发送预约资格，随后放行候选程序；观察首轮及试运行窗口内的品质、预算与命令反馈 | 若切换前失败则恢复旧代次；若切换后首轮异常，立即撤销新代次权限并核对在途命令，再决定回退或进入受控停用 |
| `ACTIVATED_OBSERVING → COMMITTED` | 观测指标满足批准门槛，将候选包记为 `last-known-good` 持久发布记录，确认无人引用后释放旧代次对象 | 若确认存在无法接管的未知外部状态，转入维护停机并告警 |

- **状态迁移契约**：跨版本迁移严格依据稳定的任务与实例身份、类型、状态 Schema 及兼容配置摘要匹配（禁止直接 `memcpy(privateData)`）。不同类别状态的处理建议如下：

| 状态类型 | 推荐迁移策略 |
| --- | --- |
| 纯计算临时值（`local` / `cycle`） | 不迁移，下一周期重新计算 |
| PI / 积分状态 | 配置摘要兼容时迁移有效数值；限幅或系数改变时按预设规则修正或复位 |
| 边沿触发历史 | 点位与触发方式未变时保留；否则重新建立基线并在首轮抑制误触发 |
| 定时器 / 采样窗口 | 按功能块契约声明停顿期是否继续计时；不跨系统重启复用单调时钟坐标 |
| 控制请求与反馈 | 保留独立的动作账本跨代次持续追踪，不随脚本重置丢弃 |
| `retain` 持久状态 | 按带版本的持久 Schema 校验迁移，失败则落入预设复位与人工确认流程 |

- **发布记录与掉电恢复**：持久发布记录明确区分“候选包已验证”“已激活未确认”和“已确认可用”三种状态，将各写盘点掉电后的恢复规则定义清楚。遇到包文件损坏、动作账本不一致或未确认状态掉电时，阻止自动下发控制动作并保留现场供对账，不根据目录下哪个 JSON 修改时间最新就盲目加载。建议保留 inotify 作为触发机制，但在初始化顺序上改为**先建立监听再做初次对账**（避免启动窗口漏掉更新），辅以周期巡检补漏与 watch 自动重建。

| 加载器 → VM | 只读 `VerifiedProgram`、预分配 `frameArena`、预算限额 | 单轮计算结果与暂存意图，交由周期协调器决定提交或丢弃 |
| VM → 宿主 | 当前周期标识与带代次句柄 | 读取冻结快照或写入工作副本/意图队列，禁止直调底层驱动 |
| 发布 → 运行 | 已验候选、就绪状态与停机反馈 | 发布协调器独占代次切换；确认旧线程与回调均脱离引用后才释放资源 |

各环节输出的诊断信息统一采用 `stage, code, severity, messageArgs` 结构（源码定位附 `sourceDigest, documentId, taskId, elementId, portId, startByte, endByte`，运行定位附 `generation, cycleId, functionIndex, pc`），自动化校验直接比对错误码、参数和位置而不依赖中文提示文案。

### 7.3 立项前待拍板问题与必采硬件参数

立项评审建议重点拍板以下 8 项方向（不影响离线原型的先行验证）：

1. 编辑形态是否采用“保留图形 + 新增 `SCRIPT` 块 + 结构化子图”混合方案；
2. 生产阶段选用自研类型化栈式 VM 还是 Wasm 等成熟受限后端（依据实测对照报告决策）；
3. 存量配置与新执行引擎采用显式切换隔离而非自动混跑；
4. 是否严格冻结“无裸指针、无递归、扫描期零动态分配”语言红线；
5. 跨任务数据隔离方式与统一输出仲裁边界；
6. 并离网、黑启动等高风险动作仅通过已验收的设备侧顺控请求接口开放；
7. 跨重启状态首期默认复位，`retain` 变量待评估闪存寿命与掉电一致性后单独开放；
8. 首期热切换失败或未知状态回退优先要求人工介入确认，不盲目自动反复重启。

此外，制定生产级 Profile 限额前，必须从目标设备实测采集以下参数（在缺乏实测数据时，仅在离线原型中使用参考测试限额，不提前拍板生产级容量或耗时指标）：

- 目标终端型号、CPU 架构（如 Cortex-A7）与主频、可用内存、Linux 内核版本、交叉编译器与浮点选项；
- 当前业务线程调度策略、真实扫描周期分布与最大调度抖动，以及其他在跑规约的 CPU/内存基线；
- 实时库能否提供一致快照、品质位和源采集时标，以及写入状态回报与并发锁耗时；
- 遥控、遥调及参数写入底层公共接口的最大阻塞时长、返回语义、队列容量及重复请求表现；
- 典型现场策略的点数规模、数组大小、调用深度、循环次数与端到端允许延迟；
- 哪些业务必须满足硬实时（保留在硬件或专用保护模块中），哪些可在 Linux 用户态周期调度下运行。

## 8. 策略示例与分层验收标准

> 说明：本章示例与验收向量用于对齐目标语言语义与测试预期，属于拟议的 VCL 设计形态，尚未在当前软件中实现。

### 8.1 典型策略设计示例

#### 示例一：跨周期推进的顺控状态机（禁止循环内等待）

并网恢复、转供或孤岛切换等顺控过程绝不能在 VM 内部用循环反复读取实时库等待设备反馈，而应通过每次扫描计算一次状态迁移，借助独立 `request_id` 与异步账本跨周期推进：

```text
  IDLE
    总许可、通信品质与设备健康度持续满足确认时间
      ──► 发出一笔带唯一 request_id 的顺控请求 ──► WAIT_FEEDBACK

  WAIT_FEEDBACK
    收到匹配 request_id 的成功反馈 ──► COMPLETE
    收到失败反馈或单调时钟等待超时 ──► FAULT
    上位撤销运行许可               ──► 发出撤销请求 ──► CANCEL_PENDING

  CANCEL_PENDING
    收到设备明确撤销确认 ──► IDLE
    超时或无法确认状态   ──► FAULT（锁定策略并告警，要求人工现场处置）

  COMPLETE / FAULT
    按安全契约维持或撤销本策略出力；满足显式复归/复位条件后 ──► IDLE
```

即使收到撤销请求，设备也可能已经执行了一部分动作；状态机必须显式容纳 `UNKNOWN` 分支，超时后转人工确认，避免盲目下发相反操作引发设备误动。

#### 示例二：四台设备按可用容量分配功率（VCL 纯函数）

该函数作为纯计算 `SCRIPT` 节点接入画布：上游图形节点先对 4 台设备的额定容量与可用状态完成品质校验并构成数组，函数返回的标量设定值交由下游输出仲裁器校验并执行。函数体本身不读 RTDB、不发遥调（以下仅演示单向非负分配的语法表达，实际充放电正负号按项目点表约定）：

```c
function f64 allocate_one(
    i32 selected,
    f64 request_kw,
    in f64 capacity_kw[4],
    in bool available[4])
{
    if (selected < i32(0) || selected >= i32(4)) {
        return f64(0);
    }
    if (request_kw <= f64(0)) {
        return f64(0);
    }

    local f64 total_kw = f64(0);
    local i32 i = i32(0);

    @max_iterations(4)
    for (i = i32(0); i < i32(4); i = i + i32(1)) {
        if (!available[i] || capacity_kw[i] <= f64(0)) {
            continue;
        }
        total_kw = total_kw + capacity_kw[i];
    }

    if (total_kw <= f64(0)) {
        return f64(0);
    }
    if (!available[selected] || capacity_kw[selected] <= f64(0)) {
        return f64(0);
    }

    local f64 accepted_kw = request_kw;
    if (accepted_kw > total_kw) {
        accepted_kw = total_kw;
    }
    return (accepted_kw / total_kw) * capacity_kw[selected];
}
```

| 测试输入（4 台容量 / 可用性） | 请求功率 | 预期输出 | 验收关注点 |
| --- | --- | --- | --- |
| `[10, 20, 30, 40]` / 全可用 | `50` | `5, 10, 15, 20` | 按比例正常分配 |
| `[10, 20, 30, 40]` / 全可用 | `150` | `10, 20, 30, 40` | 总量限幅至 `100`，各台不超额 |
| 任意容量 / 全不可用 | `50` | `0, 0, 0, 0` | 总容量为 0 时防除零返回 |
| `[10, 20, 30, 40]` / 仅 0、1 号可用 | `30` | `10, 20, 0, 0` | `continue` 跳过不可用设备 |
| 任意 / 含 `BAD` 品质点 | 任意 | 拒绝或走预设降级 | 不将坏品质替为有效 `0` |

### 8.2 七层测试与分步投运策略

每项能力必须按七个层次独立留存证据（低层次通过不替代高层次验证）：

1. **工程文件往返测试**：验证含错误草稿、布局注释、稳定端口 ID 与绑定关系的保存与打开无损。
2. **编译前端与后端测试**：验证词法、类型、确定赋值、区域分析、资源估算及确定性打包。
3. **恶意/畸形包独立拒绝测试**：直接构造越界、假跳转、未知必需能力、资源虚报与类型不合流的执行包交给设备验证器，确保零激活、零内存泄漏。
4. **跨实现对拍**：围绕同一组黄金输入与时间序列，使“语言规范参考 → C# 离线解释器 → 嵌入式同源 C VM 宿主 → 目标设备”比对返回值、中间轨迹、状态与错误码（遇到问题时修代码或修正共享契约，不以任一端错误输出临时改写预期）。
5. **影子宿主接口测试**：用内存点表与模拟命令队列覆盖实际 C 适配层。
6. **目标板压力与硬件在环（HIL）测试**：注入断网、BAD 品质、队列满、激活失败、停止超时与掉电，建议评审基准不少于 **10 万轮软件状态回放、24 小时目标负载运行及 1000 次自动重载/拒绝/回退组合**。
7. **现场六步分阶段投运**：
   1. 离线环境全量编译与对拍；
   2. 目标设备上以**影子模式**运行，仅记录输出意图不接实控；
   3. 绑定现场最终点表，逐点核实单位、极性、功率正负方向与刷新品质；
   4. 在保持真实控制禁止或试验限幅下，验证命令反馈、许可撤销与超时处置；
   5. 经批准后逐项放开常规调节（高风险顺控只通往已验收的顺控请求）；
   6. 投运前必须实际演练回退流程——确认撤销输出许可后，老配置能否顺利接管当前设备运行态、是否会重发启动命令以及哪些过程必须人工复位。

#### 核心语言与运行时黄金语义测试表

| 验证类别 | 测试场景 | 期望结果 |
| --- | --- | --- |
| 优先级与除法 | `i32(1)+i32(2)*i32(3)`；`i32(-7)/i32(2)` | `7`；向零截断得 `-3` |
| 短路与静态检查 | `false && (i32(1)/i32(0) > i32(0))`；`false && unknown_name()` | 前者返回 `false`；后者编译期拒绝未知符号 |
| 算术与移位边界 | `i32` 最大值加 1、`u32(0) - u32(1)`、`u32` 移位 32 位 | 报告 `NUMERIC_OVERFLOW` 或移位越界错误 |
| 局部变量与数组 | 读取未赋值 `local`；长度 4 访问下标 `4` 或 `-1` | 编译器或设备验证器拒绝，动态越界报 `BOUNDS` |
| 常量高精度往返 | `u64` 最大值经 JSON 执行包往返 | 完整精确保留，不经过 `double` 截断 |
| 控制流与限额 | `for` 内 `continue`、`do/while` 首轮假条件、嵌套 `break`、超上限迭代 | 跳转落点精确、`do` 至少执行 1 次、仅退出最内层、超限报 `LOOP_LIMIT` |
| 预算与工作副本 | 内层调用耗尽父任务预算；第 N 步失败前修改了 `state` | 共享预算不重置；失败后已提交主 `state` 保持不变，故障计数更新 |
| 时间与实例 `dt` | 墙钟回拨、错过节拍、连续两轮失败后第 3 轮恢复、超过 `maxDt` | 单调预算不受影响；不重入；实例 `dt` 基于上次成功提交计算，超阈报 `INVALID_DT` |
| 分支缓存与数学 | 本轮直接引用未选分支旧计算结果；常量/动态调用 `sin_deg` | 静态检查拒绝（跨周期值必须走 `state`）；常量折叠与运行结果完全一致 |
| 命令事务与账本 | 本轮提交前失败；前轮已 `SENT` 本轮失败；发送或确认异常 | 本轮零命令入队；前轮动作账本不回滚；异常记录 `FAILED`/`UNKNOWN` 不假装撤销 |
