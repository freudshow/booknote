# Linux 线程调度入门：从 CPU 如何分工说起

当几个程序同时运行时，为什么有的任务一直在计算，有的任务却像“停住了”？为什么提高优先级不一定能让程序更快？要回答这些问题，先不必记住一串接口名，而要弄清楚：线程现在是在等 CPU，还是在等别的东西。

## 1. 从只有一张工作台的工坊说起

想象一间工坊里有一张工作台，几位工人都需要使用它。有人拿齐材料，随时可以开工；有人正在等材料送来；还有人必须等别人归还工具。管理员只需要从“已经准备好”的工人中，决定接下来让谁使用工作台。

Linux 的调度器就有些像这位管理员：CPU 是工作台，线程是工人。调度策略决定谁先获得执行机会，但不能让尚未送到的数据提前到达，也不能直接替别人释放锁。

这个类比有边界。真实 CPU 执行的是机器指令，不会每执行一行程序就换一个线程；线程切换也有开销。此外，中断可能打断当前执行，多核机器则像有多张工作台。下面的时间线都是帮助理解规则的示意，不是实际运行时间的保证。

## 2. CPU、进程、线程和内核分别是什么

**CPU** 是执行指令的处理器。一个处理器可以包含多个核心；有些核心又能向操作系统呈现多个逻辑 CPU。对调度器来说，逻辑 CPU 是安排线程执行的位置。本文说“单核示例”时，指相关线程只能在同一个逻辑 CPU 上执行，不涉及同一物理核心内的硬件线程共享。

**进程**可以理解为程序运行时的一组资源，包括地址空间、打开的文件等。**线程**是其中的一条执行路线。同一个进程可以有多个线程，它们共享许多资源，但各自有执行位置和栈。例如，一个线程处理输入，另一个线程整理数据，它们不必同时做同一件事。

在 Linux 中，调度通常以线程为单位。同一进程里的两个线程可以有不同的调度策略和优先级。一个线程同一时刻最多在一个逻辑 CPU 上执行；一个多线程进程则可能同时使用多个逻辑 CPU。[1]

**内核**是操作系统管理硬件和系统资源的核心部分，**调度器**是内核中负责安排执行机会的机制。应用线程调用系统服务时，也可能进入内核执行；这不等于它变成了“内核线程”。内核线程则是由内核管理、承担内核工作的独立执行实体。二者都可以作为线程参与调度。

还要区分线程与中断：硬件发出中断后，内核可能先运行硬中断处理代码。**硬中断处理不是普通线程**，不能用应用线程的优先级数字直接给它排队。部分中断工作可以在线程中完成，但不能因此把所有中断都看作线程。

## 3. 先问有没有运行资格，再问谁优先

线程大致有两种值得先分清的处境。第一种是已经准备好，只缺 CPU，称为**可运行**；第二种是还在等待某个条件，例如定时器到期、数据到达或锁被释放，暂时不能执行，通常称为睡眠或阻塞。

正在 CPU 上执行的线程自然也具备运行资格。工具有时把“正在运行”和“可运行但正在排队”都显示成同一种状态，所以看到可运行，不代表它此刻正在消耗 CPU。

等待条件满足后，线程被**唤醒**，重新进入可运行竞争。唤醒只是拿到了入场资格，不等于立即坐上工作台。谁先执行，还要看所在 CPU、调度策略、优先级以及其他限制。

如果一个线程尚未主动停下，调度器就让它暂停，把 CPU 交给另一个线程，这叫**抢占**。例如，更高实时优先级的线程被唤醒时，通常会抢占正在执行的低优先级线程；但如果内核此刻处于暂时不能抢占的执行区间，切换仍可能延后。调度不是逐行交替，共享数据也不能靠猜测切换时机来保证正确。

## 4. 普通调度：尽量公平，而不是每人固定分一秒

多数日常应用使用普通调度策略，接口名是 `SCHED_OTHER`。它要兼顾公平和响应性：一直计算的线程需要取得进展，刚收到输入、只需短暂处理的线程也不应无谓地久等。[1]

普通线程可以有一个“谦让程度”，称为 **nice 值**。这里的**权重**是竞争资源时使用的正数比例，例如权重为 2 和 1，表达前者希望取得后者两倍的服务，而不是优先级高者先一直运行。Linux 的 nice 范围通常是 -20 到 +19，数值越小，竞争 CPU 时的权重越大；数值越大，越愿意把机会让给别人。Linux 按线程维护 nice 值。nice 影响竞争份额，但不是“保证占用多少 CPU”的合同，也不是实时优先级。

先看一个有条件的例子：只有一个逻辑 CPU，A、B 都使用普通调度、nice 相同，处于同一公平竞争范围，始终可运行；忽略其他任务、分组限制和切换开销。长时间观察时，二者通常会大致分享 CPU。若把 A 的 nice 调得比 B 小，A 通常会得到更大的份额，但不能只凭相差几个数字就断言 A 一定占整机的某个百分比。[1]

反过来，若同一单核示例中只有 A 可运行，B 正在等输入，A 不必为了“公平”空等 B，可以使用空出的 CPU。公平调度分的是实际发生的竞争，不是把 CPU 永久切成几份。

实现公平需要先记账：谁已经得到多少服务，谁相对落后；还需要决定下一次先服务谁。旧资料常把这一体系称为“完全公平调度器”（英文 Completely Fair Scheduler，简称 CFS）。本文固定的 Linux v6.6 已引入一种把“是否欠它服务”与“下一次请求先后”分开处理的选择机制，其名称是“最早的有资格虚拟截止时间优先”，英文 Earliest Eligible Virtual Deadline First，简称 EEVDF。这里先把它理解成公平调度的内部选人办法；第 11 节才逐一定义“资格”和“虚拟截止时间”。它们不是两个需要应用手动选择的策略，普通调度也不是固定时间片的简单轮流。[11]

## 5. 实时调度：更明确的先后顺序，不是算得更快

这里的“实时”强调**及时响应和执行顺序**，不是给线程换了一颗更快的 CPU。把同一段计算改成实时调度，指令本身不会因此变快；如果它等的是磁盘、网络或锁，提高调度优先级也不能消除这些等待。

Linux 的两种常见固定优先级实时策略是“先进先出”策略 `SCHED_FIFO` 和“轮转”策略 `SCHED_RR`。二者的实时优先级范围都是 1 到 99，数字越大越优先。这里的 50 与 nice 的数值没有换算关系。[1]

在同一 CPU 上，若线程都具备运行资格、实时预算未受限，并暂不考虑更高调度类别和中断等因素，FIFO/RR 实时线程优先于普通线程。即使普通线程的 nice 是 -20，也不会因此越过实时优先级为 1 的线程。

但这仍不是**硬实时保证**。硬实时系统要求对截止时间作严格保证，需要分析计算上界、锁等待、内核延迟及设备响应等整条路径。仅设置 FIFO 或 RR，不能证明任务一定在某个时刻前完成。

### 5.1 FIFO：同级不会因为时间到了就自动轮换

FIFO 的关键规则是：先选更高优先级的可运行实时线程；同级再按队列次序选择。当前线程不会仅因“已经运行得够久”就自动把机会交给同级线程。它通常会持续执行，直到阻塞、主动让出、退出，或被更高优先级线程抢占；预算限制另论。[1]

设只有一个逻辑 CPU，A、B 都是优先级 50 的 FIFO 线程，初始 A 在前，二者持续可运行；忽略实时限流、其他任务、中断和切换开销。结果可能是 A 一直运行，B 一直等待。这里没有“过 10 毫秒自然轮到 B”的规则。

在另一个同样的单核、忽略限流和开销的示例中，A 是 FIFO 50，B 是 FIFO 60。A 从 0 毫秒开始执行，B 原先在等待，到 3 毫秒时被唤醒并变得可运行。B 通常会抢占 A；若 B 运行 2 毫秒后又阻塞，那么约 5 毫秒时 A 可以继续。B 的优先级高，改变的是取得 CPU 的顺序，而不是那 2 毫秒计算本身的速度。

### 5.2 RR：增加的是同优先级线程之间的轮换

RR 大体沿用 FIFO 的规则，但增加了**时间片**：线程用完自己的时间片后，移到同一优先级队列的末尾。这里的“同一优先级”非常重要。[1]

设只有一个逻辑 CPU，A、B 都是 RR 50，始终可运行，初始 A 在前；忽略实时限流、其他任务、中断和开销，并仅为示意假设时间片是 10 毫秒。它们的执行次序可以画成：

```text
时间（毫秒）  0          10         20         30         40
CPU          |    A     |    B     |    A     |    B     |
```

这不是说所有系统的 RR 时间片都是 10 毫秒。实际时间片可以通过轮转间隔查询接口 `sched_rr_get_interval()` 获取；它也不是线程的工作周期。[2]

若在这个单核模型中，A、B 仍是持续可运行的 RR 50，另外还有一个持续可运行的 RR 40 线程，且仍忽略限流等因素，那么 A、B 的轮换**不会自动给 RR 40 留出机会**。调度器仍优先选择 50 这一层。

再把示例改成只有 A=RR 50、B=RR 40，二者持续可运行，单核且忽略限流、其他任务和开销。A 的时间片结束时，同级没有竞争者，它仍可继续运行；时间片结束不是降级，也不是保证 B 运行的信号。

### 5.3 唤醒和让出，不要理解成“立刻换人”

仍以单核、忽略限流及其他干扰为前提：如果 A=RR 50 正在执行，B=RR 60 被唤醒并可运行，B 通常会抢占 A。如果 B 也是 RR 50，它通常进入同级队列末尾，**不必立即抢占 A**。A 被更高优先级抢占后，再恢复执行时，会继续使用尚未耗尽的 RR 时间片。[1]

FIFO 和 RR 本身没有谁天然高一等。比如在单核、双方均可运行且忽略限流等因素时，RR 60 优先于 FIFO 50，FIFO 60 也优先于 RR 50。同级混用则不保证均分：如果持续不阻塞的 FIFO 50 已在前面运行，后面的 RR 50 也可能一直等不到。

还有一种主动“让出”的操作，接口名是 `sched_yield()`。对 FIFO/RR，它让当前线程排到自身优先级队列末尾，不是把机会捐给所有低优先级线程。因此，在单核、A=RR 50 与 B=RR 40 均可运行、忽略限流等因素的例子中，即使 A 反复让出，仍可能立即再次选中 A。反复调用让出接口，不能替代真正等待事件。[1]

## 6. 休眠、I/O 和锁：CPU 不是唯一要等的资源

### 6.1 请求睡 20 毫秒，不等于每 20 毫秒执行一次

休眠是线程主动等待一段时间，常见接口有 `nanosleep()`。正常完成休眠时，请求时长过去，只意味着线程可以重新争取 CPU；计时精度和调度等待都可能使真正恢复执行的时刻更晚。如果休眠被信号中断，则还要根据返回结果处理尚未完成的等待。[5]

考虑一个单核示例：A 每轮计算需要 3 毫秒，随后请求休眠 20 毫秒。假设计算期间 A 能连续执行、休眠正常完成，没有额外 I/O、锁等待和限流，暂忽略计时及切换开销。第一轮从 0 毫秒开始，3 毫秒时休眠，约 23 毫秒时才重新可运行。所以即使唤醒后立刻执行，相邻两轮起点也约隔 23 毫秒，而不是 20 毫秒。

在这 20 毫秒等待中，若 B 可运行且没有其他竞争者，B 可以使用 CPU；若所有线程都在等待，CPU 则可能空闲。若 A 到 23 毫秒时醒来，却有更高优先级线程持续运行，A 的下一轮还会更晚开始。

要维持接近固定节拍，可以按预定的绝对时间点等待，而不是每轮做完后再从头等一段相对时间。绝对时间休眠接口 `clock_nanosleep()` 的相应模式能减少这种累计漂移，但无法消除调度延迟，也需要明确错过一个时间点时如何处理。[6]

### 6.2 调用 I/O，不一定真的睡眠

输入输出操作常简称 I/O。线程读取数据时，如果数据尚未到达，操作可能让它阻塞，其他可运行线程于是有机会执行。如果数据已经在缓存里，读取也可能马上返回，根本没有一段可供别人使用的等待时间。

同样，调用内核接口不等于让出 CPU。内核代码可能等待事件而睡眠，也可能一直检查设备状态而忙等。忙等仍在执行指令，仍会消耗 CPU。解释运行表现时，要分清“花了很长的实际时间”与“真正用了很多 CPU 时间”：前者可能主要是在等待。

### 6.3 优先级反转：高优先级也可能被低优先级拖住

锁用来保护不能同时访问的共享资源。线程 A 拿到锁后，线程 B 若也需要这把锁，通常必须等 A 释放。此时 B 即使优先级很高，也无法仅凭调度优先级绕过锁。

最典型的**优先级反转**还涉及第三个线程。假设只有一个逻辑 CPU，A 是低优先级实时线程，已持锁；高优先级 B 请求同一把锁而阻塞；一个不需要这把锁的中优先级线程持续可运行。忽略限流和其他干扰后，中优先级线程可以压住 A，A 不能及时释放锁，B 也就跟着久等。高优先级 B 的进度，反而间接受中优先级线程控制。

一种缓解方法叫**优先级继承**：锁的持有者暂时借用等待者的较高优先级，以便尽快完成临界区并释放锁。**临界区**是持锁保护的那段访问共享资源的代码；**互斥锁**保证同一时刻只有一个使用者进入它。POSIX 是一组操作系统接口规范，其中的互斥锁接口可以通过相应协议请求优先级继承，常量是 `PTHREAD_PRIO_INHERIT`；它需要正确初始化并得到实现支持，不是所有锁自动具备的属性。[7]

优先级继承不能解决死锁，也不能使无限长的锁内工作变得有界。缩短持锁时间、避免在锁内做慢操作，依然是理解和改善响应的重要基础。

## 7. 多核和 CPU 百分比：先弄清分母

多核意味着不同线程可能真正同时执行。假设有两个可用逻辑 CPU，A、B 均可运行，允许使用这两个 CPU，没有共享锁等待、限流或其他任务。即使 A 的优先级高于 B，B 也可能在另一 CPU 上同时运行。单核示例中“高优先级持续占住 CPU”的结论，不能直接扩大成“整台多核机器都停止工作”。

不过，线程可能被限制在某些 CPU 上，这叫**CPU 亲和性**。有四个逻辑 CPU 的机器，如果 A、B 都只允许使用同一个 CPU，它们依然会发生单核竞争。即使它们分处不同 CPU，共享锁、设备和内存资源也仍可能让它们互相等待。

CPU 使用率必须说明统计口径。设有四个可用逻辑 CPU，一个线程持续可运行并连续占用其中一个，其余 CPU 空闲；忽略中断及统计误差。在“一个逻辑 CPU 算 100%”的口径下，这个线程约为 100%；在“整机所有 CPU 合计算 100%”的口径下，则约为 25%。同一工作量，两种显示都可能合理。

若四核上的一个进程有两个线程，各自占满一个逻辑 CPU，在上述相同前提下，按单 CPU 口径汇总的进程使用率可以约为 200%，并不是显示出错。单个线程则不能在同一时刻同时占用两个逻辑 CPU。

再回到单核示例：如果 A 每轮连续计算 3 毫秒，再正常等待 20 毫秒，且能立即恢复运行，忽略其他等待和开销，那么它长期的 CPU 使用率约为 `3 ÷ 23 ≈ 13%`。它完全可能具有很高实时优先级，却只用很少的 CPU；优先级与 CPU 使用率不是一回事。

还要看统计窗口。常见的 `top` 动态显示通常依据相邻采样区间，而 procps 版本的 `ps` 所显示的 `%CPU` 通常是累计 CPU 时间与存活时间的比值。因此，刚开始忙碌的线程在两个工具里可能显示不同数值。系统总 CPU 统计还会包含中断等开销，不能把一个线程的数值当成整机全部工作。[8]

## 8. 如何只读观察正在发生什么

先区分两个编号：**进程编号 PID** 用于定位进程，**线程编号 TID** 用于定位具体线程。一个进程中的每个线程都有自己的 TID；主线程的 TID 通常与进程 PID 相同。查询主线程的属性，不能代表整个进程的所有线程。线程库使用的 `pthread_t` 也不能直接当作这里的 TID。[1]

下面只使用查询形式。将 `PID` 或 `TID` 替换为实际数字；示例分别采用 procps 的 `ps`、`top` 和 util-linux 的 `chrt` 语法。

```sh
ps -L -p PID -o pid,tid,comm,cls,rtprio,ni,psr,stat,pcpu
top -H -p PID
chrt -p TID
```

第一条逐线程列出属性，第二条在支持这些选项的版本中动态显示指定进程的线程，第三条只查询指定线程的调度策略和优先级，不设置新优先级。[8][9]

| 列名 | 阅读方式 |
|---|---|
| `PID`、`TID`、`COMMAND` | 所属进程、具体线程及其名称；名称不是唯一身份 |
| `CLS`、`RTPRIO`、`NI` | 调度类别、实时优先级、nice；普通线程的实时优先级可能显示为 `-` |
| `PSR` | 最近执行的 CPU 编号，不是永久绑定位置 |
| `STAT` | 状态；`R` 包含正在运行与可运行，`S` 常表示可中断睡眠，`D` 表示不可中断睡眠 |
| `%CPU` | CPU 时间占比，需要结合工具、采样窗口和归一化方式解释 |

例如，看到一个线程类别为 RR、实时优先级为 50，只说明查询时它具有这样的属性；如果状态是等待，它不会因此一直使用 CPU。看到 `R` 却 CPU 占用低，则可能是在排队，也可能与统计窗口有关。`D` 常见于某些 I/O 等待，但仅凭这个字母不能确定原因。[8]

有些精简系统使用 BusyBox 版本，可能没有上述全部选项、列或命令；应以所用版本的帮助信息为准。读取失败或字段不存在，是缺少证据，不应当作数值为零。先观察多个采样窗口，再把策略、状态和 CPU 占用放在一起理解，通常比只盯一个优先级数字更有意义。

## 9. 创建线程时，策略从哪里来

理解运行规则之后，还需要知道线程如何获得这些属性。使用 POSIX 线程库创建线程时，新初始化的属性对象默认采用**继承调度属性**的方式。此时，新线程继承的是调用创建接口的那个线程的策略和调度参数，而不是无条件使用普通策略。[3]

例如，若 A 当前实际使用 RR 50，A 创建 B，并采用继承方式，B 就会继承 RR 50。“创建 B 时没有单独设置优先级”不等于“B 一定是普通线程”。反过来，如果 A 是普通线程，继承也不会凭空把 B 提升为实时线程。

对应的属性选项叫 `PTHREAD_INHERIT_SCHED`。若希望按属性对象中指定的策略和参数创建，需要选择**显式调度属性**，即 `PTHREAD_EXPLICIT_SCHED`。只填写参数，却仍采用继承方式，不能据此断言新线程会使用所填的参数。[3]

请求实时策略还涉及权限。系统可能通过专门的调度管理权限以及用户可使用的实时优先级上限来限制它，并不只是简单地区分“是不是管理员”。即使准备属性的操作成功，创建线程时仍可能因权限不足而失败。[1][4]

程序必须检查接口的返回结果。POSIX 线程接口通常直接返回错误码：例如创建接口 `pthread_create()` 成功返回 0，失败返回相应错误码，不能只查看全局错误变量 `errno` 就当作已经检查。最终还应区分“准备请求的值”和“线程实际生效的值”。[4]

## 10. 把规则写成一个独立的 C 程序

已经知道线程的属性从哪里来，现在可以看一个不依赖其他文件的例子。它不是压力测试，也不试图测出最坏延迟；目的只是展示：显式准备属性、检查创建结果、在线程内核对实际属性、做有界工作、等待绝对时间点，最后回收线程。

### 10.1 先解释程序将用到的工具

Linux 上常用的 POSIX 线程库接口以 `pthread_` 开头。**属性对象**是创建前准备的一组设置，不是已经运行的线程。**回收线程**指调用 `pthread_join()` 等它退出并取得结果，避免把“创建成功”误当成“工作已经完成”。

先认识阅读示例所需的几条 C 规则：`struct` 把相关字段组合成结构，`&对象` 取得地址，指针参数让函数访问原对象，`指针->字段` 访问其中一项；`NULL` 表示空指针。线程入口的 `void *` 是通用指针，传入后转回实际结果结构类型。`static` 在这里限制辅助函数只在当前源文件使用；`#include` 引入接口声明，`_POSIX_C_SOURCE` 在头文件之前声明所需的 POSIX 接口版本。

`if (e)` 在 `e` 非零时执行后面的语句；`!` 表示逻辑取反，所以 `if (!e)` 在 `e` 为零时执行。本例把直接返回的错误号存入 `e`，因此前者处理失败，后者才继续下一步；不是所有 C 接口都用这套成功约定。`return` 结束当前函数：`worker()` 中的 `return NULL` 结束这条工作线程的入口函数，`main()` 中的 `return 1` 则以失败状态结束程序，`return 0` 表示成功。`struct result r = {0}` 把这个结果结构的所有整数字段初始化为零，因而尚未记录错误时 `r.error` 为零。

`pthread_create(&thread, &attr, worker, &r)` 中的 `worker` 是交给线程库的函数入口，不是此处直接调用的 `worker()`；线程库让新线程调用它，并把 `&r` 作为入口参数 `arg`。于是信息沿着“主线程传入 `&r` → 工作线程把 `arg` 转为结果结构指针 → 写入结果 → 主线程在 join 成功后读取”的顺序传递。`for` 重复一段工作，`++` 增加一，`break` 结束当前循环；花括号把多条语句合成一个代码块。下面的逐步说明会把这些规则与线程生命周期对应起来。

计时使用**单调时钟** `CLOCK_MONOTONIC`：它不会因为人为修改日历时间而向后跳，适合描述等待间隔；它并不意味着线程可以准时得到 CPU。`struct timespec` 把时间拆为秒 `tv_sec` 和纳秒 `tv_nsec`；1 秒等于 1,000,000,000 纳秒。`TIMER_ABSTIME` 表示等待到某个绝对时钟坐标，而非从调用时起再等一段时长。

程序选择每轮完成后至少再等约 20 ms：若已经错过预定点，就从当前时刻重新安排下一次。这是**跳过过期节拍而不追赶**的策略，防止延迟后连续补做多轮。它与严格保留原始相位的周期设计不同，也不能用于证明每秒执行 50 次（50 Hz）的保证。

`uint64_t` 是精确 64 位的无符号整数，算术溢出按模运算定义；`UINT64_C` 为常量选取相应类型。固定次数的整数运算用来表示一点有限工作，不代表“恰好计算几毫秒”。校验和让结果可见，但不禁止编译器优化，所以更不能拿循环次数估算最坏耗时。

### 10.2 完整用户态示例

下面是**独立 C11 程序，不是内核源码**。它固定请求普通策略，没有实时模式开关。程序不修改其他线程、亲和性或系统预算，不提供提权、关限流或更改线上配置的命令。

```c
#define _POSIX_C_SOURCE 200809L
#include <pthread.h>
#include <sched.h>
#include <time.h>
#include <stdint.h>
#include <stdio.h>
#include <string.h>
#include <errno.h>

struct result {
    int policy, priority, error;
    uint64_t checksum;
};

static int fail(const char *where, int e)
{
    fprintf(stderr, "%s: %s\n", where, strerror(e));
    return 1;
}

static struct timespec after_20ms(struct timespec t)
{
    t.tv_nsec += 20000000L;
    if (t.tv_nsec >= 1000000000L) {
        ++t.tv_sec;
        t.tv_nsec -= 1000000000L;
    }
    return t;
}

static void *worker(void *arg)
{
    struct result *r = arg;
    struct sched_param sp;
    struct timespec next, now;
    int e = pthread_getschedparam(pthread_self(), &r->policy, &sp);
    if (e) { r->error = e; return NULL; }
    r->priority = sp.sched_priority;
    if (clock_gettime(CLOCK_MONOTONIC, &next) == -1) {
        r->error = errno; return NULL;
    }
    uint64_t x = UINT64_C(1);
    for (unsigned round = 0; round < 5; ++round) {
        for (unsigned j = 0; j < 10000; ++j)
            x = x * UINT64_C(1664525) + UINT64_C(1013904223);
        if (clock_gettime(CLOCK_MONOTONIC, &now) == -1) {
            r->error = errno; return NULL;
        }
        if (now.tv_sec > next.tv_sec ||
            (now.tv_sec == next.tv_sec && now.tv_nsec > next.tv_nsec))
            next = now;
        next = after_20ms(next);
        for (unsigned retry = 0; ; ++retry) {
            e = clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME,
                                &next, NULL);
            if (!e) break;
            if (e != EINTR || retry == 7) {
                r->error = e; return NULL;
            }
        }
    }
    r->checksum = x;
    return NULL;
}

int main(void)
{
    const int policy = SCHED_OTHER;
    struct sched_param sp = { .sched_priority = 0 };
    pthread_attr_t attr;
    pthread_t thread;
    struct result r = {0};
    int e = pthread_attr_init(&attr);
    if (e) return fail("pthread_attr_init", e);
    const char *where = "pthread_attr_setschedpolicy";
    e = pthread_attr_setschedpolicy(&attr, policy);
    if (!e) {
        where = "pthread_attr_setschedparam";
        e = pthread_attr_setschedparam(&attr, &sp);
    }
    if (!e) {
        where = "pthread_attr_setinheritsched";
        e = pthread_attr_setinheritsched(&attr, PTHREAD_EXPLICIT_SCHED);
    }
    if (!e) {
        where = "pthread_create";
        e = pthread_create(&thread, &attr, worker, &r);
    }
    int cleanup = pthread_attr_destroy(&attr);
    if (e) {
        if (cleanup) fail("pthread_attr_destroy", cleanup);
        return fail(where, e);
    }
    int joined = pthread_join(thread, NULL);
    if (joined) return fail("pthread_join", joined);
    if (cleanup) return fail("pthread_attr_destroy", cleanup);
    if (r.error) return fail("worker", r.error);
    if (r.policy != policy || r.priority != sp.sched_priority)
        return fail("actual scheduling attributes differ", EINVAL);
    if (printf("policy=OTHER priority=%d checksum=%llu\n",
           r.priority,
           (unsigned long long)r.checksum) < 0)
        return fail("printf", errno);
    if (fflush(stdout) == EOF) return fail("fflush", errno);
    return 0;
}
```

保存为 `sched_demo.c` 后，在具有 Linux 头文件及 POSIX 线程库的环境中，可以只做编译而不执行：

```sh
cc -std=c11 -Wall -Wextra -Wpedantic -pthread -c sched_demo.c -o sched_demo.o
```

这条命令只产生目标文件，不启动程序；它不是调度行为验证。Windows 原生 C 编译器即使存在，也不能据此当作已验证 Linux 的 `clock_nanosleep()` 与 pthread 接口。

### 10.3 按执行顺序理解，而不是只抄接口名

1. `main()` 固定请求 `SCHED_OTHER`，普通策略的 `sched_priority` 必须是 0；没有通过参数意外开启实时模式的可能。
2. `pthread_attr_init()` 成功后才有可用属性对象。后续三个设置依次准备策略、参数和显式方式；任一步失败，都不会继续创建线程。这里刻意不用继承，保证普通模式不会因创建者原本是 RR 而意外继承 RR。
3. `pthread_create()` 成功才存在需要回收的线程。属性对象随后可销毁；销毁失败也不能忘记回收已经创建的线程。创建失败时报告错误，不自动切换其他方式重试，避免把“请求值”与“实际值”混在一起。
4. `worker()` 先查询自身属性并记录，不在每轮打印。它最多做 5×10,000 次算术，等待中若反复被信号打断，也最多尝试 8 次；因此没有无界实时忙循环或无限重试。**算法步骤有界不等于墙钟退出时间有硬上界**：若它一直拿不到 CPU、输出阻塞或底层环境异常，完成仍可能推迟。
5. 每轮先做有限工作，再取当前时刻。若进度已迟于上一个参考点，就把参考点推进到现在，再加 20 ms；纳秒超过一秒时进位。这相当于主动放弃追赶积压节拍，不能把它说成严格固定周期。
6. 绝对休眠被信号中断时，错误码是 `EINTR`；再次等待仍用同一个 `next`，不把整段等待重新加一次。`clock_nanosleep()` 和 pthread 接口直接返回错误号；`clock_gettime()` 则以 -1 表示失败，错误号从 `errno` 取。混用这两种检查方式会报告错因。[4][6][12]
7. 主线程只有在 `pthread_join()` 成功后才读取工作结果；这是线程间同步，不需靠“应该已经写完”的时间猜测。`checksum` 不是 `volatile`，也不是共享计数实验。若 join 意外失败，程序报告错误并结束，不继续读取可能仍被写入的结果。
8. `printf()` 放在工作线程退出之后，减少工作路径中流锁和终端 I/O 的影响，并检查输出及刷新缓冲的结果。**缓冲**是先暂存输出、稍后再交给目的地；`fflush()` 请求送出这些暂存内容。它们仍不是无成本操作；程序也没有防止缺页带来的额外等待。缺页指需要的内存页尚未以可访问状态准备好、须由内核处理后才能继续，因此不能用这个例子宣称已满足硬实时条件。

正常完成时，程序可汇总显示实际策略、优先级和计算校验和；等待使它不会持续保持可运行。它不会输出每轮延迟，因而不能据此测出 20 ms 精度、最坏唤醒延迟或公平份额。普通策略的成功也不能证明实时权限存在。

若只想学习 RR 请求，可看下面独立的用户态辅助函数：它需要完整示例中相同的 pthread、sched 和 errno 头文件及接口声明环境；调用者必须先成功初始化属性对象。函数只填写属性，不创建线程，不是完整程序的默认路径。`sched_get_priority_min()` 以 -1 表示失败并设置 `errno`，pthread 属性函数则直接返回错误号；辅助函数统一把错误号返回给调用者。

```c
static int prepare_lowest_rr(pthread_attr_t *attr)
{
    struct sched_param sp = {
        .sched_priority = sched_get_priority_min(SCHED_RR)
    };
    if (sp.sched_priority == -1) return errno;
    int e = pthread_attr_setschedpolicy(attr, SCHED_RR);
    if (!e) e = pthread_attr_setschedparam(attr, &sp);
    if (!e) e = pthread_attr_setinheritsched(attr, PTHREAD_EXPLICIT_SCHED);
    return e;
}
```

即使辅助函数返回 0，随后创建仍可能返回权限错误 `EPERM`，应直接报告，不默默改用继承。Linux 的 `CAP_SYS_NICE` 是允许某些调度管理操作的能力位；`RLIMIT_RTPRIO` 是无相应能力时可请求实时优先级的资源上限，还可能有容器和安全策略限制。属性准备成功不等于拥有权限。最低 RR 也优先于普通线程，不能把它当成线上随意尝试的安全等级；理解代码不需要启动实时负载。[1]

### 10.4 两段短代码能改变什么，不能改变什么

如果只想查询**调用者自己的** RR 时间片（也称量子），可以在一个已有函数里写下面的用户态片段；使用完整示例中的 POSIX 声明环境以及 `<sched.h>`、`<time.h>`、`<stdio.h>`、`<string.h>`、`<errno.h>`。`0` 表示调用线程，`q` 的单位仍是秒加纳秒；错误要从 `errno` 取。这是在查询而不是设置，不能用返回量子推导工作周期，也不能仅凭普通线程的查询结果断言它正在按 RR 运行。[2]

```c
struct timespec q;
if (sched_rr_get_interval(0, &q) == -1) {
    fprintf(stderr, "sched_rr_get_interval: %s\n", strerror(errno));
    return 1; /* 片段假定所在函数返回 int */
}
```

第 6 节讲过锁的优先级继承。下面的独立辅助函数演示如何**在初始化时请求协议**，不是在锁已使用后临时改变它。它需要完整示例的 POSIX 声明环境，以及 `<pthread.h>`、`<stdio.h>`、`<string.h>`；这里只展示初始化，不是完整的加锁、解锁和退出流程。[7][13]

```c
static int init_inheriting_mutex(pthread_mutex_t *m)
{
    pthread_mutexattr_t a;
    int e = pthread_mutexattr_init(&a);
    if (e) return e;
    e = pthread_mutexattr_setprotocol(&a, PTHREAD_PRIO_INHERIT);
    if (!e) e = pthread_mutex_init(m, &a);
    int cleanup = pthread_mutexattr_destroy(&a);
    if (e) return e; /* m 未成功初始化，不能使用 */
    if (cleanup) {
        /* m 已初始化；不能把清理属性失败误报成 m 不存在。 */
        fprintf(stderr, "pthread_mutexattr_destroy: %s\n", strerror(cleanup));
    }
    return 0;
}
```

先创建锁属性，再请求 `PTHREAD_PRIO_INHERIT`，最后用这个属性初始化互斥锁；任一步拒绝都把原始错误号交给调用者。属性对象随后销毁，不会销毁已初始化的锁。辅助函数返回 0 表示锁可使用；属性清理的异常另报。真正调用时还必须检查每次加锁和解锁的返回值，并在没有使用者后销毁锁。继承只帮助持锁者尽快完成有限临界区，不会让慢 I/O、死锁或不受控制的持锁时间自动消失。

## 11. 从执行份额推导公平调度的记账

前面的程序能验证接口使用方式，却没有解释普通调度为什么能形成不同份额。现在从需求推导内部记账：先有“公平要达到什么”，再有“内核需要存什么”。本节的 CPU 时间是线程真正执行消耗的时间；经过时间还包括排队和等待，二者不能混算。

### 11.1 权重怎样变成具体数字

设同一级公平竞争中线程编号为 `i`，其正权重为 `w_i`，总权重为 `W = Σw_i`；`Σ` 表示把所有参与者的量相加。权重没有时间单位。在可供这些线程分配的 CPU 时间 `H` 内，目标长期份额和执行时间近似为：

```text
p_i = w_i / W              （份额，无量纲）
s_i ≈ H × p_i              （执行时间，和 H 同单位）
```

Linux v6.6 的权重表中，nice 0 对应 1024，nice 5 对应 335，来源是 `core.c` 的 `sched_prio_to_weight[]`，不是按 nice 数字线性相减。[14] 因而两者竞争时，总权重为 1359，份额约为 `1024/1359 = 75.35%` 和 `335/1359 = 24.65%`。如果 `H=100 ms`，可近似分到 75.35 ms 与 24.65 ms。

这些数字假定：同一个逻辑 CPU、两者持续可运行、同一级公平竞争；没有不同分组改变层级分配，没有配额节流和迁移扰动；中断及更高调度类别消耗已经扣除或忽略；观察区间足够长，忽略离散选择与整数舍入。**100 ms 是可分配执行时间，不是每个自然的 100 ms 窗口都兑现的合同。**

这里的**分组**指内核先把 CPU 服务分给一组任务，再在组内分配。例如控制组 cgroup 可以组织资源分配层级，自动任务分组 autogroup 也会影响竞争范围。不同组中的两个线程，不能只把各自权重相加就算整机份额。普通公平组的 CPU 配额也可能在一段预算用尽后暂时禁止继续执行，这叫节流；它不是下面 FIFO/RR 的实时预算机制。[1][15]

### 11.2 为什么要有虚拟运行时间

若 A 本来应该得到 B 约三倍服务，就不能看到 A 实际执行更多便认为它“不公平”。需要把不同权重的执行量换成统一刻度。定义基准表权重 `w_0=1024`，每次新增实际执行时间为 `Δt_i`，其中 `Δ` 表示增量，则：

```text
Δv_i = Δt_i × w_0 / w_i
```

`v_i` 是累计的**虚拟运行时间**，Linux 字段名为 `vruntime`。若实际时间以纳秒计，结果可称“虚拟纳秒”：这是按无量纲比例缩放后的服务坐标，不是日历时刻。高权重线程实际运行相同时间，虚拟账增加较少；因此在同样的虚拟进度中，它可以获得更多实际时间。

按上例，A 实际运行 1 ms，虚拟增加 1 ms；B 实际运行 1 ms，虚拟增加 `1024/335 ≈ 3.057 ms`。长期分到 75.35 ms 和 24.65 ms 后，两者虚拟增量反而接近相同：`75.35×1 ≈ 24.65×1024/335 ≈ 75.35` 虚拟 ms。这就是按权重公平的记账含义。

公式里的 1024 是权重表基准。内核可能为整数精度统一放大内部权重，尤其 64 位配置下的 `NICE_0_LOAD` 不能不看定义就断言字面值总为 1024；统一缩放不改变上面的权重比。

### 11.3 公平账之外，为什么还需要“资格”和“虚拟截止时间”

只知道累计服务还不足以安排下一小段工作。把一个线程希望得到的一段服务称为一次**执行请求**：这里是调度器安排的请求长度，不是应用的一整项业务，也不是应用报告的最坏执行时间。公平算法既要防止已经超前的人继续占便宜，又要在可服务的人中安排先后。

先用固定参与集合的教学模型。共同虚拟参考 `V` 是虚拟运行时间的加权平均：

```text
V = Σ(w_i × v_i) / Σw_i
α_i = w_i / w_0
L_i = α_i × (V - v_i)
```

`α_i` 是归一化权重，无量纲；`L_i` 是以服务时间表达的**落后量**。`L_i>0` 表示相对公平参考还欠它服务，`L_i<0` 表示它已超前。于是 `v_i≤V` 与 `L_i≥0` 等价，称为**有资格**。它与第 3 节“可运行”不是同一个概念：线程可能可运行，却在这一轮公平选择中因服务已经超前而暂时不具备资格。

为每次执行请求保存一个虚拟起点 `v_i_start`，请求实际长度为 `r_i`，其**虚拟截止时间**记为 `d_i_v`：

```text
d_i_v = v_i_start + r_i × w_0 / w_i
```

`r_i` 与实际 CPU 时间同单位；`d_i_v` 与虚拟运行时间同单位。这个名字里的“截止”只表示服务请求在虚拟坐标中的排序目标，**不是承诺线程在真实时钟几点前完成业务**。EEVDF 的基本思想由此可以完整说出：先看谁有资格，再从有资格者中优先考虑虚拟截止时间更早的请求。

举一个纯教学的瞬间：A、B、C 权重相同，虚拟运行时间分别为 4、5、9 虚拟 ms，所以 `V=(4+5+9)/3=6`。A、B 有资格，C 暂无资格。假定它们当前请求的虚拟起点分别为 4、2、9，请求长度均为 6 ms，则虚拟截止时间分别为 10、8、15 虚拟 ms。基本选择规则会考虑 B，而不是虚拟运行时间最小的 A。这是一个内部状态快照，不宣称仅凭这些数值就能重现整个 Linux 时间线；真实实现还有当前请求继续执行的条件。

Linux v6.6 默认开启名为 `RUN_TO_PARITY` 的特性，可以在特定状态下让已选中且仍有资格的当前实体继续执行。因此不要把基本模型写成“每一瞬间都立刻切换到最早虚拟截止时间者”。同样不能把 v6.6 写成旧式“总是选最小 `vruntime`”：第 15 节会看到真实记账与请求更新代码。[11]

## 12. 从及时响应走到可以分析的期限

公平回答“长期分多少”，实时分析还要回答“某次工作能否按期完成”。这需要换一套描述工作需求的量，不能把虚拟截止时间直接挪来用。

### 12.1 四个不同的目标

**吞吐量**是单位经过时间完成多少项工作，例如每秒处理 1000 个请求。**调度响应延迟**是线程变为可运行，到第一次真正执行的间隔。**完整响应时间**是一次工作从释放到全部完成的经过时间，包含执行、排队和可能的阻塞。**截止期**则是允许完成这次工作的时间限制。相同延迟在不同次事件间的变化叫**抖动**。

例如，把一个 10 ms 的连续计算切成十段，可能让输入处理更早插入，降低首次响应延迟；但切换和缓存干扰有成本，总吞吐未必增加。一个请求很快获得第一次执行，也不表示它的最后一段能按期完成。“实时”强调满足时间约束，不等于吞吐最大、平均延迟最小或 CPU 占用最高。硬实时要求在已知条件下对必须满足的期限作严格保证；软实时允许一定程度的超期，但超期会降低服务质量。

### 12.2 先定义任务，再定义一次作业

实时理论把反复到来的一类工作叫**任务**，一次具体到来的工作叫**作业**。这是建模用语；内核里的 `task` 往往指一个可调度线程，不要把两个含义混为一谈。

对第 `i` 个任务，定义：

- `T_i`：周期；对不是严格周期到来的偶发任务，则是两次释放的最小间隔，单位 ms。
- `C_i`：一次作业的最坏 CPU 执行时间上界，英文 Worst-Case Execution Time，简称 WCET，单位 ms。它不是随便测一次的耗时，也不包括等 CPU 或等锁的时间。
- `D_i`：相对截止期，从释放开始最多允许多久完成，单位 ms。
- `a_i,k`：第 `k` 次作业的释放时刻；绝对截止时刻是 `d_i,k=a_i,k+D_i`。
- `f_i,k`：该作业的完成时刻；完整响应时间 `R_i,k=f_i,k-a_i,k`，按期要求是 `R_i,k≤D_i`。

周期是一种到达需求，不是“操作系统保证每隔 T 毫秒运行一次”。在实际系统中，必须对锁等待、缺页、设备和中断等另作分析；可信的 `C_i` 还取决于执行平台与工作范围。

### 12.3 利用率能说明什么，不能说明什么

任务的**利用率**是长期 CPU 需求比例 `U_i=C_i/T_i`，总需求为 `U=ΣU_i`，没有单位。每 10 ms 需要最多 2 ms 执行，对应 0.2。单核长期需求若超过 1，单靠换一种算法不能凭空创造执行时间；但 `U<1` 也不自动保证任意短期限都能满足。

一种理想算法是按每次作业的**真实绝对截止时刻**排序，期限更早者先运行，英文 Earliest Deadline First，简称 EDF。假设一个理想单处理器，任务独立、可抢占，不存在锁、I/O 自行挂起和依赖；调度、切换、中断等开销忽略或已保守计入；到达周期或最小间隔已知，且所有任务 `D_i=T_i`。在这个经典模型中，EDF 可调度的条件为 `U≤1`。[16]

例如 A 为 `C=2 ms, T=D=10 ms`，B 为 `C=3 ms, T=D=15 ms`，总利用率 `2/10+3/15=0.4`。同步从 0 释放时，A 的期限为 10，B 的期限为 15；可先执行 A 的 2 ms，再执行 B 的 3 ms。30 ms 内 A 到来三次、B 到来两次，总需求为 `3×2+2×3=12 ms`，与 40% 一致；真正保证来自上述模型下的可调度结论，不是只画一轮便证明所有情况。

若把两个任务都改成 `C=2 ms,T=10 ms,D=2 ms`，总利用率仍为 0.4，却会在同时释放后的头 2 ms 内要求执行 4 ms 工作，单核不可能完成。这说明当 `D<T` 时，短时间需求可以比长期平均更苛刻。

另一种办法是**速率单调分配**，英文 Rate Monotonic，简称 RM：周期越短，给越高的固定优先级。固定是指不随每次作业的绝对期限重新排序。Linux FIFO/RR 提供固定实时优先级机制，但不会自动测量周期并替应用完成 RM 分配；是否按期，仍需分析高优先级干扰和阻塞。

### 12.4 为什么 SCHED_DEADLINE 不是 EEVDF

Linux 的 `SCHED_DEADLINE` 是用户可请求的另一种策略，通常以运行预算 `runtime`、相对调度期限 `deadline` 和周期 `period` 描述需求，满足 `0<runtime≤deadline≤period` 等参数约束。预算表示每周期可消耗的执行时间；若工作超过预算，就不能假定仍会连续执行。它结合 EDF 与**恒定带宽服务器**，英文 Constant Bandwidth Server，简称 CBS。这里的“服务器”不是网络服务器，而是为任务管理预算、截止状态和补充规则的调度抽象，用以限制超额执行对别人的干扰。[16]

**准入检查**是接受请求前检查可用调度带宽和相关约束，不是读懂业务函数。即使准入成功，应用仍要保证执行需求、到达模式及阻塞等符合设计。普通 pthread 的 `sched_priority` 不能设成 100 来获得它；Linux 通常通过专门的 `sched_setattr()` 接口请求，本文不提供修改策略的可执行片段。[1][17]

EEVDF 服务普通公平类，使用按权重缩放的虚拟服务坐标，不替应用预约真实截止期；`SCHED_DEADLINE` 使用真实调度时间和预算机制。后者的**内核调度截止时刻**也未必就是某一项业务的绝对截止时刻：预算服务器会依状态调整自身的调度参数，应用释放与业务期限仍须正确对应。内核用不同结构保存两套状态：普通公平实体中的 `deadline` 是虚拟期限，deadline 类实体中的同名字段是另一种坐标，不能因名字相同便互相替代。

普通调度还有面向批处理的 `SCHED_BATCH`、极低优先级后台工作的 `SCHED_IDLE`。BATCH 仍在公平体系内，不是始终低于所有 OTHER 的一条固定层；IDLE 用户策略也不是 CPU 无事可做时的内核空闲线程。至此，六种常见用户策略的用途都已出现，而不是只剩一串需要背诵的名称。

## 13. 进入内核：先建立实现地图

接下来的问题不再是“应用请求什么”，而是“内核如何记住并落实规则”。本节先引入存储结构和处理步骤，再看小段源码。所有内核摘录固定 **torvalds/linux 的 v6.6 标签**；行号链接指原文件行号，代码前后省略的部分都会注明。它们不是完整函数调用环境，不应复制到用户程序编译。

### 13.1 为什么需要每 CPU 的管理结构和调度类

多核机器必须同时作出多个局部选择，所以内核为每个逻辑 CPU 维护自己的**运行队列管理结构**，英文 runqueue，源码常缩写为 `rq`。它不仅是一条排队链表，还保存该 CPU 当前任务、时钟和不同调度机制的队列状态。线程允许去哪些 CPU、何时迁移，还要由亲和性和迁移逻辑约束。v6.6 `core.c` 的 `runqueues` 每 CPU 定义及 `__schedule()` 对 `cpu_rq(cpu)` 的使用体现了这种组织。[18]

不同策略需要不同选人办法，内核把它们组织为**调度类**：一组实现入队、选择、时钟更新等操作的方法。FIFO 和 RR 都交给实时类 `rt`，普通公平策略交给公平类 `fair`，期限策略交给 `dl`。**策略是应用接口上的请求，类是内核实现机制**，两者并非一一对应。

v6.6 在链接时排列的类顺序是 `stop → dl → rt → fair → idle`，`__pick_next_task()` 会从可选类中取得任务，公平路径另有快速分支。[18][19] `stop` 用于内核特殊控制，`idle` 类承接没有普通任务可选时的空闲任务；二者不是应用可以随意设定的策略。这是可调度任务的选择关系，不是把硬中断也放进来的宇宙优先级表。

同一 CPU 上，组也可能分层竞争：实时队列中某个实体可能代表一组，下一级才是线程。因此前面的扁平队列时间线，都隐含“相同队列层级、无额外分组影响”。

### 13.2 从唤醒到执行，中间为什么不是一步

线程需要等待时，内核把它从可运行竞争中移出；事件到达后，再检查状态、处理并发并选择目标 CPU。v6.6 的 `try_to_wake_up()` 承担唤醒路径的一部分，不是简单地调用一次“立刻切过去”。常规激活路径会先入队，再判断当前线程是否应被抢占。[18]

下面是真实局部源码：**v6.6 `kernel/sched/core.c`，`ttwu_do_activate()`，L3787—L3790**。省略函数前面的计数、标志处理及后续回调：[原文](https://github.com/torvalds/linux/blob/v6.6/kernel/sched/core.c#L3787-L3790)。`rq` 是目标 CPU 的管理结构，`p` 是被唤醒任务，两个 flags 参数携带唤醒和入队相关条件。

```c
    activate_task(rq, p, en_flags);
    check_preempt_curr(rq, p, wake_flags);

    ttwu_do_wakeup(p);
```

第一行把任务激活到可运行竞争；第二行比较当前运行者与新任务，判断是否需要请求抢占；第三行完成相应唤醒状态处理。它没有表示 `p` 已经执行到下一条用户指令，也不是所有并发唤醒分支的完整表示。

如果需要换人，先设置**重新调度标记**：它的含义是“到允许时重新选择”，而不是标记一写入便已切换。下面是真实局部源码：**v6.6 `core.c`，`resched_curr()`，L1053—L1060**，省略前面的任务取得和已有标记检查，以及后面的其他分支：[原文](https://github.com/torvalds/linux/blob/v6.6/kernel/sched/core.c#L1053-L1060)。

```c
    if (cpu == smp_processor_id()) {
        set_tsk_need_resched(curr);
        set_preempt_need_resched();
        return;
    }

    if (set_nr_and_not_polling(curr))
        smp_send_reschedule(cpu);
```

`curr` 表示当前任务，`cpu` 是目标 CPU；`smp_processor_id()` 取得调用处所在 CPU。若目标就是本 CPU，设置两个调度相关标记后返回；若是另一 CPU，必要时用**处理器间中断**通知它，英文 Inter-Processor Interrupt，简称 IPI。发送通知不是替另一 CPU 直接完成现场切换。

实际允许进行选择的时机可称为**调度点**。阻塞等待会进入调度，时钟和唤醒可能产生重调度请求，返回用户态或离开可抢占限制区间时也可能处理请求。v6.6 `__schedule()` 前 L6538—L6574 的注释专门解释这些条件：[原文](https://github.com/torvalds/linux/blob/v6.6/kernel/sched/core.c#L6538-L6574)。禁止抢占或关闭中断的区间、硬中断等会推迟处理，所以“高优先级唤醒可抢占”不是零纳秒承诺。

### 13.3 选中了另一个线程，具体切换什么

**上下文**是线程将来继续执行所需的处理器执行状态，例如寄存器和栈的位置。**上下文切换**要保存旧线程状态并恢复新线程状态，必要时调整地址空间相关状态；不是把进程的全部堆、全局变量和内存复制一遍。同进程线程共享地址空间，不代表共享同一个执行位置。

v6.6 `core.c` 的 `context_switch()`，L5320—L5385，包含 `switch_mm_irqs_off()` 和最终 `switch_to()`；后者继续进入架构相关实现：[原文](https://github.com/torvalds/linux/blob/v6.6/kernel/sched/core.c#L5320-L5385)。具体保存哪些寄存器取决于架构和相关路径，不能仅凭这一层函数列一张“所有 CPU 相同”的清单。切换后缓存和地址转换状态也可能影响后续速度，这解释了为何更频繁切换未必有更高吞吐。

## 14. 实时类如何落实 FIFO、RR 和预算

现在把前面的先后规则映射到数据结构：既然必须先找最高优先级，再找同级先来者，就需要“哪些级非空”的索引，以及每一级自己的排队结构；RR 还需要保存剩余量子。

### 14.1 用户数字为什么与内核数字反向

用户 API 的实时优先级越大越高，但内核通用优先级字段 `prio` 用越小越高的顺序。二者是不同表示，不要拿工具的 `PRI` 或源码内部数字直接当 `sched_priority`。

下面是真实局部源码：**v6.6 `core.c`，`__normal_prio()`，L2150—L2151**，只保留实时策略分支，前后的 deadline 与普通策略分支省略：[原文](https://github.com/torvalds/linux/blob/v6.6/kernel/sched/core.c#L2150-L2151)。

```c
    else if (rt_policy(policy))
        prio = MAX_RT_PRIO - 1 - rt_prio;
```

`rt_policy()` 判断是否为 FIFO/RR；`MAX_RT_PRIO` 在 v6.6 的 `include/linux/sched/prio.h` 定义为 100。[20] 因而用户 1 映射为 98，50 映射为 49，99 映射为 0。这里计算的是正常配置对应的优先级；锁的优先级继承可能使实际有效优先级临时不同，不能把这个公式当作所有时刻的最终值。

### 14.2 先找非空优先级，再取该级队首

**位图**是一组二进制标记，用每一位表示某个优先级是否存在可选实体；**链表**把同级实体按先后连在一起。这样不用挨个扫描所有线程才能知道最高非空级。下面是真实局部源码：**v6.6 `kernel/sched/rt.c`，`pick_next_rt_entity()`，L1776—L1782**，省略局部变量声明与末尾 `return next`：[原文](https://github.com/torvalds/linux/blob/v6.6/kernel/sched/rt.c#L1776-L1782)。

```c
    idx = sched_find_first_bit(array->bitmap);
    BUG_ON(idx >= MAX_RT_PRIO);

    queue = array->queue + idx;
    if (SCHED_WARN_ON(list_empty(queue)))
        return NULL;
    next = list_entry(queue->next, struct sched_rt_entity, run_list);
```

`array` 保存位图和各级队列。第一行找到最小置位索引，对应最高内部优先级；`BUG_ON` 是违反内核不变量时的严重检查，不是日常选人规则。接着定位这一优先级的队列；若队列意外为空就警告并返回空指针。最后通过 `list_entry` 从队首链表节点取得它所属的实时调度实体。若该实体代表组，上层选择流程还需继续向下找到任务。

这解释了三个应用层现象：RR 与 FIFO 共用实时类，并非 FIFO 天生高于 RR；RR50 的量子结束后仍先找最高级，不自动轮到 RR40；同级队首若是持续不阻塞的 FIFO，后面的 RR 也可能长期等待。

### 14.3 RR 到期为什么只改变同级轮转

本节的“量子”就是前文的 RR 时间片。为了判断量子到期，实时任务有一个剩余时间片字段 `p->rt.time_slice`，保存的是调度时钟节拍（tick）数，不是毫秒或纳秒。内核配置中的 `HZ` 表示每秒的节拍数，一个节拍名义上对应 `1/HZ` 秒；v6.6 的默认值定义为 `RR_TIMESLICE = (100 * HZ / 1000)`，见 [同一标签的 include/linux/sched/rt.h](https://github.com/torvalds/linux/blob/v6.6/include/linux/sched/rt.h)。这表示名义默认量子为 100 ms，不代表所有系统当前配置都相同。

时钟节拍处理路径对 RR 扣减这个计数，但 FIFO 不依靠 RR 量子轮换。此处一次扣减的计数单位是一节拍，用户查询接口再把间隔表示为秒和纳秒；不能仅凭下面的 `--` 推导精确的墙钟切换时刻。下面两块是真实局部源码，均来自 **v6.6 `rt.c`，`task_tick_rt()`**；第一块为 **L2652—L2658**：[原文](https://github.com/torvalds/linux/blob/v6.6/kernel/sched/rt.c#L2652-L2669)。函数前面的运行统计等公共工作省略。

```c
    if (p->policy != SCHED_RR)
        return;

    if (--p->rt.time_slice)
        return;

    p->rt.time_slice = sched_rr_timeslice;
```

不是 RR 就在此结束，不能把它误读成 FIFO 不记运行时间。RR 的剩余量子减一，非零仍可继续；变零后重装配置量子。随后跳过 L2659—L2663 的空行与解释注释，继续摘录 **L2664—L2669**；循环后部和函数闭合部分省略：

```c
    for_each_sched_rt_entity(rt_se) {
        if (rt_se->run_list.prev != rt_se->run_list.next) {
            requeue_task_rt(rq, p, 0);
            resched_curr(rq);
            return;
        }
```

`rt_se` 是任务自身及可能的组祖先实体。循环检查相应队列是否存在竞争实体；有则以参数 0 请求移到尾部，并标记需重新调度。`requeue_rt_entity()` L1566—L1578 的相应分支调用 `list_move_tail()`：[原文](https://github.com/torvalds/linux/blob/v6.6/kernel/sched/rt.c#L1566-L1578)。没有合适竞争者时，量子到期不必产生一次有意义的换人。真正下一次选择仍遵循最高非空优先级，而不是“这次用了 CPU，所以下次从所有剩余线程中选”。

### 14.4 没有 RR 时间片，不等于没有预算约束

**实时带宽预算**限制适用范围在一个周期内可消耗多少 RT 执行时间，目的之一是避免实时任务长期占满执行资源；它与 RR 的“同级每次轮多久”是不同问题。v6.6 源码默认周期为 1,000,000 μs，默认预算 950,000 μs，即 1 秒中的 0.95 秒；这是上游默认参数，不是任何具体设备读取结果。[10][21]

假设单 CPU、这些实时任务共享该预算、预算确实启用且耗尽、没有额外层级和例外：任务会受到节流，等预算补充后再竞争；此时可运行普通任务可能得到机会。RR50 和 RR40 若共享已耗尽的预算，后者不会获得单独的“剩下 5%”。高实时优先级但大部分时间在等待的线程，也可能只消耗很小比例。

v6.6 即使没有开启 `CONFIG_RT_GROUP_SCHED`（实时组调度配置），也有全局 RT 带宽限制；开启后增加组与层级管理。多 CPU 实现还有预算共享与平衡，优先级提升路径也存在例外；因此不能保证每个 CPU 都在自然一秒的第 950 ms 精确停下并交付连续 50 ms。预算设为不限或其他值时行为又不同。`sched_rt_runtime_exceeded()` 与 `update_curr_rt()` 展示了耗尽检查和运行记账：[原文 L998—L1086](https://github.com/torvalds/linux/blob/v6.6/kernel/sched/rt.c#L998-L1086)。这既不是每线程固定 95%，也不提供普通任务的延迟上界。

## 15. 公平类如何落实虚拟记账与请求选择

第 11 节已解释需要累计实际执行量、加权服务进度和当前请求终点，因此源码里出现这些字段就不再突兀。内核用一个**公平调度实体**表示参与公平竞争的线程或组，类型为 `struct sched_entity`，常缩写为 `se`；`struct cfs_rq` 表示某一级公平运行队列。历史名字仍含 CFS，不表示 v6.6 仍只按旧算法选人。[11][22]

读摘录还需认识两个整数类型：`u64` 是 64 位无符号整数，`s64` 是 64 位有符号整数；`->` 访问指针所指结构的字段；`unlikely()` 是帮助编译器安排分支的提示，不改变真假规则。下列代码都是**真实 v6.6 源码**，不是把公式改写后冠以内核函数名的伪代码。

### 15.1 先把实际时间换成虚拟增量

输入 `delta` 是实际执行增量，单位 ns；`se->load.weight` 提供内部权重，输出是对应虚拟增量。**v6.6 `fair.c`，`calc_delta_fair()`，L311—L317，完整函数**：[原文](https://github.com/torvalds/linux/blob/v6.6/kernel/sched/fair.c#L311-L317)。

```c
static inline u64 calc_delta_fair(u64 delta, struct sched_entity *se)
{
    if (unlikely(se->load.weight != NICE_0_LOAD))
        delta = __calc_delta(delta, NICE_0_LOAD, &se->load);

    return delta;
}
```

先比较实体权重与基准权重；若不同，用 `__calc_delta()` 进行比例缩放，内部采用整数运算而不是浮点；若相同就直接返回原增量。它对应 `Δt×w_0/w_i` 的意义，但不承诺与无限精度公式逐位相同。这个函数只算数，不执行线程切换。

### 15.2 为什么同时保留两种运行时间

实际累计执行量用于统计，虚拟累计量用于公平比较，二者都不能省。下面是 **v6.6 `fair.c`，`update_curr()` 内 L1173—L1178 的连续摘录**，完整函数为 L1150—L1189：[原文](https://github.com/torvalds/linux/blob/v6.6/kernel/sched/fair.c#L1150-L1189)。省略前面的当前实体取得、执行增量计算和后面的其他记账。`curr` 是当前公平实体，`delta_exec` 是自上次记账以来实际消耗的执行时间。

```c
    curr->sum_exec_runtime += delta_exec;
    schedstat_add(cfs_rq->exec_clock, delta_exec);

    curr->vruntime += calc_delta_fair(delta_exec, curr);
    update_deadline(cfs_rq, curr);
    update_min_vruntime(cfs_rq);
```

第一行把真实运行时间直接加到累计值；第二行更新队列执行统计，不是让线程又运行一次。随后用加权增量推进虚拟运行时间，检查请求是否耗尽，再维护队列最小虚拟时间基准。`update_min_vruntime()` 的存在不意味着“此处选择最小 vruntime 线程”：记账基准与最终选择规则是不同层次。

函数前面使用调度器的任务记账时钟 `rq_clock_task()` 与上次起点相减；它不是日历时钟，具体配置会考虑中断等非任务执行时间。因此不能把线程排队等了 10 ms 直接加成它实际执行了 10 ms。

### 15.3 当前请求用完后，怎样建立下一个虚拟终点

`se->slice` 是此次请求长度，`se->deadline` 是虚拟终点；`sysctl_sched_base_slice` 提供基准请求长度。下面是真实函数的**代码语句摘录**，**v6.6 `fair.c`，`update_deadline()`，L1019—L1043**；原函数中解释性注释已省略，位置用注释标记：[原文](https://github.com/torvalds/linux/blob/v6.6/kernel/sched/fair.c#L1019-L1043)。

```c
static void update_deadline(struct cfs_rq *cfs_rq, struct sched_entity *se)
{
    if ((s64)(se->vruntime - se->deadline) < 0)
        return;

    /* ... 省略原文解释性注释 ... */
    se->slice = sysctl_sched_base_slice;

    /* ... 省略原文解释性注释 ... */
    se->deadline = se->vruntime + calc_delta_fair(se->slice, se);

    /* ... 省略原文解释性注释 ... */
    if (cfs_rq->nr_running > 1) {
        resched_curr(rq_of(cfs_rq));
        clear_buddies(cfs_rq, se);
    }
}
```

第一项判断虚拟进度是否尚未达到当前终点，未达到就保留请求。达到后，取基准长度作为下一请求，用上一节的换算函数把实际长度转为虚拟长度，再加到当前虚拟时间上。如果队列有多个可运行实体，就请求重新调度，并清除旧的伙伴提示；伙伴提示是影响相关选择的内部状态，不是线程之间的业务关系。这里的 `resched_curr()` 依然只是请求，不是切换已经发生。

这也解释了为何 `slice` 不能直接叫“应用最坏计算时间”：它由调度器建立，应用函数可能要跨多次请求才能完成。

### 15.4 真正的选择器还做了什么

v6.6 `entity_eligible()`（L738—L753）落实资格判断，使用加权和的交叉相乘减少先除法造成的精度损失；`__pick_eevdf()`（L875—L967）与 `pick_eevdf()`（L969—L982）落实请求选择，`pick_next_entity()` 在 L5279 返回后者的结果：[资格判断](https://github.com/torvalds/linux/blob/v6.6/kernel/sched/fair.c#L738-L753)、[选择器](https://github.com/torvalds/linux/blob/v6.6/kernel/sched/fair.c#L875-L982)、[调用处](https://github.com/torvalds/linux/blob/v6.6/kernel/sched/fair.c#L5279)。

为了不用每次把所有实体扫描一遍，内核用**红黑树**这种保持平衡的有序树存放实体。此处不需要先学会旋转算法，只需知道它能利用有序关系快速查找。特别是 **v6.6 的树仍按虚拟运行时间排序，并保存子树最小虚拟截止时间 `min_deadline` 作为增强信息**。它不是某些后续版本中“按 deadline 排序、记录子树最小 vruntime”的实现，不能把后续代码说明倒灌到这个标签。[11]

选择器还要考虑当前实体是否仍可用、是否有资格，以及第 11 节提到的 `RUN_TO_PARITY`。该默认特性在 `features.h` 定义；`__pick_eevdf()` 中会在特定标记条件下继续返回当前实体。[23] 该处 `vlag` 字段被用于状态标记，不能仅凭名字把每次比较都解释成数学落后量。异常选择失败还有日志和回退路径，它们是防御性处理，不表示日常算法“其实仍总选最小虚拟运行时间”。

### 15.5 线程之外：中断和可抢占内核的边界

**中断请求**常写作 IRQ，表示硬件事件请求 CPU 处理。硬中断处理在特殊上下文执行，不是从普通线程队列中挑出的用户线程。适合延后的部分可以放进**中断线程**，它是可调度内核线程，会受到调度优先级与亲和性影响；软中断是另一种延后处理机制，可能在不同上下文执行，也不能统称为普通后台应用线程。

`PREEMPT_RT` 是使更多内核路径可抢占、改变若干锁机制并推动中断线程化的实时内核配置体系。v6.6 `kernel/Kconfig.preempt` 的 `PREEMPT_RT` 帮助仍明确保留入口、调度器和低层中断等关键路径的限制，可选性还取决于架构支持等条件。[24] 因此普通 Linux 能设 FIFO/RR，不代表已启用 PREEMPT_RT；启用也不意味着没有硬中断。

v6.6 `kernel/irq/manage.c` 中 `irq_thread()` 设置线程调度，`irq_setup_forced_threading()` 对带特定标记的中断有跳过规则：[函数所在固定版本文件](https://github.com/torvalds/linux/blob/v6.6/kernel/irq/manage.c)。这些函数是实现线索，不在此摘录未逐行展开的函数体。它们说明“全部中断无例外都成线程”不成立；应用 RT99 也不能凭线程优先级禁止所有硬中断。中断屏蔽、内核抢占和用户锁是不同层的机制，设置一个数字不能替代整条响应路径分析。

## 16. 把规则、理论和观察连起来

现在可以把一个“线程为何没及时工作”的问题按顺序拆开，而不先猜优先级够不够高：

1. **先看资格**：它是在等锁、数据、定时器，还是已经可运行？阻塞线程没有因为数字大就跳过等待条件的能力。公平算法内部的服务资格，还与一般可运行状态不同。
2. **再看竞争范围**：它能用哪些 CPU？是否与对手在同一 CPU、同一分组层级竞争？另一核空闲不代表这条线程允许迁移过去。
3. **然后看机制**：普通类按权重与请求状态安排服务；FIFO/RR 按实时优先级及同级规则；期限类则还要看预算和期限状态。不要把 RR 时间片、实时带宽周期、任务周期与虚拟请求长度当成同一个量。
4. **把经过时间拆开**：实际计算、等待调度、等锁、等 I/O、计时误差各占多少？首次得到执行与全部完成分别是什么时刻？只说“耗时 20 ms”不足以定位哪一层。
5. **最后解释证据**：CPU 百分比看统计分母和窗口，属性看具体线程，源码看固定版本与配置。假设时间线用于预测，程序返回值用于确认请求是否生效，运行跟踪和测量才能说明某个环境发生了什么。

最值得记住的主线不是某个默认数值，而是：**先有可运行工作，再有局部竞争；先明确分配目标，再引入记账；先定义真实期限，再讨论实时保证。** 高优先级不等于高占用，唤醒不等于执行，公平不等于固定周期，实时策略不等于已证明的硬实时系统。本文给出的是 Linux 通用接口规则、固定 v6.6 实现和声明假设下的数字推导；任何具体设备的内核配置、实际策略、RR 量子、预算、最坏延迟与可调度性仍需单独取得证据，不能用教程示例替代。
