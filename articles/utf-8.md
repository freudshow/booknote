在 UTF-8 里，合法首字节不是“只要看前两位是 110 就行”，而是必须满足“最短编码形式（shortest form）”：

	•  0x00..0x7F：1 字节
	•  0x80..0x7FF：2 字节
	•  0x800..0xFFFF：3 字节
	•  0x10000..0x10FFFF：4 字节

也就是说：

	•  一个码点如果能用 1 字节表示，就不能用 2/3/4 字节表示
	•  2 字节序列最小合法值是 0x80，不是 0x00
	•  所以 2 字节首字节的合法范围是 0xC2..0xDF，而不是 0xC0..0xDF

为什么 0xC0 / 0xC1 会导致“编码过长”？

因为 2 字节 UTF-8 的格式是：

	•  110xxxxx 10xxxxxx

其中首字节的前 3 位固定是 110，后 5 位给出高 5 位。
而最小的合法首字节是 0xC2，因为 0xC2 = 11000010，对应的高 5 位是 00010，最小能表示的代码点是 0x80。

反过来看 0xC0 和 0xC1：

	•  0xC0 = 11000000
	•  0xC1 = 11000001

这两个值的“高 5 位”非常小，解码后只会得到 0..127 这个范围。
但 0..127 本来就能用 1 字节 ASCII 表示，所以它们都是“过长编码”。

举例：

1) 0xC0 0x80

	•  先解码：
		•  (0xC0 & 0x1F) << 6 | (0x80 & 0x3F)
		•  = (0x00 << 6) | 0x00
		•  = 0

	•  结果是 0x00
	•  但 0x00 本来只需要 1 字节 0x00，不需要 2 字节
	•  所以这是“过长编码”

2) 0xC1 0xBF

	•  解码：
		•  (0xC1 & 0x1F) << 6 | (0xBF & 0x3F)
		•  = 1 << 6 | 63
		•  = 127

	•  127 也就是 0x7F
	•  但 0x7F 本来只需要 1 字节，不需要 2 字节
	•  也是“过长编码”

所以，0xC0 与 0xC1 不是“合法 2 字节开头”，而是“非法的过长编码前缀”。

这也是为什么在 src/protocol/oled/oled.c 里，get_utf8_bytes() 里写的是：

	•  if (c >= 0xC2 && c < 0xE0)

而不是：

	•  if (c >= 0xC0 && c < 0xE0)

它的核心目的就是：

	•  只接受真正合法的 2 字节 UTF-8 首字节
	•  排除 C0/C1 这种会产生“非最短编码”的非法情况

一句话总结：

“C0/C1 会产生 0..127 这样的码点，而这些码点本来就能用 1 字节表示，所以它们属于非最短编码，UTF-8 规范要求拒绝。”

一、UTF‑8 的目的与基本特点

	•  UTF‑8 是一种将 Unicode 码点（U+0000..U+10FFFF）编码为字节序列的可变长编码。设计目标包括兼容 ASCII、无字节序问题（不像 UTF‑16 要处理字节序标记）、自同步（从任何位置可找到字符边界）和尽量节省空间。
	•  ASCII（U+0000..U+007F）保持单字节不变，这使得很多以 ASCII 为主的文本在存储/传输上向后兼容。

二、字节模式与码点范围（按 RFC 3629） UTF‑8 把 Unicode 码点映射为 1..4 字节，其首字节有固定格式，后续字节都以 10xxxxxx 形式出现（即高两位为 10）。

	•  1 字节（ASCII）
	•  格式: 0xxxxxxx
	•  值: U+0000 .. U+007F
	•  2 字节
	•  格式: 110xxxxx 10xxxxxx
	•  合法码点范围: U+0080 .. U+07FF
	•  合法首字节范围: 0xC2 .. 0xDF（注意不是 0xC0/0xC1）
	•  3 字节
	•  格式: 1110xxxx 10xxxxxx 10xxxxxx
	•  合法码点范围: U+0800 .. U+FFFF，但要排除 UTF‑16 的代理区 U+D800..U+DFFF（这些不应编码为 UTF‑8）
	•  合法首字节范围: 0xE0 .. 0xEF（但 E0 和 ED 的后继字节有额外限制，见下）
	•  4 字节
	•  格式: 11110xxx 10xxxxxx 10xxxxxx 10xxxxxx
	•  合法码点范围: U+10000 .. U+10FFFF
	•  合法首字节范围: 0xF0 .. 0xF4（F5..FF 超出 Unicode 上限，所以不合法）

三、为什么不能接受 0xC0、0xC1（过长编码）

	•  2 字节的能表示的最小码点是 0x80（即 U+0080）。如果允许首字节为 0xC0（11000000）或 0xC1（11000001），它们与一个合法后续字节组合时会产生码点 0x00..0x7F（例如 0xC0 0x80 解码为 U+0000）。
	•  这称为“过长编码（overlong encoding）”：用多个字节表示一个本应用更短编码表示的码点（例如将 ASCII 用 2 字节表示）。UTF‑8 规范明确禁止过长编码，因为它破坏了规范化、可以被用作绕过安全检查（例如路径、字符串比较、字符集验证）的手段。
	•  因此合法的 2 字节首字节应从 0xC2 开始，排除 C0/C1。

举例：

	•  0xC0 0x80 解码：
	•  (0xC0 & 0x1F) << 6 | (0x80 & 0x3F) = 0 << 6 | 0 = 0x00 → 这是 U+0000，本应由单字节 0x00 表示 ⇒ 过长编码
	•  0xC1 0xBF 解码：
	•  (1 << 6) | 63 = 127 (0x7F) ⇒ 也属于 ASCII 范围

四、更多非法情况（除了过长编码）

	•  非法的续字节：续字节必须以二进制 10 开头（0x80 .. 0xBF）。如果出现 0xC0..0xFF 中的字节没有正确续字节，则序列非法。
	•  代理对（UTF‑16 surrogate）：U+D800 .. U+DFFF 不允许在 UTF‑8 中编码（这些是 UTF‑16 内部表示），任何 UTF‑8 解码得到这些码点都应视为非法。
	•  超出最大码点：Unicode 的最大码点是 U+10FFFF，任何编码出大于这个码点的序列（例如用 4 字节编码得到 > U+10FFFF 或使用 5/6 字节样式）都是非法。RFC 3629 将 UTF‑8 限制为最多 4 字节。
	•  不完整序列（缺少续字节）或多余的续字节也都是错误。

五、编码与解码的算法（简要）

	•  编码（把码点 U 转为字节）：
	•  如果 U <= 0x7F：单字节 0xxxxxxx
	•  否则若 U <= 0x7FF：两字节
		•  首字节: 110xxxxx = 0xC0 | (U >> 6)
		•  次字节: 10xxxxxx = 0x80 | (U & 0x3F)
		•  注意：首字节必须 >= 0xC2（即 U >= 0x80）

	•  否则若 U <= 0xFFFF 且不在代理区：
		•  首字节: 1110xxxx = 0xE0 | (U >> 12)
		•  后两字节: 10xxxxxx each
		•  对于 U 在 0x0800..0x0FFF 及特殊边界（当首字节为 E0 或 ED）要确保不产生过长或代理区

	•  否则若 U <= 0x10FFFF：
		•  四字节：首字节 11110xxx = 0xF0 | (U >> 18)；三个续字节均 10xxxxxx
		•  首字节需在 0xF0..0xF4 范围内（U <= 0x10FFFF）

	•  解码（从首字节判断长度并重建码点）：
	•  看首字节的高位模式（0, 110, 1110, 11110）：确定应读多少续字节
	•  验证每个续字节均在 0x80..0xBF
	•  重建码点并检查最短编码规则（即该码点确实需要该长度）以及不在代理区且不大于 U+10FFFF
	•  若任何检查失败，序列非法

六、首字节->长度的常用判断（示例）

	•  if (b < 0x80) => 1 byte (ASCII)
	•  else if (b >= 0xC2 && b <= 0xDF) => 2 bytes
	•  else if (b >= 0xE0 && b <= 0xEF) => 3 bytes (但对 E0 / ED 有额外限制)
	•  else if (b >= 0xF0 && b <= 0xF4) => 4 bytes
	•  其它值（0x80..0xBF，0xC0..0xC1，0xF5..0xFF）均为非法起始字节

特别注意：

	•  当首字节为 0xE0 时，第二字节必须 >= 0xA0（因为如果第二字节 < 0xA0，会导致过长编码，表示小于 0x800 的值）。
	•  当首字节为 0xED 时，第二字节必须 <= 0x9F（否则会进入代理区 U+D800..U+DFFF）。
	•  当首字节为 0xF0 时，第二字节必须 >= 0x90（防止过长编码，表示小于 U+10000 的值）。
	•  当首字节为 0xF4 时，第二字节必须 <= 0x8F（因为 U <= U+10FFFF）。

七、示例：几个常见字符的 UTF‑8 编码（十六进制）

	•  'A' (U+0041) => 41
	•  '¢' (U+00A2) => C2 A2
	•  '€' (U+20AC) => E2 82 AC
	•  '𝄞' (U+1D11E, 音符符号) => F0 9D 84 9E
	•  BOM（不推荐但可能存在） U+FEFF => EF BB BF（UTF‑8 BOM）

八、示例代码（验证首字节获取长度 / 简单验证） C 版（判断首字节能表示的长度；注意这只是示例，不做完整验证）：

```C
int utf8_leading_len(unsigned char c) {
    if (c < 0x80) return 1;
    if (c >= 0xC2 && c <= 0xDF) return 2;  // C2..DF: legal 2-byte start
    if (c >= 0xE0 && c <= 0xEF) return 3;
    if (c >= 0xF0 && c <= 0xF4) return 4;
    return 0; // invalid start byte (including C0/C1, 80..BF, F5..FF)
}
```

Python 版（演示验证一个字节串是否为合法 UTF‑8）：

```Python
def is_valid_utf8(data: bytes) -> bool:
    i = 0
    n = len(data)
    while i < n:
        b = data[i]
        if b < 0x80:
            i += 1
            continue
        # determine length
        if 0xC2 <= b <= 0xDF:
            needed = 1
            min_cp = 0x80
        elif 0xE0 <= b <= 0xEF:
            needed = 2
            min_cp = 0x800
        elif 0xF0 <= b <= 0xF4:
            needed = 3
            min_cp = 0x10000
        else:
            return False
        if i + needed >= n:
            return False
        # check continuation bytes
        cp = b & (0x7F >> needed)  # initial bits
        for j in range(1, needed+1):
            bj = data[i+j]
            if bj & 0xC0 != 0x80:
                return False
            cp = (cp << 6) | (bj & 0x3F)
        # reject overlong, surrogate, > 0x10FFFF
        if cp < min_cp or (0xD800 <= cp <= 0xDFFF) or cp > 0x10FFFF:
            return False
        i += needed + 1
    return True

```

（注：上面 Python 只是示意性逻辑，实际实现时要更细致地处理每个首字节的第二字节范围限制以更早地拒绝非法序列。）

九、与安全相关的注意事项

	•  一定要验证 UTF‑8 输入，尤其是从外部接收的路径、用户名、URL、JSON 字段等，防止过长编码用来绕过过滤器。
	•  使用成熟库（iconv、ICU、语言自带的 decode/encode 函数）通常比手写更可靠。
	•  在处理“字符数”时区分“码点数（code points）”、“UTF‑16 代码单元数（在某些 API 中）”与“用户感知的字符（grapheme cluster）”。例如 emoji 家族会由多个码点组成。
	•  注意字符串索引：在 UTF‑8 中按字节索引通常与“第 n 个字符”不对应。

十、总结与推荐

	•  UTF‑8 是目前互联网上最常用的 Unicode 编码，兼容 ASCII，效率与自同步性好。
	•  实现解析或验证时必须严格遵守最短编码规则、拒绝 C0/C1、拒绝代理项、拒绝超出 U+10FFFF 的编码，并检查续字节。
	•  在大多数场景下优先使用语言或系统提供的成熟库来做编码/解码与验证。
