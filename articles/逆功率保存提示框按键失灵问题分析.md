# 逆功率保存提示框按键失灵问题分析

- 分析日期：2026-10-16。
- 原分析基线：`master / c4924af8`。
- 分析对象：C0/C1 V2 路径的逆功率参数设置、消息框、按键采样和 RELEASE 调度。
- 验证范围：源码和提交差异分析；未连接目标机，未进行硬件复现、编译或运行测试。
- 本文只记录分析与修改建议，不表示相关修复已经实施。

## 1. 现象与结论

进入 `SetOledReversePowerParameter` 修改参数，例如“刚性调节”，确认保存后显示成功提示。成功提示已经出现时，首次新按 OK 未能正常关闭，出现约 2～5 秒停顿，再按 OK 才能退出。其他菜单的按键响应正常。

这里分析的是成功提示内额外的一次 OK 无效，不是“保存确认和关闭提示各按一次”的正常交互。

**静态分析尚未确认唯一根因。**当前源码没有要求 ShowMsg 双击 OK 的逻辑，也不支持简单归因为“高优先级消息框忙循环饿死 TCA 线程”。已确认输入有效性、事件投递和锁返回值处理存在缺陷，但缺少现场时间轴，不能证明某项缺陷就是本次秒级停顿的原因。

必须区分四条路径：

1. TCA 没有取得有效的按下或释放样本。
2. 扫描线程没有形成新事件，或者事件入队失败。
3. 事件成功入队，但消息框未及时消费。
4. 消息框已经消费并返回，但父菜单显示延迟。

## 2. 版本和工作区说明

原分析基线中，`oled_creatKeyThread` 在 RELEASE 下显式请求 `SCHED_RR / osPriorityNormal`。

整理本文时，工作区已有 `src/protocol/oled/oledShow.c` 的未提交修改，移除了扫描线程的显式策略、优先级设置及 EPERM 重试分支。当前函数使用 `pthread_attr_init` 后的默认继承方式创建 `lcd_ctl`。

**当前工作区不能再描述为扫描线程显式请求 RR50，也不能描述为已强制改成 SCHED_OTHER。**它继承创建者的实际调度属性；当前由显示线程创建，若创建者实际为 RR50，扫描线程通常也继承 RR50。

当前工作区参考：`src/protocol/oled/oledShow.c:792–835`、`:883`。本文保留该用户修改，不对其效果作未经实测的判断。其他引用行号以分析时源码为准，后续编辑可能导致行号偏移。

## 3. 消息框前后的调用时序

```text
led_Thread → oled_notPollShow → SetOledReversePowerParameter
  → OLED_MenuRunPage
  → OledReversePowerHandlePageKey 处理编辑页 OK
  → ShowConfirm 消费“确认保存”的 OK
  → 恢复编辑页并刷新
  → OledReversePowerWriteValue 同步保存
  → OledReversePowerShowMessage
      → OLED_MenuPrepareRender：恢复检查、布局复位、清显存
      → OLED_Refresh：发送空白帧
      → ShowMsg：绘制结果，等待新的 OK 或 RETURN
      → OLED_MenuPrepareRender：恢复检查和清显存
  → 页面回调返回 EXIT
  → 父菜单重绘
```

关键位置：

- 确认、恢复编辑页、保存和提示：`src/protocol/oled/oled_reverse_power_menu.c:433–449`。
- 消息包装函数：`src/protocol/oled/oled_reverse_power_menu.c:262–273`。
- 消息框取键和退出：`src/protocol/oled/menu.c:2577–2597`。
- 页面退出：`src/protocol/oled/oled_menu_runtime.c:203–212`。
- 父菜单重绘：`src/protocol/oled/menu.c:554–560`。

`ShowMsg` 收到第一个有效 OK 或 RETURN 就返回，没有双击计数。未退出轮执行 `OLED_MenuFinishCycle(1, 0, 1, 50)`，最后请求休眠 50 ms，不是无休眠忙循环。

维护函数位置：`src/protocol/oled/oled_menu_runtime.c:114–134`。

**成功提示出现，意味着该次同步保存已经返回。**保存阶段的锁等待不能直接解释成功框稳定显示后的首次 OK 无效。反之，屏幕仍显示成功提示，也不等于程序仍停留在 ShowMsg：它可能已经返回，随后被恢复或刷新拖住。

## 4. RELEASE 调度关系

### 4.1 原基线的配置

| 线程 | RELEASE 下请求策略 | 请求优先级 | 依据 |
|---|---|---:|---|
| `led_Thread` | SCHED_RR | Normal＝50 | `src/main.c:97` |
| `Tca955_Io_tread` | SCHED_RR | Normal＝50 | `src/main.c:374,398` |
| `lcd_ctl` | SCHED_RR | Normal＝50 | 原基线 `src/protocol/oled/oledShow.c:826–858` |

优先级定义：`src/system/system.h:18–22`。当前工作区扫描线程的变化见第 2 节。

`ShowMsg` 在显示线程内同步执行，不是新建的高优先级线程，也没有在入口提升优先级。因此不能根据原配置推出“显示高、按键低，被消息框饿死”。

### 4.2 配置不等于实际策略

定义 RELEASE 后，通用创建函数显式设置实时策略和优先级。创建遇到 EPERM 时，回退到继承创建者属性，不保证是 SCHED_OTHER。非 RELEASE 也不等于强制普通调度。

依据：`src/system/system.cpp:106–153`、`:229–265`。

SCHED_RR 的轮转仅针对同优先级可运行线程，不能保证低优先级任务获得时间片。现场是否存在高优先级负载、不同回退结果、CPU 亲和性或 RT 配额影响，仍需实测；不能用默认 RT 限流直接推导固定 2～5 秒。

## 5. 输入链路中的已确认问题

### 5.1 失败读仍发布状态

`GetTca955_InputVal` 使用清零缓冲区，读取后立即更新全局按键状态，到函数末尾才检查错误。按键低有效，读取失败留下的零值可能被解析为按下。

位置：`src/bsp/tca955io/tca955.c:919–937`、`:995–998`。

修改建议：

- 当前读取提交两条 I2C 消息，应校验完整成功返回值为 2，再使用数据。读取实现见 `tca955.c:497–514`。
- 先读临时变量，成功后才发布对应端口状态；失败保留上次有效值并标记没有新有效样本。
- 按端口判断有效性，不把第二片读取失败等同于第一片按键样本无效。
- 上下游使用同步快照，锁内只复制数据，不做 I2C 或日志。`volatile` 不能替代线程同步。

### 5.2 必须观察到释放，才能形成下一次 OK

扫描仅在软件状态由 RELEASED 变为 PRESSED 时入队。确认保存后如果释放未被观察到，成功框内再次按下仍会被当成持续按住，不产生新事件。

位置：`src/protocol/oled/oledkey.c:173–194`。

TCA 本轮工作后请求休眠约 20 ms，扫描本轮工作后请求休眠 50 ms，均不是精确定时周期。位置：`src/bsp/tca955io/tca955.c:1096–1123`；`src/protocol/oled/oledkey.c:444–457`。

修改建议：按下和释放都基于有效新样本确认。去抖应使用成功采样序号或单调时间，不能将反复读取同一缓存当成多次硬件采样。不要进入弹框就强制置 RELEASED，否则仍按住的确认键可能被误当成新 OK。

### 5.3 入队失败后仍标记按下

入队失败后仍设置 PRESSED，持续按住不会重试。位置：`src/protocol/oled/oledkey.c:175–185`。

修改建议：区分输入状态和事件投递状态，记录队列满、未就绪、停止等原因。若增加重试，明确只投递一次、释放后如何处置未投递事件及页面切换后的归属，防止延迟 OK 在下一层页面执行。

正常弹框路径没有发现无条件清空队列，不能声称提前按的 OK 必然被清除，也不建议为修复而无条件清队列。

## 6. 秒级阻塞候选：尚需实机验证

### 6.1 TCA 每轮不只有输入读取

采集线程还执行输出更新、本机输入更新和周期配置检查。输出变化及配置检查均可能调用同步 I2C，部分分支还会记录日志。

位置：`src/bsp/tca955io/tca955.c:1096–1123`、`:551–619`、`:843–887`。

本轮后半段阻塞会推迟下一次输入采样。因此计时应覆盖整轮及各子操作，不能只测 GetTca955_InputVal。没有证据证明这些操作由 ShowMsg 特有地触发。

### 6.2 同步日志可能反过来阻塞采样

启用 `DEBUG_OUT_TO_SCREEN` 时，TCA 状态变化日志和扫描入队日志会进入共享日志锁及同步 stdout 输出。日志锁等待截止时间配置为 2000 ms，持锁期间还有格式化输出和 fflush。

依据：`src/misc/basedef.h:178–183`；`src/misc/basedef.c:33,61–78,352–417`；`src/bsp/tca955io/tca955.c:943–977`。

可能链路是：读到按下并发布状态后，日志阻塞，导致下一次释放采样延后，继而没有新按下事件。扫描线程也可能被其入队日志拖慢。

**这是有条件的候选原因，不是已定位根因。**当前 `src/common/DebugPrintf.h:17` 的宏定义处于注释状态，RELEASE 本身不表示启用该宏。2 秒只是锁等待截止时间，不是整个日志操作的耗时上限。没有日志也不能直接证明没有采样。

### 6.3 OLED 同步 I/O 和恢复

OLED 配置 `/dev/i2c-1`，TCA 配置 `/dev/i2c-2`。当前证据不支持共用同一用户态 fd 或同一应用层总线锁；底层 adapter 拓扑需现场核对。

依据：`src/protocol/oled/oled.h:24`；`src/bsp/tca955io/tca955.h:540`。

OLED 只发送变化页，但发送为同步 I2C_RDWR，错误可能触发后续重初始化。其驱动耗时上界不能由应用源码确定。

依据：`src/protocol/oled/oled.c:243–297`、`:525–538`、`:153–165`。

建议计时慢 ioctl、重初始化及父菜单首帧；不能把 ioctl 墙钟耗时全部等同于占用总线时间。

### 6.4 保存锁和冗余刷新

保存路径存在两秒截止时间的 timedlock，但不是固定睡眠，也不是保存总时限。相关返回值未检查，失败后仍操作并解锁，是确定需要修复的正确性缺陷。

依据：`src/protocol/ReversePower/ReversePower.cpp:240–247,277–282`；`src/protocol/ReversePower/ReversePowerParase.cpp:359–416`。

建议锁失败立即返回错误，只在成功持锁后操作和解锁；同时检查文件写入、关闭及下层保存结果，失败不能显示成功。

确认“是”后恢复编辑页、随后发送空白帧属于冗余刷新。建议只在取消保存时恢复编辑页，提示前直接清显存、绘制提示、一次刷新；必须先刷新提示首帧再等待按键。减少传输不等于已证明能解决秒级停顿。

## 7. 最小实机验证与判定闭环

### 7.1 准备与记录

1. 核对可执行文件版本、产品宏、RELEASE、DEBUG_OUT_TO_SCREEN。
2. 查询三个线程的实际策略和优先级。目标机工具支持时使用以下只读命令，将占位符替换为实际编号：

```sh
ps -L -p <PID> -o pid,tid,comm,cls,rtprio,pri,stat,wchan
chrt -p <TID>
```

3. 使用 CLOCK_MONOTONIC，记录 TCA 有效样本序号和原始 OK 位、扫描释放/按下、入队结果、ShowMsg 进入/消费/返回、OLED 慢操作、保存起止和父菜单首帧。
4. 避免采样线程逐轮同步打印，优先预分配的线程独立有界记录，事后汇总；记录异常间隔和状态变化即可。

统一时间轴：

```text
TCA 有效释放 → 扫描观察释放 → TCA 有效按下
→ 扫描识别新按下 → 入队 → ShowMsg 消费并返回 → 父菜单首帧完成
```

### 7.2 复现与判定

先按原速度复现，再测试明确释放、提示稳定后重新按 OK，以及一次较长按压。较长按压只用于区分短按遗漏，不是建议用户用长按规避缺陷。

| 观测结果 | 判定方向 |
|---|---|
| TCA 有效采样出现秒级空档 | 分段测输入读取、日志、输出更新、配置检查及调度等待 |
| 持续成功采样却未观察到短按 | 对照采样间隙及必要的引脚波形，软件日志不能证明物理电平 |
| TCA 有释放和按下，扫描没有新事件 | 查扫描周期、缓存同步及释放识别 |
| 新按下识别成功，入队失败 | 查队列容量、就绪和停止状态 |
| 入队成功，ShowMsg 消费晚 | 查显示线程同步操作、积压或调度 |
| ShowMsg 已返回，父菜单显示晚 | 查返回维护和刷新，不应继续称为消息框要求第二次 OK |
| 仅保存阶段耗时数秒 | 查保存锁及文件操作，不能解释提示稳定后的丢键 |
| 日志操作耗时明显 | 用低扰动记录做对照，避免诊断本身造成停顿 |

### 7.3 对照和回归

- 普通目录菜单用于对照输入响应；备自投页具有相似的确认、保存、成功提示流程，可作同构对照，但不能当作无缺陷基线。参考 `src/protocol/oled/oled_bzt_menu.c:572–595`。
- 每次只改一个因素，验证一次有效新 OK 能关闭提示、取消仍恢复编辑页、错误不报成功、提示首帧不被跳过、没有残留 OK 在父菜单执行。
- 高扰动跟踪、硬件故障注入仅在安全维护环境开展。

## 8. 建议执行顺序与最终边界

1. 先取得最小时间轴，确定首次 OK 丢失或延迟在哪一层。
2. 修复失败读发布输入、入队失败处理及锁返回值等已确认问题。
3. 局部减少编辑页和提示前空白帧，不先重构全部弹框。
4. 若证据指向日志，消除采样关键路径对同步日志的依赖；若指向 OLED，则处理对应慢 I/O 或恢复路径。
5. 只有测出保存确实长，才考虑异步保存，并单独定义完成事件和页面生命周期。

不建议优先全局升降线程优先级、删除休眠、关闭实时限流、添加全局 I2C 大锁或仅添加 volatile。

**源码分析与修改建议已经完成；2～5 秒停顿的唯一根因尚未实机确认。**本文不以工作流完成或时间数值相似作为复现证据，不将当前用户工作区的调度修改视为已经验证有效的修复。
