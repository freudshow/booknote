# E9361-A0 文件系统崩溃原因分析

## 工程概述

| 项目 | 详情 |
|------|------|
| MCU | STM32F103 (Cortex-M3) |
| RTOS | RTX (Keil CMSIS-RTOS) |
| 文件系统 | FatFs R0.14 |
| 外部存储 | SPI Flash W25Q64E (SPI3) + SPI FRAM FM25CL64 (SPI2) |
| 内部存储 | STM32 片内 Flash |
| FAT 卷 | VOL_PARA (0:) 3.5MB 参数文件, VOL_VAR (1:) 4MB 可变数据 |
| 扇区大小 | 4096 字节 (FF_MAX_SS) |
| 线程安全 | FF_FS_REENTRANT=1 (信号量), FF_FS_LOCK=0 (无文件锁) |

---

## 一、掉电保护机制存在漏洞（最高风险）

### 1. 掉电检测阈值不一致，存在写入窗口

- `terminalPowerDown()` 在 `s_lowVolCount > 2` 时返回1（`SystemHook_Dcai.c:83`）
- `willPowerDown()` 在 `s_lowVolCount > 4` 时返回1（`SystemHook_Dcai.c:97`）
- `disk_write` 用 `terminalPowerDown()` 判断（`diskio.c:238`），而 `SystemTask` 用 `willPowerDown()` 设置 `ResetFlag`（`SystemTask.c:261-263`）

**问题**：`s_lowVolCount` 从2到4之间，`disk_write` 已拒绝写入但 `ResetFlag` 尚未设置，而 `f_open`/`f_write` 层面的保护（`ff.c:3684-3688`）依赖 `GetResetFlag()`，此时可能仍在执行写操作。

### 2. `disk_write` 有保护，但 `f_sync` 没有保护

- `diskio.c:238` 在 `disk_write` 层检查掉电并返回 `RES_WRPRT` 拒绝写入
- `ff.c` 中的 `f_open`（3684行）和 `f_write`（3984行）也加了 `GetResetFlag()` 检查
- **关键遗漏**：`f_sync()` 函数没有加掉电检查，而代码中大量调用 `f_sync()`（几乎每个写操作后都调用），`f_sync` 内部会触发 `disk_write` 写 FAT 表和目录项

### 3. SPI Flash 先擦后写，非原子操作

- `disk_write` 对 SPI Flash 的操作是：`SPI_FLASH_SectorErase` → `SPI_FLASH_BufferWrite`（`diskio.c:255-256`）
- 擦除一个 4KB 扇区需要 30-300ms，写入也需要时间
- **如果在擦除完成、写入未完成时掉电，该扇区数据全部丢失**（全变成 0xFF）
- 内部 Flash 的 `disk_write` 同样存在此问题：先擦 2KB 页再写（`diskio.c:214-229`）

### 4. 掉电检测依赖 ADC 采样周期

- ADC 采样在 `GetAdcVal` 中，每 2 秒执行一次（`OtherTask_HookProcAdd(GetAdcVal, 20)` → 20×100ms）
- `SystemTask` 每 100ms 检查 `willPowerDown()`
- **如果电压在两次采样之间瞬间跌落到工作电压以下**，Flash 操作可能在 MCU 还未检测到掉电时就已经出错

---

## 二、多线程并发竞争（高风险）

### 5. SOE 文件写入无互斥保护

- `WriteSoeToFile()`（`Soe_fileOper.c:317`）和 `Write104FormatSoeFile()`（`Soe_fileOper.c:192`）操作共享的全局/静态变量：
  - `WriteSoePos`、`WriteSoePoling`（`Soe_fileOper.c:32-33`）
  - `g_ucFlag`、`g_uiSoeNum`、`g_arrSOE_NO[]`（`Soe_fileOper.c:25-27`）
- 这些函数从 `YcOverLimit_tread` 线程调用（`YcLimit.c:508,521,648,700,736`），如果其他协议线程也调用，会导致竞态条件
- **没有 mutex 保护**，多个线程同时写入会导致文件指针、写入位置、FAT 表不一致

### 6. Debug 文件写入 mutex 被注释掉

- `Debug_fileOper.c:43` 注释明确写道：`// 文件系统底层的操作已经有了相应的同步机制，此处去掉`
- 但 `WriteDebugPos` 和 `WriteDebugPoling` 是全局静态变量（`Debug_fileOper.c:17-18`），多线程同时调用 `WriteDebugToFile` 会导致竞态
- FatFs 的 `FF_FS_REENTRANT` 只保护**同一个 volume 内**的并发访问，不保护**应用层的逻辑竞态**

### 7. FatFs 使用信号量而非互斥量，无优先级继承

- `ffsystem.c:62` 使用 `osSemaphoreCreate`（计数信号量）而非 mutex
- `spi_core.h:63` 中 `_USE_SPI_MUX_t` 被注释掉，SPI 总线也用信号量
- **无优先级继承**：如果高优先级任务等待低优先级任务持有的信号量，可能导致优先级反转，延长关键操作时间

### 8. FatFs 信号量超时仅 20 个 tick

- `ffconf.h:283`：`FF_FS_TIMEOUT = 20`
- SPI Flash 扇区擦除可能需要 300ms，如果一个线程持有信号量执行擦除，其他线程在 20 tick（约 20ms）内获取不到信号量，`ff_req_grant` 返回 0，导致 `FR_TIMEOUT`
- **FR_TIMEOUT 后文件操作被放弃，但部分 FAT 结构可能已经修改**

### 9. `FF_FS_LOCK = 0`，无文件锁保护

- `ffconf.h:269`：`FF_FS_LOCK = 0`
- 多个线程可以同时打开同一文件进行写操作，FatFs 不会阻止
- `common_fileOper.c` 中大量函数（如 `WriteStructToFile`、`ContinueWriteData`、`WriteDataByPosition`）都直接打开文件写入，无应用层锁

---

## 三、SPI Flash 驱动层问题（中高风险）

### 10. SPI Flash 写入无超时保护

- `SPI_FLASH_WaitForWriteEnd()`（`spi_flash.c:567-583`）使用 `do { delay_ms(1); ... } while ((recv_buff[0] & WIP_Flag) == SET)` 无限循环
- **如果 Flash 芯片损坏或 SPI 通信异常，此函数会永久阻塞**，导致看门狗超时复位
- 复位发生在 Flash 操作中间，文件系统可能被破坏

### 11. SPI 信号量超时 10ms 可能不够

- `spi_core.h:60`：`_SPI_TIMEOUT = 10`（10ms）
- Flash 扇区擦除期间（30-300ms），SPI 总线被占用
- 如果多个线程竞争 SPI3（Flash），10ms 超时后 `spi_req_grant` 返回 -1，后续 SPI 传输返回错误数据
- **错误的 SPI 数据写入 Flash 会直接破坏文件系统**

### 12. SPI Flash 初始化条件判断有问题

- `spi_flash.c:126-128`：
  ```c
  if (spi_flash_dev.InitFlag==SPI_FLASH_Inited) return 0;
  if (spi_flash_dev.InitFlag!=SPI_FLASH_Inited) { ... }
  ```
- 两个条件互为补集，逻辑上等价于直接执行初始化体，但每次 `disk_initialize` 都会重新初始化 SPI（DeInit + Init），可能干扰正在进行的 SPI 传输

---

## 四、FatFs 配置和使用问题（中风险）

### 13. LFN 使用堆内存，可能耗尽

- `ffconf.h:119`：`FF_USE_LFN = 3`（堆分配）
- `ffsystem.c:24`：`ff_memalloc` 调用 `mymalloc(SRAMEX, msize)`
- LFN 需要 `(255+1)*2 = 512` 字节 + 额外缓冲
- **如果 SRAMEX（512KB 外部 SDRAM）内存碎片化严重或耗尽，LFN 分配失败，文件操作可能返回错误或产生未定义行为**

### 14. `scan_files` 中使用静态 LFN 缓冲区，非线程安全

- `common_fileOper.c:775`：`static char lfn[_MAX_LFN * 2 + 1] = {0};`
- 静态变量在多线程环境下不安全，两个线程同时调用 `scan_files` 会互相覆盖 LFN 缓冲区

### 15. `f_sync()` 在只读操作中不必要地调用

- 多个只读函数（如 `ReadFileToStruct`、`ReadExpandSysParToRam`、`GetFileSize`）在 `f_open` 后调用 `f_sync(fd)`
- `f_sync` 对只读文件也会更新目录项的时间戳，产生不必要的 Flash 写操作
- **每次不必要的写操作都增加掉电时损坏的风险**

### 16. `FirstCreateFile` 先删后建，非原子操作

- `common_fileOper.c:136`：`f_unlink(file_name)` 然后 `f_open(fd, file_name, FA_CREATE_ALWAYS | ...)`
- 如果在 `f_unlink` 成功后、`f_open` 完成前掉电，文件丢失
- 此函数在初始化时被调用（`Debug_fileOper.c:52`），可能导致 debug.dat 丢失

---

## 五、内存和栈问题（中风险）

### 17. FIL 结构体从 SRAMEX 动态分配

- `common_fileOper.h:87`：`#define NEW_FD(fd) FIL *fd = (FIL*)mymalloc(SRAMEX, sizeof(FIL))`
- 每个文件操作都从外部 SDRAM 分配 FIL（约 556 字节）
- **如果堆碎片化导致分配失败（返回 NULL），虽然有 NULL 检查，但 SRAMEX 堆本身的元数据可能已被破坏**

### 18. 协议线程栈大小不一，存在栈溢出风险

- 各协议线程栈大小：512~8192 字节不等（`main.c:306,321,331,343,350,355`）
- FatFs 操作使用栈上的 `DEF_NAMBUF` 缓冲区
- **栈溢出会破坏相邻内存，包括 FatFs 的 FATFS 结构体或文件对象，导致文件系统崩溃**

### 19. 内部 Flash 的 `RAM_disk_read` 存在类型转换问题

- `flash.c:59`：`data16 = *(__IO uint32_t *)FlashAddress;`
- 变量名是 `data16` 但实际读取了 32 位，只使用低 16 位
- 虽然功能上正确（STM32F1 Flash 是 16 位半字编程），但如果 `FlashAddress` 未对齐到 32 位边界，可能触发 HardFault

---

## 六、文件系统完整性问题（中风险）

### 20. 无文件系统完整性校验

- `FileSetup`（`common_fileOper.c:624`）仅通过 `file_flag` 标志判断是否格式化
- **没有 `f_checkfs` 或等效的完整性检查**，如果 FAT 表部分损坏但能挂载，后续操作会在损坏的基础上继续，导致问题扩散

### 21. 无备用 FAT 表

- FatFs 默认不使用备用 FAT 表
- FAT 表是文件系统的核心结构，一旦损坏，整个卷的数据丢失
- SPI Flash 上的两个卷（VOL_PARA 和 VOL_VAR）都没有备用 FAT

### 22. 无数据完整性校验（CRC/校验和）

- 文件数据存储时没有附加 CRC 或校验和
- Flash 位翻转（bit-rot）或部分写入会导致静默数据损坏
- `ReadFileGetOnePackData` 中的 CRC 是用于文件传输校验，不是存储完整性校验

---

## 七、系统级问题（中低风险）

### 23. HardFault 处理不当

- `stm32f10it.c:484-494`：`HardFault_Handler` 直接在 `while(1)` 中调用 `NVIC_SystemReset()`
- **没有保存任何故障上下文**（SCB->CFSR、MMFAR、BFAR、LR、PC）
- 如果 HardFault 发生在 Flash 写操作期间，复位后文件系统已损坏但无法诊断原因

### 24. 看门狗超时时间过长

- `SystemTask.c:42-53`：`IWDG_Init` 配置预分频 256、重装值 4000
- 超时时间 = `(4×2^6 × 4000) / 40 = 25,600ms ≈ 25.6秒`
- **如果系统死锁 25.6 秒后才复位**，期间可能有大量文件操作异常

### 25. SPI Flash 扇区擦除期间看门狗未喂狗

- `SPI_FLASH_SectorErase` → `SPI_FLASH_WaitForWriteEnd` 是阻塞的（可能 300ms）
- 在此期间不调用 `IWDG_Feed()`
- 如果多个扇区连续擦除，累积时间可能触发看门狗复位

---

## 八、应用层逻辑问题（低风险）

### 26. `replaceLine`/`deleteLine`/`insertLine` 使用 swap 文件，非原子操作

- `common_fileOper.c:1458-1522`：先创建 swap 文件，拷贝数据，再 `f_unlink` + `f_rename`
- 如果在 `f_unlink` 后、`f_rename` 前掉电，原始文件已删除但 swap 文件未重命名，数据丢失

### 27. `SysReset` 中 `osDelay(6000)` 不可靠

- `common.c:73`：`SetResetFlag(); osDelay(6000); NVIC_SystemReset();`
- 依赖 RTX 调度器在 6 秒内正常运行
- 如果系统已经不稳定（如栈溢出、死锁），`osDelay` 可能永远不返回

### 28. `WriteDebugToFile` 在 `WriteDebugPoling` 模式下多次打开文件

- `Debug_fileOper.c:81-106`：每次写入都 `f_open` → `f_lseek` → `f_write` → `f_sync` → `f_close`
- 高频写入时，频繁的打开/关闭操作增加 FAT 表操作次数，增加损坏概率

---

## 总结：最关键的 3 个问题

| 排序 | 问题 | 文件位置 | 影响 |
|------|------|----------|------|
| **1** | SPI Flash 先擦后写，掉电时扇区数据全丢 | `diskio.c:255-256` | FAT 表/目录/数据全部丢失 |
| **2** | SOE/Debug 文件操作无应用层互斥，多线程竞态 | `Soe_fileOper.c:32-33`, `Debug_fileOper.c:17-18` | 文件指针错乱、数据覆盖 |
| **3** | `FF_FS_LOCK=0` + 信号量超时 20tick，高负载时 FR_TIMEOUT | `ffconf.h:269,283` | 部分 FAT 修改后操作被放弃 |

# 附录：基于 FatFs R0.14 原理的完整文件系统破坏场景分析

> 本节从 FatFs R0.14 源码层面分析所有可能导致**整个文件系统结构被破坏**（而非单个文件丢失）的场景。分析基于本工程使用的 FatFs R0.14b 源码（ff.c, 7007 行）。

---

## A. FatFs R0.14 架构核心机制

### A.1 单扇区窗口缓存（Single-Sector Window Cache）

FatFs 的核心设计是**单扇区缓存**机制。整个文件系统共用一个扇区缓冲区：

```
FATFS 结构体:
  win[FF_MAX_SS]   ← 唯一的扇区缓冲区（4096 字节）
  winsect           ← 当前缓存的扇区号
  wflag             ← 脏标记（1 = win[] 已修改但未写回磁盘）
```

**关键特性**：
- 所有 FAT 表修改、目录项修改、FSINFO 修改都通过 `win[]` 进行
- 当需要访问不同扇区时，`move_window()` 先调用 `sync_window()` 将当前脏扇区写回，再加载新扇区
- **同一时刻最多只有一个扇区处于"已修改未写回"状态**

这意味着：FatFs 的单扇区缓存提供了一定程度的串行化保护（同一时刻只有一个扇区在修改），但**跨扇区的操作（如 FAT 表 + 目录项）仍然不是原子的**。

### A.2 sync_window — 最底层的磁盘写入

```c
// ff.c:1041-1059
static FRESULT sync_window(FATFS* fs)
{
    if (fs->wflag) {
        disk_write(fs->pdrv, fs->win, fs->winsect, 1);  // 写主 FAT
        if (fs->n_fats == 2) {
            disk_write(fs->pdrv, fs->win, fs->winsect + fs->fsize, 1);  // 写镜像 FAT
        }
        fs->wflag = 0;
    }
}
```

**写入顺序**：先写主 FAT 扇区，再写镜像 FAT 扇区。两次 `disk_write` 之间没有原子性保证。

### A.3 move_window — 扇区切换与自动刷写

```c
// ff.c:1063-1084
static FRESULT move_window(FATFS* fs, LBA_t sect)
{
    if (sect != fs->winsect) {
        sync_window(fs);  // 刷写当前脏扇区
        disk_read(fs->pdrv, fs->win, sect, 1);  // 加载新扇区
        fs->winsect = sect;
    }
}
```

**重要**：每次切换到不同扇区时，旧扇区会被刷写。这意味着 FAT 操作和目录操作是交替进行的，每次切换都会触发实际的磁盘写入。

### A.4 sync_fs — 完整文件系统同步

```c
// ff.c:1094-1120
static FRESULT sync_fs(FATFS* fs)
{
    sync_window(fs);                    // 步骤1: 刷写当前脏扇区（1-2 次 disk_write）
    if (fs->fsi_flag == 1) {            // 步骤2: 写 FSINFO 扇区（FAT32）
        fs->winsect = fs->volbase + 1;
        disk_write(fs->pdrv, fs->win, fs->winsect, 1);
        fs->fsi_flag = 0;
    }
    disk_ioctl(fs->pdrv, CTRL_SYNC, 0); // 步骤3: 硬件刷新（本工程未实现，为空操作）
}
```

**本工程问题**：`CTRL_SYNC` 在 `diskio.c` 中未实现（直接返回 `RES_OK`），意味着 SPI Flash 的写入缓存不会被强制刷新，掉电时可能丢失未刷出的数据。

---

## B. 各文件系统操作的写入时序与掉电风险

### B.1 f_write — 写入文件

**写入时序**（FAT32，跨簇边界时）：

```
步骤1: create_chain() 分配新簇
  ├── put_fat(新簇, 0xFFFFFFFF)  → 写 FAT 扇区 A（标记新簇为 EOC）
  └── put_fat(旧簇, 新簇号)       → 写 FAT 扇区 B（链接旧→新）
      每次 put_fat 都可能触发 sync_window → disk_write

步骤2: disk_write(fp->buf, fp->sect)  → 写旧的数据扇区

步骤3: disk_write(wbuff, sect, cc)    → 写新的数据扇区
```

**注意**：`f_write` **不会更新目录项中的文件大小**，也不会调用 `f_sync`。文件大小的更新推迟到 `f_sync` 或 `f_close` 时进行。

**掉电风险**：
| 掉电时刻 | 簇链状态 | 目录项状态 | 结果 |
|----------|---------|-----------|------|
| 步骤1 中间 | 新簇已标记 EOC 但未链接到旧簇 | 未修改 | **孤儿簇**（空间泄漏） |
| 步骤1 完成后 | 新簇已链接 | 未修改（旧大小） | 数据已写但目录未反映，安全 |
| 步骤2 后 | 完整 | 未修改 | 安全（数据已持久化） |
| 步骤3 中间 | 完整 | 未修改 | 部分数据扇区已写，安全 |

**结论**：`f_write` 本身不会导致目录/FAT 不一致，但可能产生孤儿簇（空间泄漏）。

### B.2 f_sync — 同步文件

**写入时序**：

```
步骤1: disk_write(fp->buf, fp->sect)  → 写脏的数据扇区
步骤2: move_window(fs, fp->dir_sect)  → 加载目录项扇区
        └── 若窗口不同，先 sync_window → disk_write（写旧的 FAT/目录扇区）
步骤3: 更新目录项（大小、时间、起始簇）→ win[] 标记为脏
步骤4: sync_fs(fs)
        ├── sync_window() → disk_write(目录扇区)  ← 步骤5
        └── disk_write(FSInfo扇区)                 ← 步骤6
```

**掉电风险**：
| 掉电时刻 | FAT 状态 | 目录项状态 | 结果 |
|----------|---------|-----------|------|
| 步骤1 中间 | 完整 | 完整 | 数据扇区部分写入，文件大小未变，安全 |
| 步骤5 中间 | 完整 | **已写入新大小** | 目录项指向部分写入的数据，可能读到脏数据 |
| 步骤6 中间 | 完整 | 完整 | FSINFO 的 free_clst 不准确，下次 mount 可修复 |

**关键**：步骤5（目录项写入）和步骤1（数据写入）之间没有原子性保证。如果目录项先于数据扇区写入磁盘，且此时掉电，文件会指向未完全写入的数据扇区，导致**读到不一致的数据**。

### B.3 f_open — 创建/覆盖文件（FA_CREATE_ALWAYS）

**写入时序**（覆盖已有文件时）：

```
步骤1: 在目录中找到文件 → 加载目录项扇区
步骤2: 读取旧文件的起始簇号 cl
步骤3: 重置目录项（属性=ARC, 起始簇=0, 大小=0）→ win[] 标记为脏
步骤4: remove_chain(cl)  → 逐个释放旧簇链
  ├── put_fat(簇1, 0) → move_window → sync_window → disk_write(FAT扇区)
  ├── put_fat(簇2, 0) → move_window → sync_window → disk_write(FAT扇区)
  └── ... 每个簇都可能触发 sync_window
步骤5: move_window(fs, sc) → 重新加载目录项扇区
        └── sync_window → disk_write（写 FAT 扇区）
```

**注意**：步骤3（目录项重置）在步骤4（释放旧簇链）之前，但目录项修改仅在 `win[]` 内存中，不会立即写入磁盘。实际写入磁盘发生在步骤5的 `sync_window` 中。

**掉电风险**：
| 掉电时刻 | FAT 状态 | 目录项状态 | 结果 |
|----------|---------|-----------|------|
| 步骤3 之后、步骤4 中间 | 旧簇链**部分释放** | 仍在 win[] 中未写磁盘 | FAT 泄漏：部分簇已释放，部分仍分配但不可达 |
| 步骤4 中间 | 旧簇链**部分释放** | win[] 中已重置 | 若 sync_window 已刷写目录扇区：**目录指向空簇 + 旧数据仍占簇** |
| 步骤5 的 sync_window 中 | 旧簇链全部释放 | 已写入磁盘 | 安全（但新文件内容为空） |

**最危险场景**：`remove_chain` 释放了一半旧簇链，此时目录项被刷写（通过 `move_window`），新文件目录指向起始簇=0（空），但旧簇链的后半段仍在 FAT 中占用空间。后续如果 `create_chain` 分配了这些"幽灵簇"，会产生**交叉链接**（cross-link）。

### B.4 f_unlink — 删除文件

**写入时序**：

```
步骤1: dir_remove() → 标记目录项为 DDEM（删除标记）→ win[] 脏
步骤2: remove_chain() → 逐个释放簇链
  ├── put_fat(簇1, 0) → move_window → sync_window → disk_write
  ├── put_fat(簇2, 0) → move_window → sync_window → disk_write
  └── ...
步骤3: sync_fs() → 最终同步
  ├── sync_window() → disk_write（目录/FAT 扇区）
  └── disk_write(FSInfo扇区)
```

**掉电风险**：
| 掉电时刻 | 目录项状态 | FAT 状态 | 结果 |
|----------|-----------|---------|------|
| 步骤1 完成后 | **已标记 DDEM**（但未刷写） | 完整 | 若 win[] 未刷写：安全；若已刷写：**文件目录项丢失，但簇仍占用** |
| 步骤2 中间 | 已标记 DDEM | **部分释放** | 簇泄漏：部分簇释放，部分仍分配但文件已删除 |
| 步骤3 中间 | 已刷写 DDEM | 全部释放 | 安全（但 FSInfo 可能不准） |

**最危险场景**：目录项已被刷写为 DDEM（步骤1的 `sync_window` 在步骤2的 `move_window` 中触发），但簇链尚未完全释放。此时文件**无法恢复**（目录项已删除），但空间**无法回收**（簇仍标记为已分配）。反复发生会导致**可用空间逐渐耗尽**，最终无法分配新簇，文件系统"崩溃"。

### B.5 f_rename — 重命名文件

**写入时序**（FAT32）：

```
步骤1: dir_register() → 创建新目录项（新文件名）→ 可能触发 create_chain 扩展目录
步骤2: 更新子目录的 ".." 条目（如果是目录重命名）
步骤3: dir_remove() → 标记旧目录项为 DDEM
步骤4: sync_fs() → 最终同步
  ├── sync_window() → disk_write（目录扇区 A）
  ├── sync_window() → disk_write（目录扇区 B，如果与 A 不同）
  └── disk_write(FSInfo扇区)
```

**FatFs 源码明确标注**：
```c
// ff.c:5141
/* Start of critical section where an interruption can cause a cross-link */
...
// ff.c:5185
/* End of the critical section */
```

**掉电风险**：
| 掉电时刻 | 新目录项 | 旧目录项 | 结果 |
|----------|---------|---------|------|
| 步骤1 后、步骤3 前 | 已创建 | 仍在 | **交叉链接**：两个目录项指向同一数据簇 |
| 步骤3 后、步骤4 前 | 已创建 | 已标记 DDEM | 若未刷写：回滚到旧名；若已刷写：安全 |
| 步骤4 中间 | 部分刷写 | 部分刷写 | 不可预测：可能交叉链接、可能丢失 |

**最危险场景**：新目录项已写入磁盘，旧目录项尚未标记 DDEM。此时一个文件有两个目录项指向相同的数据簇（**交叉链接**）。后续修改任一目录项都会影响另一个，导致数据损坏。

### B.6 f_truncate — 截断文件

**写入时序**：

```
步骤1: 移动到文件末尾簇
步骤2: remove_chain() → 从当前簇开始释放到链尾
步骤3: 更新目录项中的文件大小（在 win[] 中标记脏）
步骤4: sync_fs() → 最终同步
```

**掉电风险**：如果步骤2释放了簇但步骤3的目录项未刷写，文件大小仍为原始值，指向已释放的簇。后续这些簇被重新分配后，旧文件会读到新数据（**数据污染**）。

## C. 完整文件系统破坏的典型场景

### 场景 1：FAT 表扇区擦写中途掉电（最常见、最严重）

**触发条件**：`sync_window()` 写 FAT 扇区时，SPI Flash 扇区擦除完成但数据写入未完成。

**FatFs 写入序列**：
```
disk_write(fat_sector) → diskio.c:255
  ├── SPI_FLASH_SectorErase(fat_sector)  // 30-300ms，扇区变 0xFF
  ├── SPI_FLASH_BufferWrite(data)         // 写入 FAT 数据
  └── 此时掉电！
```

**后果**：
1. FAT 扇区内容为 0xFF（全空）或部分写入的垃圾数据
2. 该扇区覆盖的 4KB FAT 区域内的所有簇链信息丢失
3. 下次 mount 时，FatFs 读取 FAT 表发现大量无效簇链
4. **整个卷的文件索引被破坏，所有文件不可访问**

**本工程特有风险**：
- SPI Flash W25Q64E 的扇区擦除粒度为 4KB，而 FatFs 的 FAT 扇区也是 4096 字节（`FF_MAX_SS`）
- 一个 `sync_window` 调用恰好擦写一个完整的 FAT 扇区
- **擦除 + 写入的总时间约 300-600ms**，远超电压跌落的检测窗口

### 场景 2：FAT 表 + 目录项跨扇区操作中途掉电

**触发条件**：`f_sync` 或 `f_close` 操作中，FAT 扇区已刷写但目录项扇区尚未刷写。

**时序**：
```
sync_window(fat_sector)     → disk_write: 擦写 FAT 扇区（300ms）
move_window(dir_sector)     → 先 sync_window（写 FAT），再读目录扇区
更新目录项（大小、时间）     → win[] 标记脏
sync_window(dir_sector)     → disk_write: 擦写目录扇区（300ms）
                              此时掉电！
```

**后果**：
1. FAT 表已更新（新簇链已记录）
2. 目录项未更新（文件大小仍为旧值）
3. 下次 mount 后，文件大小与实际簇链不匹配
4. FatFs 可能将超出旧大小的簇视为"未使用"，导致**数据被新文件覆盖**

### 场景 3：NewFileAndDeleteOldFile 模式中断电

**本工程的文件更新模式**（`common_fileOper.c`）：
```
f_open(新文件, CREATE_ALWAYS)  → 创建新文件
f_write(新数据)                 → 写入新数据
f_sync()                        → 刷写新文件
f_unlink(旧文件)                → 删除旧文件
f_rename(新文件→临时名)          → 重命名新文件
f_unlink(临时文件)               → 删除临时文件（如果存在）
f_rename(新文件→旧文件名)        → 重命名回旧文件名
```

**掉电在任何步骤之间**：
| 掉电位置 | 后果 |
|----------|------|
| f_write 后、f_sync 前 | 新文件数据未持久化，旧文件仍存在。安全 |
| f_sync 后、f_unlink 前 | 新旧文件并存。安全但浪费空间 |
| f_unlink 后、f_rename 前 | **旧文件已删除，新文件仍叫新名**。参数文件丢失！ |
| f_rename 后、第二次 f_unlink 前 | 新旧文件名交换，可能有临时文件残留 |
| 第二次 f_rename 后 | 安全 |

**最危险场景**：`f_unlink(旧文件)` 成功后、`f_rename(新文件→旧文件名)` 前掉电。此时：
- 旧参数文件已删除（目录项标记 DDEM）
- 新参数文件仍以 `new_xxx.dat` 命名，不在预期路径
- 系统重启后找不到参数文件 → **整个参数卷"丢失"**

### 场景 4：FAT 双写不一致掉电

**触发条件**：`sync_window` 中写主 FAT 和镜像 FAT 时掉电。

**时序**：
```
disk_write(主FAT, sector)    → 擦写主 FAT 扇区（300ms）
disk_write(镜像FAT, sector)  → 此时掉电！
```

**后果**：
1. 主 FAT 扇区已更新
2. 镜像 FAT 扇区仍为旧值或被部分擦除
3. 下次 mount 时，FatFs 只读取主 FAT（FAT32 默认不使用镜像 FAT 修复）
4. 如果主 FAT 也损坏（擦除未完成），则**整个卷不可恢复**

**本工程风险**：`ffconf.h` 中 `FF_FS_REENTRANT=1` 但未启用 `FF_FS_NOFSINFO`。FatFs R0.14 的 `sync_window` 在写主 FAT 后立即写镜像 FAT，两次写入之间没有校验。

### 场景 5：FSINFO 扇区损坏导致空间耗尽

**FSINFO 扇区**（FAT32 第 1 扇区）存储：
- `FreeClust`：剩余可用簇数
- `NxtFree`：下次分配的起始簇号

**触发条件**：`sync_fs` 写 FSINFO 时掉电，或 `f_write` 中 `create_chain` 更新 `free_clst` 但未刷写 FSINFO。

**后果**：
1. FSINFO 中的 `FreeClust` 与 FAT 实际空闲簇数不匹配
2. 如果 `FreeClust` 偏小：系统认为磁盘已满，**无法创建新文件**
3. 如果 `FreeClust` 偏大：系统尝试分配已被占用的簇，**导致交叉链接**
4. `NxtFree` 不准确：分配扫描从错误位置开始，性能下降但不致命

**本工程风险**：VOL_PARA 卷（参数文件）空间有限（3.5MB），如果 FSINFO 损坏导致 `FreeClust=0`，所有参数写入操作都会返回 `FR_DENIED`。

### 场景 6：目录扩展（create_chain）中途掉电

**触发条件**：大文件写入或目录项过多时，FatFs 需要扩展目录（分配新的目录簇）。

**时序**：
```
create_chain() → 在 FAT 中分配新簇 → put_fat(新簇, EOC) → put_fat(旧目录末簇, 新簇)
                → 此时掉电！
```

**后果**：
1. 新目录簇已在 FAT 中标记为 EOC（分配）
2. 旧目录簇未链接到新簇（链未建立）
3. 新目录簇中无有效目录项
4. 原目录末尾的目录项丢失 → **文件"消失"**

### 场景 7：remove_chain 释放簇后、更新目录项前掉电

**触发条件**：`f_open(FA_CREATE_ALWAYS)` 覆盖旧文件时。

**时序**：
```
remove_chain(旧簇链) → 逐个释放 FAT 条目 → 全部释放完成
move_window(目录扇区) → 此时掉电！
```

**后果**：
1. 旧簇链已全部释放（FAT 中标记为空闲）
2. 目录项中的起始簇仍指向旧值（但旧簇已被释放）
3. 下次 mount 后，目录指向的簇可能已被新分配
4. **交叉链接**：新文件和旧文件（已删除但目录项未更新）共享同一簇

### 场景 8：SPI Flash 扇区擦除与 FatFs 扇区对齐问题

**本工程配置**：
- FatFs 扇区大小：`FF_MAX_SS = 4096`
- SPI Flash 物理扇区大小：4KB（W25Q64E）
- VOL_PARA 起始扇区：128（偏移 512KB）
- VOL_VAR 起始扇区：1024（偏移 4MB）

**风险**：如果 FatFs 扇区号与 SPI Flash 物理扇区号未对齐，一次 `disk_write` 可能跨越两个物理扇区，需要两次擦除。在第一次擦除完成、第二次未开始时掉电，**两个物理扇区都被破坏**。

## D. 文件系统"完全破坏"的判定标准

以下任一情况发生，均可判定为**整个文件系统被破坏**：

| 破坏类型 | 判定条件 | 恢复可能性 |
|----------|---------|-----------|
| **FAT 表全损** | FAT 起始扇区（VBR 之后）被部分擦除或写入垃圾数据 | 无法恢复（无备份 FAT） |
| **VBR 损坏** | 引导扇区（扇区 0）被破坏，无法识别分区格式 | 无法恢复 |
| **FAT + 目录交叉不一致** | FAT 显示簇已分配，但目录项显示空；或反之 | 部分恢复（需专业工具） |
| **根目录损坏** | 根目录簇链断裂或内容被覆盖 | 所有根目录文件丢失 |
| **FSINFO + FAT 双损** | FSINFO 显示空闲空间为 0，且 FAT 实际也已损坏 | 无法恢复 |
| **所有参数文件丢失** | VOL_PARA 中的配置文件因 f_unlink + 掉电而全部删除 | 需重新配置 |

## E. 本工程特有的"文件系统完全破坏"高危路径

### E.1 参数卷（VOL_PARA）破坏路径

```
正常运行中:
  WriteStructToFile(param) → f_open(VOL_PARA, WRITE)
    → f_write(参数数据)
    → f_sync()               ← 触发 sync_window → disk_write(FAT扇区)
                                 SPI Flash 扇区擦除中... 掉电！
                                 FAT 扇区变 0xFF
    → f_close()
    
重启后:
  FileSetup() → f_mount(0:) → f_open(param.dat)
    → FatFs 读取 FAT 表 → FAT 扇区内容为 0xFF
    → f_mount 返回 FR_DISK_ERR 或 FR_NO_FILESYSTEM
    → 所有参数文件不可访问
```

### E.2 可变数据卷（VOL_VAR）破坏路径

```
正常运行中:
  WriteSoeToFile() → f_open(VOL_VAR, WRITE)
    → f_write(SOE数据)
    → f_sync()               ← 触发 sync_window
                                 此时 SOE 写入频繁，FAT 表频繁更新
                                 多个 FAT 扇区交替修改
                                 掉电！多个 FAT 扇区部分擦除
    → f_close()

重启后:
  f_mount(1:) → FAT 表多处损坏
    → ScanDirFile() → 遍历目录时访问损坏的 FAT 条目
    → 可能触发 FatFs 内部 assert 或返回 FR_INT_ERR
    → 所有日志/SOE/调试文件不可访问
```

### E.3 NewFileAndDeleteOldFile 模式下的参数卷"假性丢失"

```
正常运行中:
  每次写入参数:
    f_unlink(param_old.dat)   ← 旧参数文件删除（目录项标记 DDEM）
    f_open(param_new.dat)     ← 新参数文件
    f_write(...)
    f_sync(...)
    f_close(...)
    f_unlink(param.dat)       ← 删除旧的"正式"参数文件
    f_rename(param_new→param)  ← 新文件重命名为正式名

  掉电在 f_unlink(param_old.dat) 之后、f_rename 之前！
  
重启后:
  param_old.dat → 已删除（DDEM）
  param_new.dat → 存在但不是预期的文件名
  param.dat     → 已被 f_unlink 删除（如果执行到了那一步）
  
  → 系统找不到 param.dat → "参数文件丢失"
  → 实际数据在 param_new.dat 中，但系统不知道
```

| `f_truncate` | 4867-4908 | ❌ 无 | ❌ 无 | 高 |
| `f_mkdir` | 5011-5086 | ❌ 无 | ❌ 无 | 中 |

## G. 为什么"参数文件读不到"是最常见的表现

1. **参数文件写入频率高**：每次系统启动、每次遥测数据更新、每次配置变更都会调用 `WriteStructToFile`，触发 `f_open` → `f_write` → `f_sync` → `f_close` 完整序列
2. **NewFileAndDeleteOldFile 模式**：每次写入都涉及 `f_unlink` + `f_rename`，这两个函数无掉电保护
3. **VOL_PARA 空间小（3.5MB）**：FAT 表很小，一个 FAT 扇区损坏就可能影响所有文件的簇链
4. **参数文件是系统启动的必要条件**：没有参数文件，系统无法正常运行，表现为"文件系统崩溃"
5. **SPI Flash 扇区擦除时间长（300ms）**：远超电压跌落检测窗口，掉电时擦写中断概率极高

## H. 修复优先级建议（基于 FatFs 原理）

| 优先级 | 修复方案 | 原理 | 实现复杂度 |
|--------|---------|------|-----------|
| **P0** | 在 `f_sync`/`f_close`/`f_unlink`/`f_rename` 入口处加入 `GetResetFlag()` 检查 | 阻止掉电时执行文件系统修改操作 | 低（复制 f_write 的检查代码） |
| **P0** | `sync_window` 中在 `disk_write` 前检查掉电 | 最后一道防线，阻止 FAT/目录扇区被写入 | 低 |
| **P0** | 将 SPI Flash 的 `disk_write` 改为先写备份扇区，成功后再擦写主扇区 | 即使掉电，备份扇区仍完好 | 中（需要双倍 Flash 空间） |
| **P1** | 启用 `FF_FS_LOCK`（设为 5~10） | 防止多线程同时修改同一文件 | 低 |
| **P1** | `NewFileAndDeleteOldFile` 改为先写新文件 → f_sync → 再 f_unlink 旧文件 | 减少掉电时的不一致窗口 | 低（已实现，但需确认掉电检查覆盖） |
| **P2** | 在 `f_open(FA_CREATE_ALWAYS)` 中，先 `f_sync` 新文件再 `remove_chain` 旧链 | 确保新文件数据已持久化再释放旧空间 | 中 |
| **P2** | 启用 FatFs 的备用 FAT 表（需自定义实现） | 双 FAT 互为备份 | 高（FatFs 不原生支持） |
| **P3** | 为参数文件增加 CRC 校验头 | 检测静默数据损坏 | 中 |
